How to actually use AI to build a project

💡
In plain English
The failure mode is asking for the whole app in one prompt and hoping. It can write a lot of code fast, which is exactly the danger — a hundred lines you didn't read is a hundred lines you don't understand when they break at 2am. The fix isn't asking for less; it's asking for it in an order you can review as it arrives, the same discipline you'd want from any engineer moving fast.

Four habits separate a project an AI helped build well from one that collapses under its own code six weeks in.

1. Write the spec first, yourself

One page: what it does, the main entities, the endpoints, what "done" looks like for the first slice. An AI given a clear spec produces focused code; given "build me a task tracker" it guesses at every decision you didn't make.

2. Build one vertical slice before the next

One real feature, end to end — one API endpoint, wired to one UI screen, actually working — before starting the second. Not "all the backend, then all the frontend."

3. Give it the real context, not a blank page

The actual file it's editing, the actual API response shape, the project's existing conventions. A model guessing at a schema it was never shown produces plausible code against the wrong one.

4. Read every diff before it merges

Not skim — read. You are the one who has to debug it in production later, and "I don't know, the AI wrote it" is not a debugging strategy.

This note works through one real scenario end to end — QuickTasks, a small task tracker — applying exactly this discipline: a spec, then the backend slice, then the frontend slice, then wiring them together, then shipping it with the Docker/CI-CD/Kubernetes pipeline from the previous note.
Why does giving the model the existing file it's editing produce better code than describing the feature from scratch?Answer

Without it, the model has to guess at your naming conventions, your error-handling pattern, your validation style, and the exact shape of your schema — and a guess that's 90% right is often worse than one that's obviously wrong, because the mismatch is subtle and easy to merge without noticing. Given the real file, it matches what's already there instead of inventing a plausible-looking alternative.

The scenario: QuickTasks, a real task tracker

💡
In plain English
A small, genuinely buildable product: a team creates a board, adds tasks to it, assigns them to people, and marks them done. Small enough to build in an afternoon with help, real enough that every decision below — the schema, the API shape, the deploy pipeline — is one you would actually make on a real product.

The one-page spec, written before any code — this is the thing you hand the AI, not "build me a task tracker":

EntityFieldsRule
Userid, email, name, passwordHashSigns in with email + password, gets a JWT.
Boardid, name, ownerIdBelongs to one user; that user can invite others (out of scope for v1).
Taskid, boardId, title, done, assigneeIdBelongs to one board. done defaults to false.

The first vertical slice — the only thing v1 has to do: sign in, see your boards, open one, add a task, mark it done. Everything else is a later slice.

!
The spec is the boundary that keeps AI-assisted work honest. Without it, "add a task" can quietly grow subtasks, due dates and labels mid-conversation because they seemed reasonable to add. None of that is wrong to want eventually — it's wrong to accept unreviewed, three features deep into a session that started as one endpoint.
The spec above says nothing about subtasks, but partway through building, a generated Task model includes a parentTaskId field. What should you do?Answer

Remove it, or stop and consciously decide to expand the spec — but don't let it through unnoticed. Scope creeping in one field at a time is how a one-afternoon slice becomes a week, and how a schema ends up with columns nobody remembers the reason for. If subtasks turn out to matter, that's a deliberate v2 slice with its own review, not a rider on this one.

The backend and API, built with AI

💡
In plain English
The useful prompt is never "build the backend." It's "here is the schema, here is how the existing routes are written, add exactly this one endpoint." The model isn't inventing a design — it's extending one you already committed to, which is why the result matches the rest of the codebase instead of looking like it came from a different project.
prismaschema.prisma — given to the model as context, not guessed at
model User {
  id           String   @id @default(cuid())
  email        String   @unique
  name         String
  passwordHash String
  boards       Board[]
}

model Board {
  id      String @id @default(cuid())
  name    String
  ownerId String
  owner   User   @relation(fields: [ownerId], references: [id])
  tasks   Task[]
}

model Task {
  id         String   @id @default(cuid())
  boardId    String
  board      Board    @relation(fields: [boardId], references: [id])
  title      String
  done       Boolean  @default(false)
  assigneeId String?
  createdAt  DateTime @default(now())
}

The prompt for one slice: "Add POST /api/boards/:id/tasks. Validate title is a non-empty string. Confirm the board exists and belongs to the signed-in user before creating anything. Return 201 with the created row, matching the error-handling style in routes/boards.ts."

jsroutes/tasks.ts — the result, reviewed and run before it merged
router.post('/boards/:id/tasks', requireAuth, async (req, res, next) => {
  try {
    const { title } = req.body;
    if (typeof title !== 'string' || !title.trim()) {
      return res.status(400).json({ error: 'title is required' });
    }

    const board = await prisma.board.findUnique({ where: { id: req.params.id } });
    if (!board || board.ownerId !== req.user.id) {
      return res.status(404).json({ error: 'board not found' });   // 404, not 403 —
    }                                                                // don't reveal it exists

    const task = await prisma.task.create({
      data: { boardId: board.id, title: title.trim() },
    });
    res.status(201).json(task);
  } catch (err) {
    next(err);
  }
});
i
Notice the 404-not-403 detail — that came from the existing routes/boards.ts convention the model was shown, not from the prompt. That is exactly the payoff of feeding it real context: a security-relevant decision your team already made once gets applied again automatically, instead of needing to be re-explained and possibly forgotten.
Why does the route return 404 rather than 403 when a board exists but belongs to someone else?Answer

A 403 confirms the board exists — it just says "you can't see it," which tells an attacker that ID is real and worth probing further. A 404 gives the same answer whether the board doesn't exist at all or exists but isn't yours, so an attacker enumerating IDs learns nothing either way.

The frontend, wired to the actual API

💡
In plain English
The recurring failure when frontend and backend are built in separate AI sessions is drift: the frontend expects a field the API doesn't send, or the wrong casing, or a type that's a string on one side and a number on the other. Generating the frontend's types straight from the same Prisma schema removes an entire category of bug by construction rather than by discipline.
tsxTaskBoard.tsx — fetches real tasks, optimistic create
import { useState } from 'react';
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

type Task = { id: string; title: string; done: boolean };

export function TaskBoard({ boardId }: { boardId: string }) {
  const qc = useQueryClient();
  const { data: tasks } = useQuery({
    queryKey: ['tasks', boardId],
    queryFn: () => fetch(`/api/boards/${boardId}/tasks`).then(r => r.json()),
  });

  const [title, setTitle] = useState('');
  const addTask = useMutation({
    mutationFn: (title: string) =>
      fetch(`/api/boards/${boardId}/tasks`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ title }),
      }).then(r => r.json()),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['tasks', boardId] }),
  });

  return (
    <div>
      <ul>{tasks?.map(t => <li key={t.id}>{t.title}</li>)}</ul>
      <input value={title} onChange={e => setTitle(e.target.value)} />
      <button onClick={() => addTask.mutate(title)}>Add task</button>
    </div>
  );
}

The API renames done to completed. With a shared, generated types package, how does the frontend find out?Answer

The frontend's TypeScript build fails at compile time, on the exact line that referenced .done — in CI, before it ever merges. Without the shared types, the same rename ships silently: the field is just undefined in the browser, discovered only when a user notices tasks that all appear incomplete.

Wiring frontend, backend and database together locally

💡
In plain English
Three pieces built separately need one place where they actually run together — this is where a schema mismatch, a missing environment variable, or a CORS setting nobody configured finally shows up, before any of it reaches production.
yamldocker-compose.yml — the whole app, one command
services:
  db:
    image: postgres:16-alpine
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: quicktasks }

  api:
    build: ./api
    environment:
      DATABASE_URL: postgresql://postgres:dev@db:5432/quicktasks
      CORS_ORIGIN: http://localhost:3000
    ports: ["8080:8080"]
    depends_on: [db]

  web:
    build: ./web
    environment:
      NEXT_PUBLIC_API_URL: http://localhost:8080
    ports: ["3000:3000"]
    depends_on: [api]
jsapi/src/server.ts — the CORS line every scaffold forgets
import cors from 'cors';
// Without this, the browser blocks every request from the web
// container to the api container — even though curl works fine,
// because curl doesn't enforce CORS. Only browsers do.
app.use(cors({ origin: process.env.CORS_ORIGIN }));
Your frontend's fetch call to the API fails with a CORS error in the browser console, but running the exact same request with curl works perfectly. Why the difference?Answer

CORS is a browser-enforced rule, not a server-enforced one. The browser sends an Origin header and refuses to hand the response to your page's JavaScript unless the server explicitly allows that origin back — a protection against a malicious page silently calling APIs on your behalf using your logged-in session. curl has no such page context to protect, so it never triggers the check at all; the API responds identically either way.

Shipping it: containers, CI/CD and Kubernetes for this app

💡
In plain English
Everything from here is a direct application of the DevOps note, not new ideas — two Dockerfiles, one pipeline that builds and tests both, and two Kubernetes Deployments behind one Ingress. The scenario was never separate from that note; this is the point where they meet.
yaml.github/workflows/deploy.yml — both services, one pipeline
on: { push: { branches: [main] } }
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cd api && npm ci && npm test
      - run: cd web && npm ci && npm run build   # a type error here fails CI

  build-and-push:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - run: |
          docker build -t ghcr.io/acme/api:${{ github.sha }} ./api
          docker build -t ghcr.io/acme/web:${{ github.sha }} ./web
          docker push ghcr.io/acme/api:${{ github.sha }}
          docker push ghcr.io/acme/web:${{ github.sha }}

  migrate-and-deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - run: npx prisma migrate deploy          # BEFORE the new code goes live
      - run: |
          kubectl set image deployment/api api=ghcr.io/acme/api:${{ github.sha }}
          kubectl set image deployment/web web=ghcr.io/acme/web:${{ github.sha }}
          kubectl rollout status deployment/api
          kubectl rollout status deployment/web
yamlingress.yaml — one address, two services behind it
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: quicktasks
spec:
  rules:
    - host: quicktasks.app
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: { service: { name: api-service, port: { number: 80 } } }
          - path: /
            pathType: Prefix
            backend: { service: { name: web-service, port: { number: 80 } } }

One push to main now means: AI-assisted code change → reviewed and merged → tested in CI → two images built and tagged with that commit → migration applied → both Deployments updated → live, with the DevOps note's rollout and rollback discipline covering the last step.

✓ Worth remembering
  • Spec first, one vertical slice at a time — not the whole app in one prompt.
  • Give the model the real schema and the real existing file, not a description of them.
  • Share types between frontend and backend so a rename fails a build instead of shipping silently.
  • localhost inside one container never reaches another — use the Compose/Kubernetes service name.
  • CORS is enforced by the browser, not the server — that's why curl "works" when the browser doesn't.
  • The deploy pipeline for an AI-assisted project is identical to any other project's: tests gate it, migrations run before the new code, images are tagged by commit.
Why does prisma migrate deploy run before the images are rolled out, rather than after?Answer

The new code is written expecting the new schema to already exist — a column it reads or writes has to be there before that code receives any traffic. Running the migration first means by the time the new Pods start serving requests, the database already matches what they expect. It also has to stay backwards-compatible, because the old Pods are still running against the same database until the rollout finishes.
