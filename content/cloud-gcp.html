What a cloud actually rents you

Google Cloud has hundreds of products and the console is genuinely intimidating. It gets much smaller once you notice that a cloud rents you only four things.

1. Compute

Somewhere for your code to run. A whole machine, a container, or just a function. You are renting CPU and memory by the second.

2. Storage

Somewhere to keep bytes that survive the machine dying. Files, database rows, backups.

3. Networking

How traffic reaches your code and how your pieces reach each other. Addresses, load balancers, firewalls, DNS.

4. Identity

Who is allowed to do what. This is the one people skip and the one that ends up in the incident report.

💡
In plain English
Running a server yourself is owning a car: you buy it whether you drive or not, you fix it, and if you need a second one on Friday you cannot have it. A cloud is a taxi rank with an unlimited fleet, billed by the minute. The catch is the same as with taxis: it is cheaper right up until you leave one idling for a month.

The shape of a Google Cloud account

The project is the only level you need at first. It is the boundary for billing, for permissions, and for blast radius.

i
Use separate projects for dev, staging and production. Not separate folders in one project — separate projects. It is the cheapest safety measure available: a mistake in dev cannot touch production data, permissions do not leak across, and the bill tells you which environment is costing you money. Doing this on day one takes ten minutes; retrofitting it takes a week.

Where your code runs

💡
In plain English
Four ways to run code, differing in one thing: how much of the machine you are forced to think about. From a single function where you think about none of it, to a whole server where you think about all of it. The temptation is to pick the serious-sounding option and spend your first three months operating it instead of building the product.

GCP gives you four ways to run code. They differ in one dimension: how much of the machine you have to think about.

!
Use Cloud Run unless you have a specific reason not to. It takes any container, scales from zero to hundreds automatically, charges only while a request is being handled, and requires no cluster. Teams reach for Kubernetes because it sounds like the serious choice, then spend their first three months operating a cluster instead of building the product. Kubernetes is the right answer for a platform team running many services; it is an expensive hobby for one application.

The two questions that decide it

Deploying to Cloud Run, properly

💡
In plain English
The deal is simple: hand over a container that listens for web requests, and the platform runs as many copies as the traffic needs — down to none when nobody is asking. You never think about a machine. What you do have to think about are the three settings that decide whether this costs a few pounds a month or a few hundred.

Cloud Run takes a container that listens on the port given in $PORT and serves HTTP. That is the entire contract.

dockerfileDockerfile — a Node API, multi-stage so the image stays small
# Stage 1: install and build with the full toolchain.
FROM node:20-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: ship only what runs. Smaller image = faster cold start.
FROM node:20-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist

# Cloud Run TELLS you the port. Never hardcode 3000.
ENV PORT=8080
EXPOSE 8080
CMD ["node", "dist/server.js"]
jsThe one line in your server that matters
// Read the port Cloud Run gives you, and bind to 0.0.0.0 —
// binding to localhost means nothing outside the container can reach you,
// and the deploy fails with a health check timeout that explains nothing.
const port = process.env.PORT || 8080;
app.listen(port, '0.0.0.0', () => console.log(`listening on ${port}`));
bashBuild and deploy
# Build the image in the cloud and push it to Artifact Registry.
gcloud builds submit --tag \
  europe-west2-docker.pkg.dev/$PROJECT/app/api:$(git rev-parse --short HEAD)

# Deploy that exact image as a new revision.
gcloud run deploy api \
  --image europe-west2-docker.pkg.dev/$PROJECT/app/api:$(git rev-parse --short HEAD) \
  --region europe-west2 \
  --min-instances 0 \
  --max-instances 10 \
  --concurrency 80 \
  --cpu 1 --memory 512Mi \
  --no-allow-unauthenticated \
  --set-secrets "DATABASE_URL=db-url:latest,MODEL_KEY=model-key:latest"

The three settings that decide your bill

SettingWhat it doesGet it wrong and
--max-instancesThe ceiling on how many copies can run at onceLeaving it unbounded means a traffic spike — or a retry loop of your own making — scales into a five-figure bill. Always set this.
--concurrencyHow many requests one instance handles at the same timeSet to 1 and you pay for an instance per request. The default of 80 suits a Node app that is mostly waiting on I/O; lower it only if each request is CPU-heavy.
--min-instancesHow many stay warm0 is free when idle but the first request after a quiet spell waits for a cold start. Set 1 for a user-facing API where that first slow request matters.
i
Tag images with the git commit, never :latest. :latest means the thing running in production has no name you can trace, rolling back is guesswork, and two deploys can race. A commit SHA makes “what is running?” and “put yesterday's back” both one command.

Storing things

💡
In plain English
The instances running your code are temporary. They appear, handle some requests and vanish, and anything written to their local disk goes with them. So every fact that has to outlive a single request lives somewhere else deliberately — a bucket for files, a database for rows. This is the rule that catches people out first.

Cloud Run instances are ephemeral. They appear, serve requests, and vanish. Anything written to the local disk is gone, and any two requests may land on different instances. Every piece of state therefore has to live somewhere else.

What you haveWhere it goesNotes
Uploaded files, images, PDFs, exportsCloud Storage (a bucket)Cheap, effectively unlimited. Serve them with signed URLs rather than proxying bytes through your API.
Rows — users, orders, anything relationalCloud SQL for PostgreSQLManaged Postgres. See the PostgreSQL note for what to do with it.
Embeddings for RAGCloud SQL + pgvector, or a dedicated vector databaseStart with pgvector. One database to operate, one backup to test, and it is fast enough far longer than people expect.
Cache, sessions, rate-limit countersMemorystore (Redis)Or skip it: a rate limit in Postgres is fine until it is not.
Background jobsCloud Tasks or Pub/SubTasks for “do this one thing later”, Pub/Sub for “tell everyone who cares that this happened”.
!
Connection pools and scale-to-zero fight each other. Each Cloud Run instance opens its own pool, so ten instances with a pool of ten each is a hundred connections — and a small Cloud SQL instance allows around a hundred in total. Either set a small per-instance pool (connection_limit=5 in a Prisma URL) or put Cloud SQL Auth Proxy or PgBouncer in front. This is the most common production failure in this exact stack, and it appears only under load.
bashSigned URLs — let the browser talk to the bucket directly
# Your API never touches the file bytes. It issues a time-limited
# permission slip, and the browser uploads straight to the bucket.
#   - no request-size limits on your API
#   - no memory spike on a 200MB upload
#   - no bandwidth cost through your service
# Generated server-side, valid for minutes, scoped to ONE object key.
Your app writes an uploaded file to /tmp and a later request cannot find it. Why?Answer

The second request was served by a different instance, which has its own filesystem. Even on the same instance, the container can be replaced at any moment. On Cloud Run, /tmp is scratch space within a single request — useful for a temporary file you delete before responding, and useless for anything that must exist afterwards. It is also in-memory, so a large file there counts against your memory limit.

IAM, without despair

IAM answers “who can do what, to which thing”. It has a reputation for being impenetrable, which comes almost entirely from the vocabulary. The vocabulary is four words.

WordMeansExample
PrincipalWho is askingYou. Or a service account — an identity for code rather than a person.
RoleA named bundle of permissionsroles/storage.objectViewer — may read objects in buckets.
ResourceThe thing being acted onA bucket, a Cloud Run service, a whole project.
BindingGranting one role to one principal on one resource“This service account may read that bucket.”
💡
In plain English
A hotel. The principal is the guest, the resource is a room, and the role is what the key card opens. The default when you are in a hurry is to hand out the master key because it definitely works. IAM done properly is cutting a card that opens room 402 and the gym, and nothing else — so that a lost card is an inconvenience rather than a crisis.

The one rule

Give each service its own service account, with the smallest roles it needs. Not the default compute service account, which has Editor on the whole project. Not roles/owner because a deploy failed and that made it work.

Not this · the master key
gcloud projects add-iam-policy-binding $P \
  --member="serviceAccount:api@..." \
  --role="roles/editor"

# This service can now delete your
# database, read every secret, and
# spin up machines. To read one bucket.
Do this · one key, one door
gcloud storage buckets \
  add-iam-policy-binding gs://uploads \
  --member="serviceAccount:api@..." \
  --role="roles/storage.objectAdmin"

# Scoped to ONE bucket. A compromise
# of this service reaches that bucket
# and stops there.
!
Never download a service account key file. A JSON key is a permanent credential with no expiry that ends up in a repository, a Slack message or a laptop backup. Code running on GCP already has an identity attached — the client libraries find it automatically with no configuration. For CI running outside GCP, use Workload Identity Federation, which issues short-lived tokens instead. If you have ever emailed a key file to a colleague, rotate it today.
Why is a downloaded service-account key file worse than the identity already attached to your running code?Answer

Because it is a permanent credential in a file, and files travel — into a repository, a chat message, a laptop backup, an old container image. It does not expire, so a copy made two years ago still works today.

Code running on the platform already has an identity that the client libraries find automatically, with credentials that rotate on their own. The key file solves a problem you do not have and creates one you cannot easily undo.

Secrets and configuration

💡
In plain English
Two things get muddled here. Configuration differs between environments and is not sensitive — a log level, a region. Secrets are credentials. Configuration can sit in a file; secrets need somewhere they are versioned, access-controlled, audited and rotatable, and delivered to the process at the moment it starts.

Two different things get confused here. Configuration is a value that differs per environment and is not sensitive — a log level, a feature flag, a region. Secrets are credentials. They need different handling.

bashSecret Manager, end to end
# 1. Create the secret. The value never appears in your shell history
#    or in a file — it is piped in.
printf '%s' "$DB_PASSWORD" | gcloud secrets create db-url --data-file=-

# 2. Grant ONE service account permission to read ONE secret.
gcloud secrets add-iam-policy-binding db-url \
  --member="serviceAccount:api@$PROJECT.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"

# 3. Mount it. It arrives as an ordinary environment variable, so your
#    code needs no cloud-specific library and still runs on your laptop.
gcloud run deploy api --set-secrets "DATABASE_URL=db-url:latest"

# 4. Rotate: add a new version, redeploy. Old versions stay for rollback.
printf '%s' "$NEW_PASSWORD" | gcloud secrets versions add db-url --data-file=-
Where a secret ends upVerdict
Committed in .envIt is now in git history forever. Rotate it, then remove it.
Set by hand in the consoleWorks, but nobody knows where it came from, it is invisible to review, and it is lost when the service is recreated.
In your CI provider's secret storeFine for CI's own credentials. Not the place for runtime secrets.
Secret Manager, mounted at deployCorrect. Versioned, access-controlled, audit-logged, rotatable.
i
Validate configuration at startup, not at first use. A service that boots happily and fails an hour later on the first request that needs MODEL_KEY is much worse than one that refuses to start. Parse your whole environment into a typed object on line one and exit if anything is missing.

Vertex AI and the model layer

💡
In plain English
A large platform of which you will use a small corner. For building with models rather than training them, the relevant part is calling models through your cloud account instead of a separate API key — which mainly buys you one bill, one audit trail and no long-lived credential to look after.

Vertex AI is Google Cloud's umbrella for machine learning. For most people building an AI product, only a small part of it is relevant.

What you will actually use

The model API — calling Gemini, and in some regions third-party models, through GCP rather than direct. Plus Vector Search if you outgrow pgvector.

What you probably will not

Training pipelines, feature stores, AutoML, notebooks, model registries. These are for teams training their own models, which is a different job from building with them.

Vertex, or a direct API key?

Direct provider APIThrough Vertex AI
SetupAn API keyIAM, no key to manage
AuthenticationA secret you rotateThe service account already attached to your code
BillingA separate invoiceOn your GCP bill, with the same cost controls
Audit logsThe provider'sCloud Audit Logs, alongside everything else
Data residencyThe provider's regionsPinned to a GCP region you choose
Newest models firstUsually yesSometimes later
i
The deciding factor is rarely technical. If you already have a GCP compliance story — audit logs, data residency, one bill, no long-lived keys — going through Vertex means the model call inherits it instead of needing its own. If you do not, a direct API key is simpler and you lose nothing. Either way, put it behind the complete() wrapper from the Architecture note and the choice stays reversible.
!
Model availability is regional and it changes. A model available in us-central1 may not exist in europe-west2, and a data-residency requirement can therefore rule out a model entirely. Check this before you design around a specific one, not after. Check the current documentation rather than any note including this one — regional availability moves faster than anything written down.

Keeping the bill honest

💡
In plain English
A cloud bill goes wrong in exactly two ways: something scaled that you never bounded, or something has been quietly running for months that nobody uses. Both are prevented in an afternoon, and neither is preventable retrospectively — which is why the four things in this topic belong on day one.

Cloud bills go wrong in one of two ways: something scaled that you did not bound, or something has been running for months that nobody uses. Both are preventable in an afternoon.

1. A budget with alerts

Set one per project on the day you create it. Alerts at 50%, 90% and 100% of what you expect. It costs nothing and is the difference between noticing on the 3rd and noticing on the 30th.

2. Max instances on everything

Every Cloud Run service. An unbounded service under an accidental retry storm is the single most common way a bill goes from tens to thousands.

3. Labels on every resource

env=prod, team=web, service=api. Without them the bill is one number. With them you can answer “what does staging cost us?” in thirty seconds.

4. A monthly look at the top five lines

Not a full review — just the five biggest items and whether each still makes sense. The idle Kubernetes cluster from a spike three months ago is always found this way.

Getting it deployed automatically

💡
In plain English
Deploying from a laptop works right up until the day the wrong branch goes out, or the only person who knows the command is on holiday. A pipeline is that command written down, with gates in front of it — and for an AI system, one of those gates has to be a quality check, because every ordinary test can pass while the answers get worse.

Deploying by hand from a laptop works exactly until the day it does not: the wrong branch, an uncommitted change, or the only person who knows the command is away.

yamlThe pipeline, in the order the steps must happen
on: push to main
steps:
  1. install and typecheck
  2. run tests                      # gate: fails here, nothing deploys
  3. run the eval set               # gate: AI quality, see the Evals note
  4. build the container, tag it with the commit SHA
  5. push to Artifact Registry
  6. run database migrations        # BEFORE the new code, and additive only
  7. deploy the revision with NO traffic
  8. smoke-test the revision's own URL
  9. shift traffic: 10% -> wait -> 100%
 10. on error rate rising: shift back to the previous revision

The two gates

Step 3 is the one specific to AI systems. A prompt change that passes every unit test can still make answers worse, and nothing in a normal pipeline will notice. An eval set that runs on every push is what turns “it seems better” into a number.

Steps 7 to 10 are the ordinary discipline that most teams skip. Cloud Run keeps every revision and can split traffic between them, so a rollback is one command against a revision that is already there — not a rebuild under pressure.

!
Migrations must be backwards-compatible. During a gradual rollout, old code and new code are running at the same time against one database. A migration that drops a column the old revision still reads will break production for the users on the old revision. Add columns first, deploy code that writes both, then remove the old column in a later release. See the PostgreSQL note for the full pattern.
✓ Worth remembering
  • A cloud rents compute, storage, networking and identity. Everything else is a combination of the four.
  • Separate projects for dev, staging and production, from day one.
  • Cloud Run unless you have a specific reason. Always set max-instances.
  • Instances are ephemeral: nothing that must survive goes on local disk.
  • One service account per service, smallest roles, and never a downloaded key file.
  • Secrets in Secret Manager, mounted as environment variables at deploy.
  • Budget alerts and labels on day one; log tokens per feature from the first call.
Why must database migrations be backwards-compatible during a gradual rollout?Answer

Because for a while the old code and the new code are both running against the same database. A migration that drops a column the old version still reads breaks production for exactly the users still being served by it.

Add first, deploy code that handles both shapes, and only remove in a later release. It turns a risky moment into three unremarkable ones.
