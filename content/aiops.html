Why this is not normal ops

You already know how to run a service: watch the error rate, watch latency, page someone when a graph goes the wrong way. All of that still applies. The problem is that it is no longer sufficient, because an AI system has a failure mode ordinary software does not.

💡
In plain English
A broken tap either runs or it does not, and you can tell instantly. An AI system is a tap that always runs — but the water is sometimes slightly the wrong temperature, and nobody complains for three weeks. Every dial on your existing dashboard reads normal the entire time.
A normal serviceAn AI system
Failure looks likeA 500, a stack trace, a timeoutA 200 with a wrong answer
Same input, same output?YesNo — and that is not a bug
Degrades becauseYou changed the codeYou changed the prompt, or your data drifted, or the provider changed the model under you
Detected byMonitoringEvaluation, sampling, and user feedback
Cost per requestEffectively fixedVaries by a factor of fifty depending on input
“Works on my machine”Means the code is fineMeans nothing at all
!
The scariest row is the third one. Your system can get worse while nobody deploys anything — because the documents you retrieve went stale, because the kind of question users ask shifted, or because a provider updated a model behind the same name. If your only quality signal is “did anyone complain”, you will find out months late from a customer.

What to log on every call

💡
In plain English
This is the highest-value habit in the note, because it is the one thing you cannot add retrospectively. Every question you will later want to answer — why was this answer wrong, what does this feature cost, when did quality drop — is only answerable if the data was written down at the time.

This is the highest-value thing in the note. Everything downstream — debugging, cost analysis, evaluation, incident response — is possible only if the data was captured at the time. You cannot go back and add it.

tsOne structured line per model call
log.info('llm.call', {
  // Who and what — so you can group by anything later.
  trace_id:   'req_8f3a...',    // ties every step of ONE request together
  user_id:    hash(userId),     // hashed: enough to group, not to identify
  feature:    'support_reply',  // WHICH feature — the field people forget
  env:        'production',

  // The exact configuration. Without these, a regression is unattributable.
  model:      'claude-sonnet-5',
  prompt_ver: 'support_reply@v7',
  temperature: 0.2,

  // The numbers.
  tokens_in:  1840,
  tokens_out: 260,
  latency_ms: 2310,
  cached:     false,

  // The outcome.
  status:     'ok',             // ok | invalid_shape | refused | error | timeout
  finish:     'stop',           // stop | length | tool_use

  // For RAG: which passages were used. This is what separates a
  // retrieval failure from a generation failure, and it is the single
  // most useful field in the whole line.
  chunk_ids:  ['doc_41#p3', 'doc_88#p1'],

  // Tool calls, if any.
  tools:      [{ name: 'lookup_order', ms: 120, ok: true }],
});
i
prompt_ver and feature are the two fields teams add late and wish they had added first. Without feature, your token spend is one undifferentiated number. Without prompt_ver, you cannot say “quality dropped when we shipped v7” — you can only say it dropped.

What about the prompt and the answer themselves?

They are enormously useful for debugging and are also the most sensitive thing you handle. Decide deliberately rather than by default:

ApproachWhen it fits
Log both in fullInternal tools, no personal data, short retention. Easiest to debug.
Log a hash and the lengthYou can tell whether two calls were identical and spot truncation, without storing content.
Log a redacted versionRun PII detection first, replace what it finds. Costs latency; catches most but not all.
Sample — store 1% in fullThe pragmatic answer for most production systems: enough examples to debug, a fraction of the exposure.
!
Whatever you choose, write it in the privacy policy and set a retention period that something actually enforces. “We log prompts for debugging” with no expiry means you have an indefinite archive of whatever your users typed, which is a liability that grows on its own. See the Governance note.

Tracing a request through the whole chain

A single user question might embed a query, search a vector index, rerank, call a model, call two tools, and call the model again. When it takes eleven seconds, a log line per step in six different places will not tell you why.

💡
In plain English
A parcel tracking page. You do not want six separate emails from six depots — you want one page showing the whole journey, where it waited, and for how long. A trace is that page for one request, and each stop is a span.

Without the trace, the obvious move is to switch to a faster model — a change that would have saved perhaps a second and a half and cost you quality. With it, the answer is a reranker on a warm instance, or fewer candidates.

tsSpans, using OpenTelemetry conventions
// A trace id is created at the edge and passed down through everything.
// It is the join key for your entire system.
await tracer.startActiveSpan('rag.answer', async (span) => {
  span.setAttribute('feature', 'support_reply');

  const hits = await tracer.startActiveSpan('vector.search', async (s) => {
    const r = await index.search(vec, { k: 20, filter: { org: orgId } });
    s.setAttribute('result_count', r.length);
    return r;
  });

  const answer = await tracer.startActiveSpan('llm.call', async (s) => {
    const r = await complete({ prompt, context: hits });
    s.setAttribute('tokens_in', r.usage.in);
    s.setAttribute('tokens_out', r.usage.out);
    return r;
  });

  span.setAttribute('chunk_ids', hits.map((h) => h.id).join(','));
  return answer;
});
i
Use OpenTelemetry rather than a vendor's SDK directly. It is the open standard, every observability backend accepts it, and it means the tool you send traces to is a configuration change rather than a rewrite. The same reasoning as putting your model calls behind one wrapper.
Users report the assistant is slow, but your dashboard shows a p50 of 1.8s. What is the most likely explanation?Answer

You are looking at the median, and half your users are above it. In AI systems the tail is unusually long — a request that retrieves more, generates more, or takes an extra tool step can be five times the median. Look at p95 and p99. Also check whether “latency” means time-to-first-token or time-to-complete: with streaming those are very different numbers, and the one users feel is the first.

Prompts are code, so version them like code

💡
In plain English
A prompt decides what your system does, which makes editing one a behaviour change. It therefore needs what any behaviour change needs: a diff someone reviewed, a version number, a test that ran, and a way back. A prompt living as a string in the middle of a function has none of those.

A prompt determines what your system does. Changing one is a behaviour change. It therefore needs everything a behaviour change needs: a diff, a review, a version, a test, and a way back.

Not this · a string in the middle of a function
const res = await llm({

// Which version is in production?

Do this · a versioned, testable object
// prompts/support_reply.v7.ts

  id: 'support_reply',
  version: 7,
  model: 'claude-sonnet-5',
  temperature: 0.2,
  system: readFile('./support_reply.v7.md'),
  // The eval set that must pass before
  // this version may ship.
  evals: './support_reply.cases.jsonl',
};

The rules that make this work

In the repository, not a database

A prompt in a database can be changed without review, without a diff, and without a deploy — which sounds like agility and is actually an unreviewable production change. Keep them in git. If non-engineers must edit them, give them a pull request, not a text box wired to production.

The version is logged on every call

This is what makes a regression attributable. “Quality dropped on the 14th” plus “v7 shipped on the 14th” is an answer. Without the version it is a mystery.

The model id is pinned

Never point at a moving alias in production. Pin the specific dated version, upgrade deliberately, and run your evals against the new one before you switch. A model that changes under you is a change you did not make and cannot roll back.

Evals gate the merge

A prompt change with no eval run is a guess deployed to users. This is the AI equivalent of merging without running tests, and it should feel equally uncomfortable.

!
Watch for silent model changes. If you call gpt-4o or any other unpinned alias, the model behind that name changes over time. Your prompt was tuned against one set of behaviours and is now running against another. Pin the dated identifier, and treat upgrading it as a change that goes through the same gates as a prompt edit.
Why pin an exact dated model version rather than a friendly alias like the latest one?Answer

Because an alias moves. The model behind it is updated, your prompt was tuned against the old behaviour, and your system changes without anyone deploying anything — so there is no diff to look at and nothing to roll back to.

Pin the dated version and treat upgrading it as a change that goes through the same review and the same eval run as a prompt edit. It converts a silent change into a deliberate one.

Rolling out a change without holding your breath

💡
In plain English
You cannot fully test quality before shipping, so the way you ship has to absorb some of that risk. Run the new version alongside the old on real traffic without showing it to anyone; then to a small percentage; then widen. Each step buys evidence that no amount of testing beforehand could give you.

Because you cannot fully test quality in advance, the deployment mechanism has to carry some of the load.

TechniqueHow it worksCosts you
Shadow runRun the new version on real traffic in parallel. Log both, show the user the old one.Double the tokens. Zero risk. The best first step, and the most underused.
Canary1% of traffic on the new version. Watch the metrics. Widen if they hold.Nothing much. This should be the default for prompt changes.
A/B test50/50 split, measure a real outcome — resolution rate, thumbs up, escalations.Time. You need enough traffic for the result to mean anything.
Kill switchA flag that reverts to the previous version, or disables the feature entirely.One flag to maintain. Nobody has ever regretted having one.
i
Shadow running deserves more attention than it gets. It is the only technique here that gives you real-traffic evidence at zero user risk, and the questions real users ask are reliably stranger than the ones in your eval set. A day of shadow traffic regularly finds a failure mode that a hundred hand-written cases missed.

The dashboard, and the alerts

💡
In plain English
Four numbers tell you the system is running: volume, latency, failures and cost. None of them would move at all if every answer became subtly wrong tomorrow. That is why a fifth panel — some measure of whether the answers are any good — is the one that separates monitoring an AI system from monitoring a normal one.

Resist the instinct to graph everything. A dashboard with forty panels is a dashboard nobody reads.

1. Volume, by feature

Calls per minute, split by feature. Everything else is read relative to this line — cost is only alarming if volume did not explain it.

2. Latency, p50 and p95

Both, always. And for anything streamed, time-to-first-token separately from time-to-complete, because they diverge and users feel the first.

3. Failure rate, by kind

Not one number. Split: provider errors, timeouts, invalid output shape, refusals, guardrail blocks. Each has a completely different cause and fix.

4. Cost per request

Tokens in and out per call, multiplied out, split by feature. A rising line here with flat volume means your prompts or your context grew.

The fifth panel most dashboards do not have

A quality signal. The four above tell you the system is running. None of them would move at all if every answer became subtly wrong tomorrow. You need at least one of:

SignalHonestyEffort
Thumbs up / downLow volume, biased towards the angry — but the trend is realAn afternoon
Implicit signalsGood. Did they copy it, retry, rephrase, escalate to a human, abandon?A day, and worth it
A scheduled eval runBest. The same cases every hour against production, scored automaticallyYou have already built the eval set — just run it on a schedule
Sampled human reviewThe ground truth everything else is calibrated againstAn hour a week, and it is the hour that catches what nothing else does

Alert on cost. It is the one metric where a bug is silently expensive rather than visibly broken: a retry loop, an accidentally unbounded agent, or a prompt that started including a whole document. Everything else fails in a way somebody notices; this one just arrives as an invoice.

When it goes wrong at 3am

💡
In plain English
At 3am the instinct is to start rewriting the prompt, because that feels like the part you control. It is almost never the cause, it cannot be verified quickly, and a prompt changed under pressure with no eval run tends to become tomorrow’s incident. Work the list in order instead.

An AI incident is usually one of five things. Working through them in this order finds it quickly, because it goes from cheapest-to-check to hardest.

txtThe triage order
1. IS THE PROVIDER UP?
   Check their status page first, every time. Half of all AI
   incidents are somebody else's incident. Your fallback should
   already have engaged — check whether it did.

2. DID WE CHANGE SOMETHING?
   Deploys, prompt versions, model ids, feature flags, config,
   in the last 24 hours. Look at prompt_ver in the logs: if the
   error rate steps up exactly when a version changed, you are done.

3. DID THE INPUT CHANGE?
   A new customer with unusual documents. A marketing campaign
   bringing a different kind of question. An integration sending
   ten times the volume. Nothing broke — the load changed shape.

4. DID THE DATA CHANGE?
   For RAG: did an indexing job fail, half-complete, or index
   the wrong version of a document? Look at the chunk_ids on bad
   answers and read what those chunks actually say. This is where
   the "confidently wrong about the refund policy" bug lives.

5. IS IT THE MODEL?
   Last, not first. It is the hardest to verify and the least
   likely. Compare against a pinned known-good version on the
   same inputs before concluding anything.
i
The order is deliberate. The instinct at 3am is to start rewriting the prompt, because that is the part you feel you control. It is almost never the cause, it cannot be tested quickly, and a prompt change made under pressure with no eval run tends to become tomorrow's incident.

What to have ready before you need it

A kill switch per feature

Turns the AI path off and falls back to whatever the product did before it existed. Tested. Not tested on the night.

A one-command rollback

To a previous revision and a previous prompt version, independently. They break independently, so they must revert independently.

A saved query for bad answers

“Show me the last fifty calls for this feature with their chunk ids and outputs.” Writing that query while the incident is live wastes twenty minutes.

A written fallback decision

What the product does when the model is unavailable, agreed with someone outside engineering. Decided in a meeting, not by whoever is on call.

✎
Try this
Run the drill. Turn the kill switch on in staging and watch what the user actually sees. Then roll a prompt version back and time it. Both should take under a minute and neither should require reading documentation. If either surprises you, you have found the work that is worth doing this week rather than at 3am.
✓ Worth remembering
  • AI systems fail with a 200 OK. Your existing monitoring will not notice.
  • One structured log line per call, and feature, prompt_ver and chunk_ids are the three fields you will wish you had.
  • Trace the whole chain. The slow part is usually not the model.
  • Prompts are code: versioned, reviewed, pinned models, evals gating the merge.
  • Shadow, then canary, then widen. Keep a kill switch.
  • Four operational panels plus one quality signal, and alert on cost.
  • Triage in order: provider, our change, input, data, model. The model is last.
The assistant started giving wrong answers this morning. Nobody deployed anything. Where do you look?Answer

At the data and at the inputs, not at the model. For a retrieval system: did an indexing job fail or half-complete, and are the passages being retrieved actually the current ones? Read what those chunks say — it is very often a superseded document that never got removed.

The other common answer is that the traffic changed shape rather than the system: a new customer, a campaign, an integration sending a kind of question you never had before. Nothing broke; the load is different.
