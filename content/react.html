What React is

React is a library for building what a person sees in a browser. Its one big idea is worth more than every feature it has: you never describe how to change the screen, you describe what the screen should look like for some data. React works out the changes.

💡
In plain English
Old way: “find the price label, erase it, write 40 in it, then find the total, erase that too…” React way: “the cart has these items; here is what a cart with these items looks like.” When an item is added you hand React the new list and it works out which words on the screen actually changed.

That is the whole trade. You give up direct control of the page, and you get back the thing that makes large screens survivable: the screen can never disagree with the data, because it is drawn from it every time.

tsxThe shape of every React program
data  ->  your component  ->  what the screen should be

change the data  ->  React runs your component again
                  ->  compares old and new
                  ->  touches only the bits that differ

Steps three to five are React’s job and are the reason it exists. You only ever write steps one and two.

i
React draws the screen. It does not fetch data, route between pages, or talk to a database. Those come from things around it — in this product, Next.js (routing and rendering) and a plain fetch to the Express API. Confusion about “what React does” is nearly always this line being blurry.

Components & JSX

A component is a function that returns a description of some screen. That is genuinely all it is: a function whose name starts with a capital letter and which returns markup.

jsA component
function SaveButton() {
  return <button className="s-btn">Save</button>;
}

// Used like an HTML tag of your own:
<SaveButton />

The markup inside the function is JSX. It looks like HTML and is not: it is JavaScript that a build step turns into function calls. The differences that bite:

HTMLJSXWhy
class="box"className="box"class is a reserved word in JavaScript.
onclick="save()"onClick={save}Events are camelCase, and you pass the function itself — no quotes, no parentheses.
<br><br />Every tag must close. JSX is parsed strictly.
Text is text{name}Curly braces drop out of markup and back into JavaScript. Any expression is allowed inside.

A component returns one element. When you need several side by side, wrap them in a fragment — <>...</> — which groups without adding a tag to the page.

jsBraces, conditions and fragments
function Greeting({ name, unread }) {
  return (
    <>
      <h1>Hello {name}</h1>

      {/* A condition: && renders the right side only if the left is true */}
      {unread > 0 && <p>You have {unread} unread messages</p>}

      {/* Either/or: the ternary, because if-statements are not expressions */}
      {unread > 0 ? <button>Read them</button> : <p>All caught up</p>}
    </>
  );
}
!
Zero is not nothing. {count && <Badge />} renders a literal 0 on the screen when count is 0, because 0 is falsy but still a valid thing to render. Write {count > 0 && ...} and the problem disappears.

Props: data passed in

A component takes arguments, called props. They arrive as one object, and are almost always destructured in the parameter list so the names are visible at the top of the function.

jsProps in, markup out
function SaveButton({ label, disabled, onSave }) {
  return (
    <button className="s-btn" disabled={disabled} onClick={onSave}>
      {label}
    </button>
  );
}

<SaveButton label="Save draft" disabled={false} onSave={handleSave} />

Two rules make props predictable, and both are non-negotiable:

  • Props are read-only. A component never writes to its own props. If a value needs to change, it belongs to whoever passed it — which is why buttons receive an onSave function instead of changing anything themselves.
  • Data flows down. Parent to child, one direction. A child talks back by calling a function its parent gave it. This is the whole reason a React screen is traceable: when a value is wrong, there is exactly one place it can have come from.
Props

Given by the parent. Read-only. Change them and React cannot know who is responsible for the value.

State

Owned by this component. Changing it is what causes a redraw.

Handler prop

A function passed down so a child can ask the parent to change something.

Children

Whatever was written between the tags. How wrappers stay ignorant of what they wrap.

children is the one prop with special syntax: whatever you put between the opening and closing tags arrives as props.children. It is how wrappers — cards, dialogs, layouts — are written.

jschildren: a wrapper that does not care what it wraps
function Card({ title, children }) {
  return (
    <div className="s-card p-4">
      <h3>{title}</h3>
      {children}
    </div>
  );
}

<Card title="Billing">
  <p>Anything at all goes here.</p>
</Card>

State: data that changes

Props come from outside. State is a value a component owns and can change — and changing it is what makes React redraw. useState gives you a value and a function to replace it.

tsxuseState
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  //     ^ current value    ^ how to change it   ^ starting value

  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
💡
In plain English
useState hands you a value and a pen. Writing with the pen does not edit the screen directly; it tells React “this is different now”, React runs your function again with the new value, and the new screen falls out of that.

Two things about setting state surprise everybody once:

  1. It is not immediate. Reading count on the line after setCount gives you the old value. The variable belongs to this run of the function; the new value shows up in the next one.
  2. It replaces, it does not merge. Setting an object throws the old object away, so spread what you want to keep: setUser({...user, name}).

When the new value is computed from the old one — and especially when several updates can happen in the same tick — pass a function instead of a value. React hands it the latest state, so nothing is lost.

Not this · stale value
// Both reads see the same old count.
// This adds 1, not 2.
setCount(count + 1);
setCount(count + 1);
Do this · updater function
// Each call receives the freshest value.
// This adds 2.
setCount((c) => c + 1);
setCount((c) => c + 1);

Never edit state in place. React decides whether to redraw by asking “is this a different object than before?” — pushing into the same array leaves it the same object, so nothing happens and the screen silently goes stale.

Not this · mutating
items.push(newItem);
setItems(items);       // same array — no redraw

user.name = 'Ada';
setUser(user);         // same object — no redraw
Do this · replacing
setItems([...items, newItem]);

setUser({ ...user, name: 'Ada' });

setItems(items.filter((i) => i.id !== id));
A list on screen never updates, though a new item was definitely added. What is the first thing to look at?Answer

Whether the array was mutated. items.push(x) followed by setItems(items) hands React the same array it already had, so it concludes nothing changed and does not redraw. The fix is setItems([...items, x]) — a new array, which is a different object.

The second thing to look at is whether the update happened at all: a forgotten await on the save can leave the state correct and the server unaware, or the other way round.

Real worldThe save button, with real states

A button that saves has four possible looks, and all four come out of two pieces of state. No if anywhere touches the DOM; the markup simply says what each combination looks like. 

function SaveButton({ draft }) {
  const [saving, setSaving] = useState(false);
  const [error, setError] = useState(null);

  async function handleSave() {
    setSaving(true);
    setError(null);
    try {
      await saveDraft(draft);
    } catch (err) {
      setError('Could not save. Check your connection.');
    } finally {
      // finally, so the button never gets stuck spinning after a failure.
      setSaving(false);
    }
  }

  return (
    <div>
      <button className="s-btn" onClick={handleSave} disabled={saving}>
        {saving ? 'Saving…' : 'Save'}
      </button>
      {error && <p role="alert">{error}</p>}
    </div>
  );
}

Lists & keys

A list of data becomes a list of elements with map — the array method that turns each item into something else. Ninety per cent of React screens are this.

jsRendering a list
function UserList({ users }) {
  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.email}</li>
      ))}
    </ul>
  );
}

The key is not decoration. It is how React tells one row from another between redraws, so it can move a row rather than rebuild it. Get it wrong and the symptoms are bizarre rather than obvious: text typed into one row appearing in another after a sort, checkboxes staying ticked on the wrong item, animations firing on rows that did not change.

!
Do not use the array index as a key in any list that can be reordered, filtered or added to at the front. Index 0 means “whatever is first now”, so React concludes the first row simply changed its contents and keeps the state that belonged to the old one. Use a genuine id from the data.

Events & forms

An event handler is a function passed to a prop like onClick or onChange. Pass the function, do not call it: onClick={save} runs it when clicked, onClick={save()} runs it immediately during rendering, which is a classic and confusing bug.

Inputs are usually controlled: state holds the value, the input displays it, and typing updates the state. The state is the single truth, so validation, resetting and pre-filling are all just state changes.

tsxA controlled form
function ContactForm({ onSubmit }) {
  const [form, setForm] = useState({ email: '', message: '' });
  const [sending, setSending] = useState(false);

  function update(field, value) {
    setForm((current) => ({ ...current, [field]: value }));
    //                                  ^ computed key: updates one field, keeps the rest
  }

  async function handleSubmit(event) {
    event.preventDefault();  // stop the browser reloading the page
    setSending(true);
    await onSubmit(form);
    setSending(false);
    setForm({ email: '', message: '' });
  }

  const valid = form.email.includes('@') && form.message.trim().length > 0;

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={form.email}
        onChange={(e) => update('email', e.target.value)}
      />
      <textarea
        value={form.message}
        onChange={(e) => update('message', e.target.value)}
      />
      <button type="submit" disabled={!valid || sending}>
        {sending ? 'Sending…' : 'Send'}
      </button>
    </form>
  );
}
i
Validation on the screen is a courtesy, never a control. Anybody can send a request without ever loading your form. The server has to check the same things again — which is why this product validates in the browser and in the API, and why the API is the one that decides.

Effects: talking to the outside world

Rendering must be pure: given the same props and state, a component returns the same markup and touches nothing else. Everything that breaks that rule — fetching, timers, subscriptions, listening to the browser — is a side effect, and goes in useEffect.

tsxFetching when the screen appears
import { useEffect, useState } from 'react';

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    let cancelled = false;                       // guard: see below
    setLoading(true);

    fetch('/api/v1/users/' + userId)
      .then((response) => response.json())
      .then((data) => {
        if (!cancelled) setUser(data);
      })
      .finally(() => {
        if (!cancelled) setLoading(false);
      });

    return () => { cancelled = true; };          // cleanup, run before the next effect
  }, [userId]);                                  // dependencies: re-run when userId changes

  if (loading) return <p>Loading…</p>;
  return <h1>{user.email}</h1>;
}

The three parts, and what each one is for:

PartMeans
The function bodyWhat to do after React has updated the screen.
The dependency array [userId]Re-run whenever one of these values differs from last time. An empty array means "once, when this component first appears".
The returned functionCleanup. React runs it before the next run and when the component disappears — unsubscribe, clear the timer, ignore the reply.

The cancelled flag above is not ceremony. Change the user twice quickly and two requests are in flight; if the first reply arrives last, it overwrites the screen with the wrong person’s data. The cleanup makes the stale reply harmless.

Real worldAutosave in the Studio, and the two bugs it would have without cleanup

The editor saves a draft a moment after you stop typing. That is a timer started in an effect: every keystroke changes the draft, the effect re-runs, and the cleanup cancels the previous timer — so a hundred keystrokes cause one save rather than a hundred.

Remove the cleanup and both failures arrive together. Every keystroke schedules its own save, so the server is hammered; and because the requests finish out of order, an early draft can land after a later one and silently undo the last thing you typed. The cleanup line is what makes the feature correct, not merely efficient.

!
Most effects should not exist. If you can compute a value from props and state during rendering, compute it — do not store it in state and sync it with an effect. An effect that sets state that another effect reads is the standard way a screen starts flickering and looping. Effects are for reaching outside React, not for moving data around inside it.

The other hooks worth knowing

A hook is a function starting with use that lets a component remember something between renders. Two rules apply to every one of them, and breaking either produces baffling bugs rather than errors:

  1. Only at the top level. Never inside an if, a loop or a nested function. React matches hooks to their stored values by call order, so a hook that sometimes runs shifts every hook after it onto the wrong value.
  2. Only in components or other hooks. Not in plain functions, not in event handlers.
HookUse it forExample
useStateA value that changes and should redraw the screen.const [open, setOpen] = useState(false)
useEffectReaching outside React: fetching, timers, listeners.useEffect(load, [id])
useRefA value that survives redraws but must not cause one — a DOM node, a timer id, "did I already do this".const input = useRef(null)
useMemoSkipping an expensive calculation when its inputs have not changed.useMemo(() => sort(rows), [rows])
useCallbackKeeping a function identity stable, so a memoised child does not redraw for nothing.useCallback(save, [draft])
useContextReading shared data without passing it through every level.const { user } = useContext(AuthContext)
i
Reach for useMemo and useCallback last, not first. They have a cost of their own and they make code harder to read. Add them when something is measurably slow — a big sorted table, a chart — not as a habit.
Why can a hook not be called inside an if-statement?Answer

React does not know your hooks by name — it matches them to their stored values by the order they are called in. A hook that runs on some renders and not others shifts every hook after it by one position, so your state ends up in another hook’s slot. The symptom is a value that belongs to something else entirely, which is far harder to diagnose than an error would be.

A custom hook is just a function that calls other hooks, and it is how logic gets shared between components. Nothing special happens: the name beginning with use is what tells the tooling to apply the rules above.

tsxA custom hook — the logic, without the markup
function useDebounced(value, delay = 300) {
  const [settled, setSettled] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setSettled(value), delay);
    return () => clearTimeout(timer);   // typing again cancels the pending update
  }, [value, delay]);

  return settled;
}

// In a component: search only after the typing stops.
const [query, setQuery] = useState('');
const debouncedQuery = useDebounced(query);
useEffect(() => { search(debouncedQuery); }, [debouncedQuery]);

Sharing state between components

When two components need the same value, the value moves up to their closest common parent, which passes it down to both. This is called lifting state up, and it is the default answer.

tsxLifting state up
function Filters() {
  // The search box types into it; the table reads it. So it lives here,
  // above both, and neither child owns it.
  const [query, setQuery] = useState('');

  return (
    <>
      <SearchBox value={query} onChange={setQuery} />
      <ResultsTable query={query} />
    </>
  );
}

It stops being the answer when the value is needed by something eight levels down and every level in between is only passing it along. That is context: a value published at the top of a subtree and read anywhere inside it.

tsxContext — for genuinely global things
const AuthContext = createContext(null);

function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  return (
    <AuthContext.Provider value={{ user, setUser }}>
      {children}
    </AuthContext.Provider>
  );
}

// Anywhere below, at any depth:
function Header() {
  const { user } = useContext(AuthContext);
  return <span>{user?.email}</span>;
}
i
Context is for things almost everything needs — who is signed in, the theme, the language. It is not a general store: every component reading a context redraws when any part of that value changes, so a large, frequently-changing context is a performance problem waiting to happen. Split it, or keep the busy state local.

The mistakes everybody makes

SymptomCauseFix
The screen does not update, though the data changed.State was edited in place, so it is still the same object.Replace it: setItems([...items, x]).
"Too many re-renders" and the tab freezes.A handler was called instead of passed — onClick={save()} — or an effect sets state it also depends on.Pass the function: onClick={save}. Fix the effect’s dependencies.
A value is one step behind.State was read straight after setting it.Use the updater form: setX((current) => ...).
Rows behave oddly after sorting or filtering.The array index was used as the key.Key by a stable id from the data.
An old reply overwrites a newer one.A fetch in an effect had no cleanup.Return a cleanup that sets a cancelled flag, or use AbortController.
A literal 0 appears on the screen.{count && ...} with a numeric count.Compare explicitly: {count > 0 && ...}.
Everything re-renders on every keystroke.Busy state lives too high up, or in a context.Move the state down to the component that actually uses it.

Practice

Build a to-do list in a single component, and do not look anything up until you are stuck. It needs: state for the items, state for the input, adding on submit, removing by id, a key on each row, and a count of what is left. It is about forty lines, and it uses every idea in this note except context.

Then break it deliberately: use the array index as the key, add a row at the top and watch the wrong item get ticked. That is the bug you will otherwise spend an afternoon on later.

✓ Worth remembering
  • A component is a function that turns data into a description of the screen.
  • Props come in from the parent and are read-only; state is owned and changeable.
  • Setting state replaces rather than edits, and takes effect on the next render.
  • Keys must be stable ids, never array indexes.
  • Effects are for reaching outside React, and most of them should not exist.
