Why you cannot ship without this

Ordinary code is predictable: the same input gives the same output, so a test that passed yesterday still means something today. A model gives you a range of possible outputs, and that range shifts when you change the prompt, the model version, the retrieval — or when you change nothing at all.

💡
In plain English

Testing normal code is like checking a calculator: 2 + 2 must give 4 every single time. Testing a model is much more like correcting exam papers — you cannot look for one exact sentence, you have to judge whether an answer is good, and you need enough papers that one lucky guess does not fool you.

An eval is that marking scheme, done automatically: a set of real inputs, a clear description of what a good answer looks like, and a score you can watch over time.

!

Without a test set you are not doing engineering, you are gambling. Every prompt change turns into a quick eyeball check on three examples somebody happens to remember. Whatever you broke on the fourth case goes live, and you hear about it from a customer six weeks later — if you hear about it at all.

What evals actually catch

ChangeWhat goes wrong without an eval set
You improve the prompt.It gets better on the case you were looking at, and worse on two you were not looking at. Nobody notices.
The model version updates.Something your prompt was quietly relying on changes. A newer model is better on average but it is not the same.
You switch to a cheaper model.You have no way to know whether the money you saved cost you any quality, so you either never try it or try it blindfolded.
You change chunking or retrieval.The answers slowly become less tied to the sources. Nothing throws an error. Quality slides downwards for a month.
Someone edits a tool description.The agent starts picking the wrong tool for a whole group of cases that nobody checks by hand.

Building the set — the part that matters

💡
In plain English
A test set is a collection of real cases with an agreed answer for each one. This is the part people skip because it is boring, and it is the part that decides whether any of the rest works. Twenty cases taken from things users actually asked are worth more than five hundred you made up yourself, because made-up cases only cover what you had already thought of.

Almost all the value sits here, and almost all the effort goes somewhere else: people build fancy scoring machinery on top of twelve examples they made up at their desk.

i

Your test set is a genuine asset. Prompts get rewritten, models get replaced, frameworks come and go. The set of real cases with agreed-correct answers is the one thing that stays valuable, and gets more valuable every month. Keep it in the repository, right next to the code it tests.

Where should the cases in an eval set come from?Answer

Real usage — the logs, the support tickets, the complaints. Especially the failures, because a set made only of cases you already handle well cannot tell you when things have got worse.

Deliberately put in the awkward ones: unclear questions, questions with no good answer, and questions the system should refuse. A set of easy cases scores high and measures nothing.

How to score an answer

💡
In plain English
There are four ways to score an answer, from cheap and strict to expensive and flexible. An exact match, when there is only one right answer. A rule or a pattern, when you can describe what correct looks like. A human, who is the real truth but cannot do thousands. Or another model as the examiner — which works, as long as you have first checked that the examiner agrees with the humans.

Four kinds of marker, cheapest and most reliable first. Use the simplest one that can actually judge your task — and use several together, because most tasks have one part you can check exactly and one part that needs judgement.

GraderHow it worksGood forWatch out
Exact / structuralA text match, a JSON schema check, a pattern.Sorting, pulling out fields, routing, anything with one correct answer.Nothing — use it wherever you can. It costs nothing and it never lies.
ProgrammaticCode that checks qualities: does it parse, does it cite sources, is every cited id a real one, is it within the length limit.Whether it stuck to the sources, whether it followed the format, safety rules, and anything you can write as a simple check.It only checks the things you remembered to check.
LLM-as-judgeA model marks the answer against a written marking scheme.Tone, helpfulness, quality of the reasoning — the parts that really are a matter of judgement.It has its own biases, and it varies more than people expect. See below.
HumanA person reads it and gives it a mark.Checking that the other three are right. This is the real truth that all the others are trying to copy.Slow and expensive — so spend it on checking the other markers, not on doing thousands of cases.
!

Reach for the model examiner last, not first. “Just get a model to mark it” feels like the answer to everything, so it ends up being used for things a three-line check would settle exactly. If the requirement is “returns valid JSON with these five fields”, that is JSON.parse and a schema, not a matter of opinion.

Making an LLM judge trustworthy

Write a real rubric

“Rate helpfulness out of 10” just gives you noise. Write down what each score means, in full sentences, with an example showing the line between one score and the next.

Prefer binary questions

“Is every fact in this answer supported by the given text? Yes or no.” is far steadier than any out-of-10 scale, and far easier to act on.

Show the criteria, not the answer key

If you show it the model answer, the examiner starts rewarding answers that look similar to it rather than answers that are correct. Different wording is not a mistake.

Calibrate against humans

Mark fifty cases by hand and check whether the examiner agrees with you. If it does not, fix the marking scheme before you trust a single score it gives.

i

Model examiners have known biases, and all of them can be measured: they prefer longer answers, they prefer answers written in their own style, and when comparing two options the order you show them in changes which one wins. Shuffle the order and check whether the result still holds.

Evaluating RAG and agents specifically

RAG: score retrieval and generation separately

This is the single most useful idea in this note. Almost every disappointing RAG system fails at the search step and gets the blame put on the model — and one combined score cannot tell you which half is broken.

StageQuestionHow to score it
RetrievalDid the chunk containing the answer come back at all?Write down the correct chunk id for each case, then check whether it turns up in the top k. Done by code, exact, no judgement needed.
GroundingIs every claim in the answer supported by what was retrieved?A model examiner, with the fetched text in front of it. A yes-or-no answer for each claim.
RefusalWhen the answer genuinely is not in the corpus, does it say so?Cases with no answer at all, and an exact refusal sentence you expect back. This one catches the failure that damages trust the most.
Answer qualityIs it actually useful to a person?A model examiner with a marking scheme — and it only means anything once the three above are passing.
💡
In plain English

If the search scores 60%, no amount of prompt writing will save you — the answer was never in the room. Fix the search before you touch a single word of the prompt. Teams routinely spend weeks rewriting a prompt to fix what is actually a search bug.

Agents: score the trajectory, not just the ending

An agent can arrive at the right answer after twelve wasteful steps, or arrive at the wrong one having done everything sensibly. Scoring only the final answer hides both of those.

What to measureWhy it matters
Task success — did it achieve the goal?The number everybody quotes, but on its own it does not tell you what went wrong.
Steps takenA step count that keeps rising is the earliest sign that something about your tools has become confusing.
Tool choice accuracyDid it pick the right tool at each decision point? This narrows the problem down to one description you can go and rewrite.
Tokens and cost per runThe thing that quietly destroys the economics. Measure it per run, not per request.
Gate hitsHow often it tried to do something that needed approval. A sudden jump is worth looking into straight away.

Running them, and running them automatically

💡
In plain English
A test set nobody runs is just a document. The value only appears when it runs automatically — on every change to a prompt, and on a schedule against the live system — so that a break is caught by your pipeline instead of by a customer.
tsevals/run.ts — small enough that it actually gets used
import cases from './cases/support-qa.json';
import { answer } from '../src/answer.js';
import { judgeGrounded } from './graders.js';

type Case = {
  id: string;
  question: string;
  expectedChunkId: string | null;   // null = not answerable from the corpus
  mustRefuse?: boolean;
};

const results = [];

for (const c of (cases as Case[])) {
  const out = await answer(c.question);

  // 1. Retrieval — exact, cheap, and the first thing to look at when a score drops.
  const retrieved = c.expectedChunkId === null
    ? true
    : out.chunkIds.includes(c.expectedChunkId);

  // 2. Refusal — does it decline when there is genuinely nothing to say?
  const refusedCorrectly = c.mustRefuse
    ? out.text.includes('I do not have that information')
    : true;

  // 3. Grounding — the only part that needs a model, and only if the rest passed.
  const grounded = retrieved && !c.mustRefuse
    ? await judgeGrounded(out.text, out.context)
    : true;

  results.push({ id: c.id, retrieved, refusedCorrectly, grounded });
}

const rate = (k: keyof (typeof results)[0]) =>
  (results.filter((r) => r[k]).length / results.length * 100).toFixed(0) + '%';

console.log(`retrieval  ${rate('retrieved')}`);
console.log(`refusal    ${rate('refusedCorrectly')}`);
console.log(`grounding  ${rate('grounded')}`);

// Fail the build on a regression. Thresholds are a ratchet: raise them as the
// system improves, never lower them to make a red build go green.
const failed = results.filter((r) => !r.retrieved || !r.grounded || !r.refusedCorrectly);
if (failed.length > 3) {
  console.error(`${failed.length} failures:`, failed.map((f) => f.id).join(', '));
  process.exit(1);
}
i

Run it on every change to a prompt, a model id, or the retrieval pipeline. Those three files are every bit as dangerous as a database migration, and they get a fraction of the attention. Wiring the test set into CI is what turns “we really should test this” into something that actually happens.

!

Running these tests costs real money, because they make real API calls. Keep the CI set small and quick — thirty to fifty cases — and run the big set overnight. A test suite that is too expensive to run is a test suite nobody runs.

Your grounding score is 95% and users still complain the answers are wrong. What is the eval missing?Answer

Most likely the search step, measured on its own. Grounding only asks “is this answer supported by the text we fetched?” — and an answer can be perfectly supported by the wrong chunk, scoring 95% while being useless. A high grounding score together with unhappy users is the classic sign of a search problem hiding behind a writing score.

The second suspect is having no refusal cases. If your set only has questions that can be answered, you have never measured what happens when your documents contain nothing — and confidently inventing an answer in that situation is what destroys trust fastest.

▶
Practice

Take any AI feature you already have. Open the logs, pull out thirty real inputs, and write down for each one what a good answer would look like. That is one afternoon of work, and it is the whole job.

Now run your current system against all thirty and count the results. Whatever number comes out is your real starting point — almost certainly lower than you expected — and from now on you can improve it on purpose instead of guessing.

✓ Worth remembering
  • Without a test set, every prompt change is a gamble and everything you break goes live quietly.
  • Thirty real cases beat three hundred made-up ones. Include the unclear, the hostile and the unanswerable.
  • Turn every reported bug into a case. That one habit builds up into your most valuable asset.
  • Use the simplest marker that works. Reach for a model examiner last, and check it against human marks first.
  • For RAG, score the search and the writing separately — one number cannot tell you which half is broken.
  • For agents, score the whole path: steps taken, tools chosen, cost, gates hit — not only the final answer.
  • Wire it into CI. Prompts and model ids are as dangerous as database migrations and get a fraction of the review.
