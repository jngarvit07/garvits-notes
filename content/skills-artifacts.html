Four ways to extend a model, and how they differ

By this point in the notes you have met several things that all sound like “giving the model more abilities”. They are genuinely different mechanisms, and choosing wrongly is the most common architectural mistake in applied AI.

MechanismWhat it addsWho invokes itLives where
ToolsThe ability to do something — read a row, send an email, run a query.The model, mid-conversation.Your code, or an MCP server.
RAGKnowledge the model was never trained on, retrieved per question.Your code, before the call.A vector store you own.
SkillsKnow-how — procedures, conventions, and files for doing a task properly.The model, when the task calls for it.A folder with a SKILL.md.
ArtifactsA place to put substantial output, so it is a document rather than a wall of chat.The model, when output warrants it.The host application.
💡
In plain English

Think of hiring someone. Tools are the keys and logins you give them. RAG is the filing cabinet they can look things up in. Skills are the “how we do things here” handbook they read when a relevant job comes up. Artifacts are the difference between telling you the answer across a noisy desk and handing you a written report.

!

The frequent error is reaching for RAG when the problem is know-how. If the model gets facts right but does the procedure wrong — wrong format, wrong sequence, missing the step your team always does — retrieval will not fix it. That is a skill.

Skills: instructions that load themselves

A skill is a folder. At its root is a SKILL.md whose front matter carries a name and a one-line description; below that is whatever the task needs — longer instructions, reference documents, scripts, templates.

The mechanism that makes it useful is progressive disclosure. Only the description sits in context all the time. The model reads the full file — and any files it points to — only when a task actually calls for it.

mdskills/invoice-review/SKILL.md
---
name: invoice-review
description: >
  Review a supplier invoice against our purchase-order rules before it is
  approved for payment. Use whenever someone asks to check, review, or approve
  an invoice, or asks whether an invoice looks right.
---

# Reviewing a supplier invoice

Work through these in order. Stop at the first hard failure and say which.

1. **Match the PO.** Every line must map to a line on the referenced purchase
   order. A line with no PO line is a hard failure — never "probably fine".
2. **Check the totals.** Recompute from the line items. Do not trust the stated
   total; the whole point of this check is that it is sometimes wrong.
3. **Check the tax treatment** against `reference/tax-rules.md`. Read that file
   only when the supplier is outside the UK — domestic invoices never need it.
4. **Flag anything over £10,000** for a second human approver, regardless of
   whether it passes everything else.

## Output

A short verdict — `approve`, `query`, or `reject` — then the reasons as bullets.
Quote the invoice line number for every problem. Never approve with unresolved
queries; "approve with caveats" is not one of the three options.

## What not to do

- Do not contact the supplier. That is a person's decision, not this task's.
- Do not adjust figures to make them match. Report the mismatch.

What makes a skill good

RuleWhy
The description is a trigger, not a summary. Say when to use it, in the words someone would actually use.It is the only part always in context. If it does not match how people phrase the request, the skill never loads and everything below it is wasted.
Write procedure, not background. Steps, order, decision points.The model already knows what an invoice is. It does not know that you always recompute the total.
Say what not to do.Negative instructions prevent the confident, plausible, wrong action — which is the failure mode that costs you.
Push detail into referenced files.Keeps the always-read body short, and the rarely-needed reference out of context until the day it matters.
One skill, one job.A skill covering “finance tasks” matches everything and helps with nothing.

Using skills from the API

On the Messages API, skills run inside the code-execution container, so they are enabled through container alongside the code-execution tool. This is the path that produces real .pptx, .xlsx or .docx files.

tsa skill that produces a real file
const response = await client.beta.messages.create({
  model: 'claude-opus-5',
  max_tokens: 16000,
  betas: ['code-execution-2025-08-25'],

  // Which skills are available inside the container for this request.
  container: {
    skills: [{ type: 'anthropic', skill_id: 'pptx', version: 'latest' }],
  },

  // Skills execute via code execution — both parts are needed.
  tools: [{ type: 'code_execution_20260521', name: 'code_execution' }],

  messages: [{ role: 'user', content: 'Build a 3-slide deck summarising Q3 revenue.' }],
});

// The file is written inside the container; the response carries a file id.

Agent Skills are not Managed Agents. Both involve the word “agent” and they are unrelated surfaces. Skills go through container on a normal Messages call, as above. Managed Agents is a separate product where Anthropic runs the loop and hosts a session workspace. Reaching for client.beta.agents to generate a PowerPoint is a wrong turn that costs an afternoon.

Your model keeps producing correct figures in the wrong report format, no matter how much you add to the system prompt. Skill, tool, or RAG?Answer

A skill. The facts are right, so retrieval is not the gap; nothing needs doing, so a tool is not the gap. What is missing is the procedure — your format, your section order, your conventions — which is exactly what a skill carries.

The reason the system prompt is not working is usually length. Formatting rules added there compete with everything else for attention on every request. In a skill they arrive as the focused, relevant instruction at the moment the task calls for them.

Artifacts: output that is a document, not a message

An artifact is substantial output rendered as its own thing — a page, a document, an app — instead of scrolling past in a conversation. It has a URL, it persists, it can be revised in place, and it can be shared.

The distinction that matters is not technical, it is about audience.

Not an artifact · advice for you, now
"Why is this query slow?"

  -> An answer in the conversation.
     You read it, you change the
     query, you move on.

     Nobody else ever needs it.
     A document would be overhead.

"Write the migration plan for
 moving us off the old schema."

  -> A page other people will read,

     It needs a link.
i

The test: does anyone other than the person asking need to see this, or will the person asking need it again next week? If yes, it wants to be a document. If it is a fix you are about to apply and forget, it wants to be a sentence.

What this means for what you build

You will mostly meet artifacts as a user of AI tools rather than as something you implement. The transferable lesson is about your own products: when your AI feature produces something substantial, giving it a home — a URL, a version, a share button — changes it from a novelty into something a team uses. Output that only exists inside a chat transcript is output that gets lost.

Real worldThe site you are reading

These notes are the case in point. As chat messages they would have been read once and lost. As files with URLs, a search index and a build script, they are something to return to, extend, and hand to somebody else.

Nothing about that required an AI feature. It required deciding that the output had an audience and a future, and then giving it a shape that matched.

Choosing between them

✓ Worth remembering
  • Tools add ability, RAG adds facts, skills add know-how, artifacts add a place to put the result. Different problems.
  • If the facts are right but the procedure is wrong, no amount of retrieval will fix it. That is a skill.
  • A skill’s description is the only part always in context — write it as a trigger in the words people actually use.
  • Progressive disclosure is the point: one line always, the body on demand, references only when needed.
  • Agent Skills go through container on a normal Messages call. That is not Managed Agents.
  • Output with an audience deserves a URL. Output that only lives in a transcript gets lost.
