Four ways to extend a model, and how they differ

By this point in the notes you have met several things that all sound like “giving the model more abilities”. They are genuinely different mechanisms, and picking the wrong one is the most common design mistake people make when building with AI.

MechanismWhat it addsWho invokes itLives where
ToolsThe ability to do something — read a row, send an email, run a query.The model, mid-conversation.Your code, or an MCP server.
RAGKnowledge the model was never trained on, fetched fresh for each question.Your code, before the call.A vector store you own.
SkillsKnow-how — the steps, the conventions, and the files needed to do a task properly.The model, when the task calls for it.A folder with a SKILL.md.
ArtifactsA place to put a big piece of output, so it becomes a document instead of a wall of chat.The model, when the output deserves it.The host application.
💡
In plain English

Think of a new person joining your office. Tools are the keys and the logins you hand them. RAG is the filing cabinet where they look things up. Skills are the “this is how we do it here” handbook they open when that kind of job comes up. Artifacts are the difference between shouting the answer to you across a noisy office and handing you a neatly typed report.

!

The common mistake is reaching for RAG when the real problem is know-how. If the model gets the facts right but follows the steps wrong — wrong format, wrong order, skipping the step your team always does — retrieval will not fix any of that. That is a skill.

Skills: instructions that load themselves

💡
In plain English
A skill is a written set of steps that loads itself the moment it becomes relevant, instead of sitting in the prompt all the time and taking up space. Think of a rack of instruction cards on a wall: the model reaches for the one card that matches the job, instead of carrying all of them everywhere.

A skill is just a folder. At the top of it sits a SKILL.md file whose header carries a name and a one-line description. Below that is whatever the task needs — longer instructions, reference documents, scripts, templates.

What makes it useful is that it opens up in stages. Only the one-line description sits in the context all the time. The model reads the full file — and any files that file points to — only when a task actually needs it.

mdskills/invoice-review/SKILL.md
---
name: invoice-review
description: >
  Review a supplier invoice against our purchase-order rules before it is
  approved for payment. Use whenever someone asks to check, review, or approve
  an invoice, or asks whether an invoice looks right.
---

# Reviewing a supplier invoice

Work through these in order. Stop at the first hard failure and say which.

1. **Match the PO.** Every line must map to a line on the referenced purchase
   order. A line with no PO line is a hard failure — never "probably fine".
2. **Check the totals.** Recompute from the line items. Do not trust the stated
   total; the whole point of this check is that it is sometimes wrong.
3. **Check the tax treatment** against `reference/tax-rules.md`. Read that file
   only when the supplier is outside the UK — domestic invoices never need it.
4. **Flag anything over £10,000** for a second human approver, regardless of
   whether it passes everything else.

## Output

A short verdict — `approve`, `query`, or `reject` — then the reasons as bullets.
Quote the invoice line number for every problem. Never approve with unresolved
queries; "approve with caveats" is not one of the three options.

## What not to do

- Do not contact the supplier. That is a person's decision, not this task's.
- Do not adjust figures to make them match. Report the mismatch.

What makes a skill good

RuleWhy
The description is a trigger, not a summary. Say when to use it, using the words a real person would actually type.It is the only part that is always in the context. If it does not match the way people word the request, the skill never loads and everything below it is wasted effort.
Write the steps, not the background. What to do, in what order, and where the decisions are.The model already knows what an invoice is. What it does not know is that your team always recalculates the total.
Say what not to do.Telling it what not to do is what prevents the confident, believable, wrong action — and that is the failure that actually costs you money.
Push the detail into separate files.It keeps the always-read part short, and keeps the rarely-needed reference out of the context until the day it matters.
One skill, one job.A skill that covers “finance tasks” matches everything and helps with nothing.

Using skills from the API

On the Messages API, skills run inside the code-execution container, so you switch them on through container next to the code-execution tool. This is the route that produces real .pptx, .xlsx or .docx files.

tsa skill that produces a real file
const response = await client.beta.messages.create({
  model: 'claude-opus-5',
  max_tokens: 16000,
  betas: ['code-execution-2025-08-25'],

  // Which skills are available inside the container for this request.
  container: {
    skills: [{ type: 'anthropic', skill_id: 'pptx', version: 'latest' }],
  },

  // Skills execute via code execution — both parts are needed.
  tools: [{ type: 'code_execution_20260521', name: 'code_execution' }],

  messages: [{ role: 'user', content: 'Build a 3-slide deck summarising Q3 revenue.' }],
});

// The file is written inside the container; the response carries a file id.

Agent Skills are not the same thing as Managed Agents. Both have the word “agent” in them and they are completely different things. Skills go through container on an ordinary Messages call, as shown above. Managed Agents is a separate product where Anthropic runs the loop and hosts a workspace for the session. Reaching for client.beta.agents to make a PowerPoint is a wrong turn that costs you an afternoon.

Your model keeps producing correct figures in the wrong report format, no matter how much you add to the system prompt. Skill, tool, or RAG?Answer

A skill. The facts are right, so retrieval is not the missing piece; nothing needs doing, so a tool is not it either. What is missing is the method — your format, your order of sections, your conventions — and that is exactly what a skill carries.

The reason the system prompt is not working is usually that it is too long. Formatting rules added there have to compete with everything else for attention, on every single request. In a skill they arrive as one focused, relevant instruction at the exact moment the task needs them.

Artifacts: output that is a document, not a message

💡
In plain English
Some output is a reply, and some output is a thing — a document, a page, a spreadsheet. A reply scrolls away and is gone; a thing has an address, and can be reopened, edited and shared. Artifacts are the second kind, and choosing between the two is really a question about what the person is going to do with what you gave them.

An artifact is a big piece of output shown as its own thing — a page, a document, an app — instead of scrolling past inside a conversation. It has a link, it stays there, it can be edited in place, and it can be shared.

The difference that matters is not technical at all. It is about who is going to read it.

Not an artifact · advice for you, now
"Why is this query slow?"

  -> An answer in the conversation.
     You read it, you change the
     query, you move on.

     Nobody else ever needs it.
     A document would be overhead.
An artifact · work with an audience
"Write the migration plan for
 moving us off the old schema."

  -> A page other people will read,
     follow, and refer back to.

     It outlives the conversation.
     It needs a link.
i

The test is simple: does anybody other than the person asking need to see this, or will the person asking need it again next week? If yes, it should be a document. If it is a fix you are about to apply and then forget, it should be one sentence.

What this means for what you build

You will mostly meet artifacts as a user of AI tools rather than as something you build yourself. The lesson that carries over to your own products is this: when your AI feature produces something substantial, giving it a home — a link, a version, a share button — turns it from a novelty into something a whole team uses. Output that only exists inside a chat transcript is output that gets lost.

Real worldThe site you are reading

These notes are the obvious example. As chat messages they would have been read once and then lost. As files with links, a search index and a build script, they are something you can come back to, add to, and hand to somebody else.

None of that needed an AI feature. It only needed somebody to decide that the output had readers and a future, and then to give it a shape that matched.

Choosing between them

💡
In plain English
Four options, and one question for each. Does it need to do something? A tool. Does it need to know something it was never trained on? Retrieval. Does it need to know how your team does things? A skill. Does the output need to stay around as a document? An artifact. Most of the confusion here clears up the moment you ask which of those four you actually have.
✓ Worth remembering
  • Tools add ability, RAG adds facts, skills add know-how, artifacts add a place to put the result. Four different problems.
  • If the facts are right but the steps are wrong, no amount of retrieval will fix it. That is a skill.
  • A skill's description is the only part that is always in the context — write it as a trigger, in the words people actually use.
  • Opening up in stages is the whole point: one line always, the main file on demand, the references only when they are needed.
  • Agent Skills go through container on a normal Messages call. That is not the same thing as Managed Agents.
  • Output that has readers deserves a link. Output that only lives inside a transcript gets lost.
Your assistant keeps formatting reports the wrong way, even though the correct format is written in a document it can retrieve. Which of the four do you need?Answer

A skill, not retrieval. Retrieval puts the format document in front of the model as information, and information has to compete with everything else in the context. A skill is know-how about method: it loads when the task matches, and it tells the model how to behave.

The difference is facts versus method. “What is our refund policy” is retrieval; “how we write a report here” is a skill.
