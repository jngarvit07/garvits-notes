Why shape matters more than wording

💡
In plain English
When a person reads the output, one extra line of introduction does no harm. When your code reads it, "Sure! Here's the JSON you asked for:" sitting in front of the data is a crash. The moment an AI call feeds another program, you stop needing good writing and start needing a guaranteed structure.
Not this · hope, then parse
const out = await model({
  prompt: `Extract the invoice fields.
Respond with JSON only, no markdown,
no explanation. I mean it.`
});

const data = JSON.parse(out);
// Crashes on:
//   "Here is the JSON:\n{...}"
//   "```json\n{...}\n```"
//   "{...}  Let me know if..."
//   a trailing comma
//   a curly quote instead of "
Do this · declare the schema
const out = await model({
  prompt: 'Extract the invoice fields.',
  responseFormat: {
    type: 'json_schema',
    schema: InvoiceSchema,   // enforced
  },
});

// Guaranteed to parse and to match
// the schema. Now check the CONTENT,
// which is a completely separate job.
const data = InvoiceSchema.parse(out);
!
A schema guarantees the shape and nothing else. You can get perfectly valid JSON containing an order_id that does not exist, a refund bigger than the order, a date in 1847, or a confident extraction of a field the document never had. Structured output removes parse errors. It does not remove wrong answers, and treating it as if it does is how a whole class of bug slips past review.

The four levels of enforcement

MethodGuaranteeVerdict
1Ask for it in the promptNoneWorks most of the time, which is the worst possible failure rate — often enough to ship, rarely enough that nobody wakes you up.
2Ask, plus a few examplesNone, but betterNoticeably more reliable. Still just a hope.
3Tool / function callingStrongThe provider checks the arguments against your schema. Well supported everywhere.
4Constrained decodingAbsoluteInvalid tokens are removed from the choice at every step, so broken output is not merely unlikely — it is impossible.
💡
How constrained decoding actually works
Remember that the model produces a score for every token in its vocabulary, and a separate step picks from that list. Constrained decoding edits the list before the pick happens. If the schema says the next character must be " or }, every other token gets its score set to minus infinity. The model cannot produce invalid JSON in the same way you cannot walk through a wall — it is not willpower, it is the shape of the space.
txtGrammar-constrained generation, step by step
schema:  { "total": number }
so far:  {"total":

  full vocabulary        after the grammar mask
    "  0.72   ->  -inf     (a string cannot start a number)
    1  0.09   ->   0.09
    2  0.04   ->   0.04
    -  0.02   ->   0.02    (a minus sign is allowed)
    the 0.01  ->  -inf
    ...                    everything that is not valid here: -inf

  The model still CHOOSES. It simply cannot choose wrongly.
i
Constrained decoding is offered by most hosted providers under a name like "strict" or "structured outputs", and on self-hosted stacks through libraries like Outlines or llama.cpp's grammars. Where it is available, it is simply better than level 3 for extraction. It usually limits which JSON Schema features you can use — expect no anyOf at the top level, and every field required.

Designing a schema the model reads well

💡
In plain English
The schema is not just a checker bolted on at the end — the model sees it and reads it as part of your instructions. A field called d with no description gets filled in with a guess. A field called invoice_date described as "the date printed on the invoice in YYYY-MM-DD, not today's date" gets filled in correctly. Time spent on the schema is time you do not have to spend on prompt wording.
tsA schema that does most of the prompting for you
const InvoiceSchema = z.object({
  invoice_number: z.string()
    .describe('As printed on the document. Null if not present.')
    .nullable(),

  // An enum removes a whole category of variation. Without it you get
  // "INR", "inr", "₹", "rupees", "Indian Rupee" across the same set of files.
  currency: z.enum(['INR', 'USD', 'EUR', 'OTHER']),

  total: z.number()
    .describe('Grand total INCLUDING tax, as a number with no symbol.'),

  // Every optional field should be nullable rather than missing, and the
  // description must say when to use null. Otherwise the model invents
  // something believable instead of admitting the field was not there.
  due_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/)
    .describe('ISO date. Null if the invoice states no due date.')
    .nullable(),

  line_items: z.array(z.object({
    description: z.string(),
    quantity: z.number().int().positive(),
    unit_price: z.number(),
  })).describe('One entry per row of the itemised table.'),

  // The way out. Without one, a model asked for a structure will produce
  // that structure — even from a photograph of a cat.
  extraction_confidence: z.enum(['high', 'low'])
    .describe('low if the document was unclear or is not an invoice'),
});
Name fields as you would for a colleague

shipping_address_country, not c3. The name is the strongest clue the model has about what belongs in there.

Enums instead of free text

Any field with a known set of valid values should be an enum. It saves you cleaning up the values later and removes a whole class of nearly-right answers.

Nullable, not optional

A missing field is confusing — was it absent from the document, or did the model just forget? An explicit null, with a description saying when to use it, is a real answer.

Always give it a way out

A confidence field, a not_applicable enum value, or a reason_declined. Forced into a shape with no exit, a model will fill it in whether or not the input supported it.

!
Deeply nested schemas make the quality worse. Four levels of nesting, with arrays of objects containing more arrays, gives noticeably worse extraction than a flat structure, and it is slower too. If you need a complicated shape, extract it flat and assemble it in your own code — that assembly is code you can test, and the model's part of the job gets easier.
Your extractor returns a believable due_date for invoices that do not have one. The field is marked optional. What is wrong?Answer

Optional means the model is allowed to simply leave the key out, which feels to it like an unremarkable choice — and producing a believable date is a better next-token guess than producing nothing at all. Nothing has told it that "absent" is a valid and expected outcome.

Make it nullable and required, and describe when null applies: "Null if the invoice states no due date." You have turned "you may skip this" into "you must answer, and nothing is one of the allowed answers."

Tool calling, precisely

💡
In plain English
The model cannot run anything. It never could. What it produces is a neat message saying "I would like to call lookup_order with this order number" — and then your code decides whether to allow it, runs it, and hands the result back. That decision point is not a formality. It is where every permission check, every rate limit and every audit log belongs.
tsThe gate every tool call should pass through
for (const call of response.toolCalls) {
  // 1. Is this tool available to THIS user? The model's opinion that it
  //    should be called is not a permission decision.
  if (!allowedTools(user).includes(call.name)) {
    results.push({ id: call.id, error: 'not_permitted' });
    continue;                                   // tell it; do not throw
  }

  // 2. Check the arguments again on your side. The provider's check is
  //    not your check, and business rules cannot fit inside a schema.
  const args = TOOLS[call.name].schema.safeParse(call.arguments);
  if (!args.success) {
    results.push({ id: call.id, error: 'invalid_arguments: ' + args.error });
    continue;                                   // it can correct itself
  }

  // 3. Anything that cannot be undone stops here and waits for a person,
  //    who is shown the REAL effect — the amount, the recipient, the change.
  if (TOOLS[call.name].irreversible) {
    results.push({ id: call.id, status: await askHuman(call, user) });
    continue;
  }

  // 4. Run it as the user. Never as your service account.
  audit.log({ user: user.id, tool: call.name, args: args.data });
  results.push({ id: call.id, result: await TOOLS[call.name].run(args.data, user) });
}
!
Send errors back to the model as tool results, not as exceptions. A tool that returns {"error": "no order found with that number"} lets the model recover — ask the user, try a different search, explain the problem. An exception that breaks the loop turns a fixable situation into a failed request. Write tool errors the way you would write a message to a colleague, not as a stack trace.

Designing the set of tools

💡
In plain English
Every tool you offer is a permission you have handed to a system that can be talked into things. The design question is not "what would be convenient" but "what is the smallest ability that does this job". A tool that runs any SQL you like is a convenient way to walk straight past every control you have ever written.
Not this · general purpose
run_sql(query: string)
read_file(path: string)
http_request(url, method, body)
send_email(to, subject, body)

// Each one is "do anything at all"
// wearing a specific-sounding name.
// There is no check you can write on
// run_sql(query) that is not itself
// an entire database engine.
Do this · one job each
get_order(order_id)
list_orders_for_current_user(limit)
refund_order(order_id, amount, reason)
read_project_file(project_id, name)
notify_customer(order_id, template_id)

// Every one can be permission-checked,
// rate-limited, logged and reasoned
// about. How much damage it can do is
// written into the signature itself.
RuleWhy
The description is the documentationIt is the only thing the model has when deciding whether to reach for this tool. Say what it does, when to use it, when not to, and what it gives back.
Fewer tools, better chosenThe model picks less accurately as the list grows. Past roughly fifteen or twenty, route to a smaller set first instead of offering everything at once.
No two tools that overlapTwo tools that could both plausibly apply gives you inconsistent behaviour that is very hard to debug. Merge them, or spell out the boundary in both descriptions.
Use ids, not free text, wherever you canrefund_order(order_id) can be checked. refund(customer_name) needs a fuzzy name lookup that can match the wrong person.
Return as little as possibleEvery byte you return becomes a token in the next call, and in every call after that. Return the fields that are needed, not the whole record.
Make it safe to call twiceRetries happen. A tool called twice by accident must not refund twice. Take an idempotency key.
You need the assistant to answer any question about your database. Is run_sql justified here?Answer

Almost never in a real product. It gives read access to everything, cannot be permission-checked in any meaningful way, and a prompt injection hidden in any fetched text turns straight into a data leak.

The workable versions are narrower: run it against a read-only copy, as a database user with row-level security enforcing which tenant's rows are visible, limited to a set of views built for exactly this purpose, with a query timeout and a row limit. Notice that every one of those is a database-level control. The safety comes from the boundary, never from the wording of the tool description.

When the shape is right and the content is wrong

💡
In plain English
Two layers of checking, and they catch different things. The schema catches "this is not the right shape". Your business rules catch "the shape is fine and the values are impossible". Only the second one notices a refund bigger than the order, or a date in the next century. Systems that stop at the schema fail in ways that look perfectly correct all the way into production.
tsTwo layers, and a retry that carries the reason with it
async function extract(doc: string, attempt = 0): Promise<Invoice> {
  const raw = await model({ prompt: build(doc), schema: InvoiceSchema });

  // Layer 1 — the shape. With constrained decoding this rarely fails,
  // and you check anyway, because "rarely" is not "never".
  const shape = InvoiceSchema.safeParse(raw);
  if (!shape.success) return retry(doc, attempt, String(shape.error));

  // Layer 2 — does it make sense. No schema can express any of these.
  const problems = [
    shape.data.total < 0                        && 'total is negative',
    shape.data.total > 1_000_000                && 'total unbelievably large',
    sum(shape.data.line_items) !== shape.data.total
                                                && 'line items do not add up to total',
    shape.data.due_date && !isReasonableDate(shape.data.due_date)
                                                && 'due date out of range',
  ].filter(Boolean);

  if (problems.length) return retry(doc, attempt, problems.join('; '));
  return shape.data;
}

// The retry must TELL the model what was wrong. Sending the same prompt
// again is asking the same question and hoping for better luck.
async function retry(doc: string, attempt: number, why: string) {
  metrics.count('extract.invalid', { why });
  if (attempt >= 1) throw new NeedsHumanReview(why);   // two tries, then stop
  return extract(doc + `\n\nYour previous answer was rejected: ${why}`, attempt + 1);
}
!
Cap the retries and count the failures. Retrying forever on a document the model genuinely cannot read turns one bad input into a cost spike and a request that never finishes. Two attempts, then send it to a person. And the rate of invalid results is a number worth alerting on — it going up is usually the first visible sign that a format upstream changed, or that a model was updated under your feet.
✓ Worth remembering
  • Once code reads the output, you need a guaranteed shape — not a politely worded request for one.
  • Constrained decoding makes invalid output impossible; tool calling is the well-supported alternative.
  • The schema is part of the prompt. Descriptive names, enums, nullable-not-optional, and always a way out.
  • A tool call is a request. Your code checks permissions, checks arguments, and puts a gate on anything one-way.
  • Narrow tools can be made safe; general ones cannot. Send errors back to the model so it can recover.
  • Check the shape and whether it makes sense. Retry once with the reason attached, then hand it to a person.
