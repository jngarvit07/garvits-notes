Why shape matters more than wording

💡
In plain English
When a person reads the output, a stray sentence of preamble is harmless. When your code reads it, “Sure! Here's the JSON you asked for:” in front of the data is a crash. The instant an AI call feeds another program, you stop needing good writing and start needing a guaranteed structure.
Not this · hoping and parsing
const out = await model({
  prompt: `Extract the invoice fields.
Respond with JSON only, no markdown,
no explanation. I mean it.`
});

const data = JSON.parse(out);
// Throws on:
//   "Here is the JSON:\n{...}"
//   "```json\n{...}\n```"
//   "{...}  Let me know if..."
//   a trailing comma
//   a smart quote instead of "
Do this · declare the schema
const out = await model({
  prompt: 'Extract the invoice fields.',
  responseFormat: {
    type: 'json_schema',
    schema: InvoiceSchema,   // enforced
  },
});

// Guaranteed to parse and to match
// the schema. Now validate the
// CONTENT, which is a separate job.
const data = InvoiceSchema.parse(out);
!
A schema guarantees the shape and nothing else. You can get perfectly valid JSON containing an order_id that does not exist, a refund larger than the order, a date in 1847, or a confident extraction of a field the document never contained. Structured output eliminates parse errors. It does not eliminate wrong answers, and treating it as though it does is how a whole class of bug gets past review.

The four levels of enforcement

MethodGuaranteeVerdict
1Ask in the promptNoneWorks most of the time, which is the worst possible failure rate — often enough to ship, rarely enough to page you.
2Ask, plus few-shot examplesNone, but betterMeaningfully more reliable. Still a hope.
3Tool / function callingStrongThe provider validates arguments against your schema. Well supported everywhere.
4Constrained decodingAbsoluteInvalid tokens are removed from the choice at each step, so malformed output is not merely unlikely — it is unreachable.
💡
How constrained decoding actually works
Remember that the model produces a score for every token in the vocabulary, and something else picks from that list. Constrained decoding edits the list before the pick. If the schema says the next character must be " or }, every other token has its score set to negative infinity. The model cannot emit invalid JSON in the same way you cannot walk through a wall — not discipline, geometry.
txtGrammar-constrained generation, step by step
schema:  { "total": number }
so far:  {"total":

  full vocabulary        after the grammar mask
    "  0.72   ->  -inf     (a string cannot start a number)
    1  0.09   ->   0.09
    2  0.04   ->   0.04
    -  0.02   ->   0.02    (negative is allowed)
    the 0.01  ->  -inf
    ...                    everything not a valid continuation: -inf

  The model still CHOOSES. It just cannot choose wrongly.
i
Constrained decoding is available on most hosted providers under a name like “strict” or “structured outputs”, and on self-hosted stacks through libraries like Outlines or llama.cpp's grammars. Where it is offered, it is strictly better than level 3 for extraction. It usually restricts which JSON Schema features you can use — expect no anyOf at the root, and required fields everywhere.

Designing a schema the model reads well

💡
In plain English
The schema is not just a validator bolted on afterwards — the model sees it, and reads it as part of the instructions. A field called d with no description gets filled in with a guess. A field called invoice_date described as “the date on the invoice in YYYY-MM-DD, not today's date” gets filled in correctly. Time spent on the schema is time not spent on prompt wording.
tsA schema that does most of the prompting for you
const InvoiceSchema = z.object({
  invoice_number: z.string()
    .describe('As printed on the document. Null if not present.')
    .nullable(),

  // An enum removes an entire category of variation. Without it you
  // get "GBP", "gbp", "£", "pounds", "British Pound" across a corpus.
  currency: z.enum(['GBP', 'USD', 'EUR', 'OTHER']),

  total: z.number()
    .describe('Grand total INCLUDING tax, as a number with no symbol.'),

  // Every optional field must be nullable rather than absent, and the
  // description must say when to use null. Otherwise the model invents
  // something plausible rather than admitting the field was not there.
  due_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/)
    .describe('ISO date. Null if the invoice states no due date.')
    .nullable(),

  line_items: z.array(z.object({
    description: z.string(),
    quantity: z.number().int().positive(),
    unit_price: z.number(),
  })).describe('One entry per row of the itemised table.'),

  // The escape hatch. Without one, a model asked for structure will
  // produce structure — even from a photograph of a cat.
  extraction_confidence: z.enum(['high', 'low'])
    .describe('low if the document was unclear or is not an invoice'),
});
Name fields as you would for a colleague

shipping_address_country, not c3. The name is the strongest signal the model has about what belongs there.

Enums over free strings

Any field with a known set of valid values should be an enum. It removes normalisation work downstream and eliminates a whole class of near-miss values.

Nullable, not optional

An absent field is ambiguous — was it missing from the document, or did the model forget? An explicit null with a description saying when to use it is a real answer.

Always give it a way out

A confidence field, a not_applicable enum value, or a reason_declined. Forced to produce a shape with no exit, a model will fill it in regardless of whether the input supported it.

!
Deeply nested schemas degrade quality. Four levels of nesting with arrays of objects containing arrays produces noticeably worse extraction than a flat structure, and it is slower. If you need a complex shape, extract flat and assemble it in your own code — that assembly is code you can test, and the model's part gets easier.
Your extractor returns a plausible due_date for invoices that do not have one. The field is marked optional. What is wrong?Answer

Optional means the model may simply omit the key, which reads to it as an unremarkable choice — and producing a plausible date is a better next-token prediction than producing nothing. It has no instruction telling it that absence is a valid and expected outcome.

Make it nullable and required, and describe when null applies: “Null if the invoice states no due date.” You have converted “you may skip this” into “you must answer, and nothing is one of the answers.”

Tool calling, precisely

💡
In plain English
The model cannot run anything. It never could. What it produces is a structured message saying “I would like to call lookup_order with this order number” — and then your code decides whether to comply, runs it, and hands the result back. That decision point is not a formality. It is where every permission check, every rate limit and every audit log belongs.
tsThe gate every tool call should pass through
for (const call of response.toolCalls) {
  // 1. Is this tool available to THIS user? The model's opinion that it
  //    should be called is not an authorisation decision.
  if (!allowedTools(user).includes(call.name)) {
    results.push({ id: call.id, error: 'not_permitted' });
    continue;                                   // tell it, do not throw
  }

  // 2. Validate again on your side. Provider validation is not your
  //    validation, and business rules are not expressible in a schema.
  const args = TOOLS[call.name].schema.safeParse(call.arguments);
  if (!args.success) {
    results.push({ id: call.id, error: 'invalid_arguments: ' + args.error });
    continue;                                   // it can correct itself
  }

  // 3. Anything irreversible stops here and waits for a person, who is
  //    shown the ACTUAL effect — the amount, the recipient, the diff.
  if (TOOLS[call.name].irreversible) {
    results.push({ id: call.id, status: await askHuman(call, user) });
    continue;
  }

  // 4. Scope the execution to the user. Never to your service account.
  audit.log({ user: user.id, tool: call.name, args: args.data });
  results.push({ id: call.id, result: await TOOLS[call.name].run(args.data, user) });
}
!
Return errors to the model as tool results, not as exceptions. A tool that returns {"error": "no order found with that number"} lets the model recover — ask the user, try a different search, explain the problem. An exception that breaks the loop turns a recoverable situation into a failed request. Write tool errors as messages to a colleague, not as stack traces.

Designing the tool surface

💡
In plain English
Every tool you expose is a permission you have granted to a system that can be talked into things. The design question is not “what would be convenient” but “what is the smallest capability that does the job”. A tool that runs arbitrary SQL is a convenient way to bypass every control you have ever written.
Not this · general purpose
run_sql(query: string)
read_file(path: string)
http_request(url, method, body)
send_email(to, subject, body)

// Each one is "do anything" wearing
// a specific-sounding name. There is
// no check you can write on
// run_sql(query) that is not itself
// a database engine.
Do this · one job each
get_order(order_id)
list_orders_for_current_user(limit)
refund_order(order_id, amount, reason)
read_project_file(project_id, name)
notify_customer(order_id, template_id)

// Every one can be permission-checked,
// rate-limited, logged and reasoned
// about. The blast radius is written
// into the signature.
RuleWhy
The description is the documentationIt is the only thing the model has when deciding whether to reach for this tool. Say what it does, when to use it, when not to, and what it returns.
Fewer tools, better chosenSelection accuracy falls as the list grows. Past roughly fifteen or twenty, route to a subset first rather than offering everything at once.
No overlapping toolsTwo tools that could both plausibly apply produces inconsistent behaviour that is very hard to debug. Merge them or make the boundary explicit in both descriptions.
Ids, not free text, wherever possiblerefund_order(order_id) is checkable. refund(customer_name) requires a fuzzy lookup that can match the wrong person.
Return littleEvery byte returned is a token in the next call, on every subsequent turn. Return the fields needed, not the whole record.
Idempotent where you canRetries happen. A tool called twice by accident should not refund twice. Take an idempotency key.
You need the assistant to answer arbitrary questions about your database. Is run_sql justified here?Answer

Almost never in a product. It grants read access to everything, cannot be permission-checked in any meaningful way, and a prompt injection in any retrieved text turns into data exfiltration.

The workable versions are narrower: run against a read-only replica, as a database user with row-level security enforcing the tenant, restricted to a set of views built for this purpose, with a statement timeout and a row cap. Notice that every one of those is a database-level constraint. The safety comes from the boundary, never from the wording of the tool description.

When the shape is right and the content is wrong

💡
In plain English
Two layers of checking, and they catch different things. The schema catches “this is not the right shape”. Your business rules catch “this shape is fine and the values are impossible”. Only the second one notices a refund larger than the order, or a date next century. Systems that stop at the schema fail in ways that look correct all the way to production.
tsTwo layers, and a retry that carries the reason
async function extract(doc: string, attempt = 0): Promise<Invoice> {
  const raw = await model({ prompt: build(doc), schema: InvoiceSchema });

  // Layer 1 — shape. With constrained decoding this rarely fails,
  // and you check anyway because "rarely" is not "never".
  const shape = InvoiceSchema.safeParse(raw);
  if (!shape.success) return retry(doc, attempt, String(shape.error));

  // Layer 2 — sense. No schema can express these.
  const problems = [
    shape.data.total < 0                        && 'total is negative',
    shape.data.total > 1_000_000                && 'total implausibly large',
    sum(shape.data.line_items) !== shape.data.total
                                                && 'line items do not sum to total',
    shape.data.due_date && !isReasonableDate(shape.data.due_date)
                                                && 'due date out of range',
  ].filter(Boolean);

  if (problems.length) return retry(doc, attempt, problems.join('; '));
  return shape.data;
}

// The retry must TELL the model what was wrong. Sending the identical
// prompt again is asking the same question and hoping for luck.
async function retry(doc: string, attempt: number, why: string) {
  metrics.count('extract.invalid', { why });
  if (attempt >= 1) throw new NeedsHumanReview(why);   // two tries, then stop
  return extract(doc + `\n\nYour previous answer was rejected: ${why}`, attempt + 1);
}
!
Cap the retries and count the failures. Unbounded retrying on a document the model genuinely cannot read turns one bad input into a cost spike and a hung request. Two attempts, then route to a human. And the rate of invalid results is a metric worth alerting on — it climbing is usually the first visible sign that an upstream format changed or a model was updated underneath you.
✓ Worth remembering
  • Once code consumes the output, you need a guaranteed shape — not a politely worded request for one.
  • Constrained decoding makes invalid output unreachable; tool calling is the well-supported alternative.
  • The schema is part of the prompt. Descriptive names, enums, nullable-not-optional, and always an escape hatch.
  • A tool call is a request. Your code checks permissions, validates arguments, and gates anything irreversible.
  • Narrow tools can be secured; general ones cannot. Return errors to the model so it can recover.
  • Validate shape and sense. Retry once with the reason attached, then hand it to a person.
