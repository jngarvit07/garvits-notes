What Express is

Node can already run a web server — the built-in http module does it in ten lines. What it cannot do is tell you which address was asked for, read the body of the request, or run the same check before forty different endpoints. Express is a thin layer that adds exactly those things and stays out of the way otherwise.

💡
In plain English
Express is the receptionist for your server. Requests arrive at the desk; the receptionist checks who you are, decides which department handles what you asked for, and makes sure somebody always answers — even if the answer is no.
tsA complete Express server
import express from 'express';

const app = express();
app.use(express.json());                    // parse JSON request bodies

app.get('/health', (req, res) => {
  res.json({ ok: true });
});

app.listen(5000, () => console.log('listening on 5000'));

It is deliberately unopinionated: it does not choose your database, your folder layout or your validation library. That freedom is why two Express codebases can look nothing alike, and why the conventions a team picks matter more than the framework does.

The request and response cycle

Every handler receives the same three things: the request, the response, and the way to pass along. The rule underneath all of it is simple and unforgiving — exactly one response per request. Zero and the caller hangs until it times out; two and Node throws “headers already sent”.

jsonreq, res, next
app.post('/projects/:id/publish', (req, res, next) => {
  req.params.id;      // "/projects/abc/publish" -> "abc"
  req.query.force;    // "?force=true" -> "true"  (always a string)
  req.body;           // the parsed JSON body — needs express.json()
  req.headers;        // lower-cased header names
  req.user;           // not built in: put there by our auth middleware

  res.status(202).json({ jobId });   // status + body, and we are done
  // res.send(...)     — a string or a buffer
  // res.redirect(302, '/somewhere')
  // res.status(204).end()          — success, nothing to say

  next();             // WRONG here: the response already went out
});
!
The commonest form of this bug is a missing return. A validation branch that responds with a 400 and then falls through into the success path sends two responses. Get into the habit: return res.status(400).json(...).

Routes and routers

A route is a method plus a path plus a handler. A router is a group of routes that can be mounted under a prefix, which is how an API stays navigable past about twenty endpoints.

tsOne router per resource, mounted under a prefix
// routes/projects.ts
import { Router } from 'express';
const router = Router();

router.get('/', listProjects);          // GET  /api/v1/projects
router.post('/', createProject);        // POST /api/v1/projects
router.get('/:id', getProject);         // GET  /api/v1/projects/abc
router.patch('/:id', updateProject);
router.delete('/:id', deleteProject);

export default router;

// routes/index.ts
router.use('/projects', projectRoutes);
router.use('/auth', authRoutes);

// app.ts
app.use('/api/v1', apiRoutes);          // everything lives under one version prefix
!
Order matters, and it is a real source of lost afternoons. Express takes the first route that matches. Register /projects/:id before /projects/export and a request for the export is handled as a project whose id happens to be the word “export”. Specific paths first, parameterised paths after.
i
This backend has no controllers folder, on purpose. Handlers live inline in the route files, and the reusable work lives in src/services/. A controller layer existed once and was deleted: it had become a directory of one-line functions that only forwarded to a service, so every change meant editing three files to add nothing. If you are following a tutorial that insists on the layer, this is why you will not find it.

Middleware: the one idea to actually learn

Middleware is a function that runs before your handler and can do three things: look at the request, change it, or stop it. It receives the same three arguments, and calling next() passes control to whatever is next in line.

💡
In plain English
A parcel on a sorting belt. Each station can inspect it, put a sticker on it, or take it off the belt entirely. Reaching the end of the belt means reaching your handler — and a station that neither passes it along nor answers leaves the parcel sitting there, which is exactly what a hung request is.
jsWriting one
function requestLogger(req, res, next) {
  const started = Date.now();

  // Register work for when the response finishes, then get out of the way.
  res.on('finish', () => {
    logger.info({
      method: req.method,
      path: req.originalUrl,
      status: res.statusCode,
      ms: Date.now() - started,
    });
  });

  next();   // forget this line and every request hangs forever
}

app.use(requestLogger);              // everything
app.use('/api/v1/admin', requireAdmin);   // only this prefix
router.get('/:id', requireAuth, getProject);   // only this route

The order they are registered is the order they run, and the stack in this product’s app.ts is a good reading of what a real one looks like:

#MiddlewareWhy it is there, and why in that position

2cors(...)Decides which other origins may call this API. Before anything expensive, because a rejected origin should cost nothing.
3express.json({ limit })Parses the body — and caps its size, so a huge payload cannot exhaust memory.
4compression()Shrinks responses on the way out.

8The error handlerLast, always. It only sees what the layers above passed to next(error).

Reading and validating input

Input arrives in four places and every one of them is written by whoever is calling you:

WhereReached byNotes
Pathreq.params.idFrom the pattern — /projects/:id.
Query stringreq.query.pageAlways strings, and can arrive as arrays if repeated. Convert deliberately.
Bodyreq.bodyUndefined unless a parser like express.json() ran.
Headers & cookiesreq.headers.authorizationHeader names are lower-cased for you.

Validate before you use any of it, at the edge, in one place — not scattered through the handler as a series of if statements that each forgot a case.

Not this · trusting the caller
router.patch('/:id', async (req, res) => {
  // Whatever was sent goes straight into the row —
  // including "role": "ADMIN" and "credits": 999999.
  const user = await db.user.update({
    where: { id: req.params.id },
    data: req.body,
  });
  res.json(user);
});
Do this · accept only what you meant
router.patch('/:id', async (req, res) => {
  const { name, email } = req.body;

  if (typeof name !== 'string' || name.trim().length === 0) {
    return res.status(400).json({ error: 'name is required' });
  }

  const user = await db.user.update({
    where: { id: req.params.id },
    data: { name: name.trim(), email },   // an explicit list of fields
  });
  res.json(user);
});
!
Mass assignment — the left-hand version above — is one of the most reliably exploitable bugs in any API. The caller does not need a form; they need one extra key in a JSON body. Name the fields you accept, every time.

Pagination belongs in this section too, because an endpoint that returns everything is fine for the first year and then is not. Take page and limit, clamp the limit to something sane, and return the total so the caller can draw the controls.

Authentication and authorisation

Two different questions, and confusing them is how access-control bugs get written. Authentication is “who are you”. Authorisation is “are you allowed to do this”. Signing in proves the first and settles nothing about the second.

The usual mechanism is a JWT: a signed token the server hands out at sign-in and the client sends back on every request. Signed, not encrypted — anybody can read what is in it; nobody can change it without the secret.

jsonAuth middleware, close to this product's
export const authMiddleware = async (req, res, next) => {
  const header = req.headers.authorization;
  if (!header?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Not signed in' });
  }

  try {
    const decoded = jwt.verify(header.slice(7), process.env.JWT_SECRET);

    // The database decides, not the token. A suspended or deleted account
    // must stop working immediately, not when its token happens to expire.
    const user = await db.user.findUnique({ where: { id: decoded.userId } });
    if (!user || !user.isActive) {
      return res.status(401).json({ error: 'Not signed in' });
    }

    req.user = { userId: user.id, role: user.role };
    next();
  } catch {
    return res.status(401).json({ error: 'Not signed in' });
  }
};

Four rules are doing the real work there:

  1. Never trust a claim inside the token for authorisation. A token saying role: admin means the account was an admin when it was issued. Re-read the role from the database, which is what this product does.
  2. Every failure returns the same message. “No such account” versus “wrong password” tells someone probing which half they got right.
  3. Check ownership on every record, not just identity. Being signed in does not make project abc yours — the query has to be scoped to the caller.
  4. The server is the boundary. Hiding a button in the frontend is courtesy; the endpoint behind it is the control.
Not this · authenticated, but not authorised
router.get('/:id', requireAuth, async (req, res) => {
  // Signed in, so... here is any project at all.
  const project = await db.project.findUnique({
    where: { id: req.params.id },
  });
  res.json(project);
});
Do this · scoped to the caller
router.get('/:id', requireAuth, async (req, res) => {
  const project = await db.project.findFirst({
    where: { id: req.params.id, userId: req.user.userId },
  });
  if (!project) return res.status(404).json({ error: 'Not found' });
  res.json(project);
});
i
Answering 404 rather than 403 for somebody else’s record is deliberate: a 403 confirms the record exists, which is itself information. Same reason the sign-in errors above are identical.

Error handling

An endpoint returns nothing at all — no response, no error in the logs — and the caller eventually times out. Where do you look first?Answer

Two candidates, and both are in this note. Either a middleware neither responded nor called next(), so the request is parked on the conveyor belt; or an async handler threw without a wrapper, so the rejection went nowhere Express looks. Both produce exactly this silence, which is why asyncHandler exists.

An error handler is middleware with four arguments. That extra argument is not decoration — it is how Express recognises the function as an error handler at all, so removing an unused next silently turns it back into ordinary middleware.

jsonOne handler, registered last
export const errorHandler = (error, req, res, next) => {
  if (error instanceof ApiError) {
    return res.status(error.status).json({ error: error.message, code: error.code });
  }

  logger.error({ error, path: req.originalUrl }, 'unhandled error');

  // Never send a stack trace to a caller: it names your files, your
  // libraries and their versions.
  res.status(500).json({ error: 'Something went wrong' });
};

app.use(errorHandler);   // after every route
!
Express 4 does not catch errors thrown in async handlers. An await that rejects produces a rejected promise Express never looks at: no response, no log, a hung request. Either wrap every async handler, or use Express 5, where this was finally fixed.
jsonThe wrapper this backend uses
export const asyncHandler = (fn) => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

// Now a throw anywhere inside reaches the error handler:
router.get('/:id', asyncHandler(async (req, res) => {
  const project = await db.project.findUnique({ where: { id: req.params.id } });
  if (!project) throw new ApiError(404, 'Project not found');
  res.json(project);
}));

With that in place, handlers stop being defensive: they describe the happy path and throw when reality disagrees. One place decides what an error looks like on the wire, so the shape is consistent and the frontend can rely on it.

Suppose the rate limiter is registered after the routes. Every request now runs the route first, so a flood of sign-in attempts reaches the database and the password hashing before anything counts them — and password hashing is deliberately expensive. The limiter still returns 429 afterwards, and the server has already done all the work.

The limit has to sit in front of the cost it is protecting. That is the whole reason the stack has an order rather than a list.

Real worldWhy rate limiting is not optional on sign-in

An unlimited login endpoint can be tried a thousand times a second. Common passwords number in the hundreds, so it is arithmetic rather than skill. A limit of a handful of attempts per minute per address turns an afternoon into several years and costs an honest user nothing — they mistype twice, not forty times.

The same reasoning covers password reset, invitation acceptance and email verification: any endpoint that sends a message or checks a secret.

Designing the API

Idempotent

Running it twice is the same as once. GET, PUT and DELETE should be; POST usually is not, which is why double-clicks create two of things.

Stateless

The server keeps no per-caller memory between requests. Everything needed arrives with the request.

Versioning

A prefix like /api/v1 so a breaking change can ship beside the old one instead of instead of it.

One error shape

Every failure looks the same on the wire, so the frontend has one thing to handle.

REST is a convention: the path names a thing, the method says what to do with it. Following it means a new endpoint is guessable rather than documented.

Two more conventions worth adopting early: version the API in the path — this one is at /api/v1 — so a breaking change can ship alongside the old one rather than instead of it; and keep one error shape everywhere, so the frontend has a single thing to handle.

Testing and debugging

An HTTP API is unusually pleasant to test, because a test is just a request and an assertion about the answer. curl is enough to start.

jsPoking at it by hand
curl http://localhost:5000/api/v1/health

curl -X POST http://localhost:5000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"a@b.com","password":"secret"}'

curl http://localhost:5000/api/v1/projects \
  -H 'Authorization: Bearer eyJhbGciOi...'

# -i to see the status and headers; -v when you need the whole conversation.
  • A request hangs forever — some middleware neither responded nor called next(), or an async handler threw without a wrapper.
  • “Cannot set headers after they are sent” — two responses. Look for a missing return.
  • req.body is undefined — no body parser, or the caller did not send Content-Type: application/json.
  • A CORS error in the browser, but curl works — the browser is enforcing something curl does not. It is a configuration problem on the server, never a frontend one.
  • The wrong handler runs — route order; a parameterised path is shadowing a literal one.

Express in this product

  • backend/src/app.ts — the middleware stack in the table above, with the reasoning for each layer written next to it.
  • backend/src/middleware/auth.ts — authMiddleware, optionalAuthMiddleware and adminMiddleware, including the re-read of the role from the database.
  • backend/src/middleware/errorHandler.ts — ApiError, asyncHandler and the single handler at the end of the chain.
  • backend/src/routes/ — one file per resource. Start with auth.ts, then projects.ts.

Practice
  1. Write a twenty-line Express server with a GET /hello that answers with JSON. Call it with curl.
  2. Add a middleware that logs the method, path and duration of every request — and once it works, delete its next() and watch the request hang. That is the shape of a real outage.
  3. Add POST /echo that returns the body. Call it without express.json() registered and see undefined; add the parser and see it work.
  4. Throw an error inside an async handler with no wrapper, and confirm nothing comes back. Then add asyncHandler and see the 500 arrive properly.
✓ Worth remembering
  • One response per request — no more, and never none.
  • Middleware runs in registration order; the error handler is last and takes four arguments.
  • Name the fields you accept instead of spreading the body into a row.
  • Authentication is not authorisation: scope every query to the caller.
  • Wrap async handlers on Express 4, or errors vanish silently.
