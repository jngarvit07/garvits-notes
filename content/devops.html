Why this layer exists

💡
In plain English
Writing the app is one job. Getting it to run reliably on a machine that is not yours, every time someone pushes a change, without a person doing it by hand at 11pm, is a different job — and it has its own four tools. A virtual machine is a rentable computer. Docker packs your app and everything it needs into one box that runs identically on any of those computers. Kubernetes is the manager that keeps many of those boxes running, restarts the ones that die, and spreads them across machines. CI/CD is the conveyor belt that takes a git push and, if it passes the checks, turns it into an updated box running in production — with nobody typing a command.

Four ideas, and the confusion between them is almost always a layering problem — each one sits on top of the one before it.

txtThe stack, bottom to top
Virtual machine        a rentable computer: CPU, memory, disk, an OS
      |
      |  Docker packages your app + its dependencies into one file
      v
Container image        "this exact app, guaranteed to run the same everywhere"
      |

      |  how many copies, and what happens when one dies

      |  this whole chain every time the code changes

LayerAnswersEveryday analogy
Virtual machineWhere does code physically run?Renting an apartment — walls, plumbing, an address. You still have to move your own furniture in.
DockerHow do I make sure it runs the same on my laptop, in CI, and in production?A shipping container — whatever is inside, the crane, the ship and the truck all handle it the same way.
KubernetesHow do I run many containers, reliably, across many machines?A shipping port's control tower — deciding which crane loads which container onto which ship, and re-routing the moment one crane breaks.
CI/CDHow does a code change become a running update, automatically?A factory conveyor belt — the part only moves forward once it has passed the inspection station.
!
You very rarely need all four, fully, on day one. Plenty of real products run happily as one Docker container on one managed platform (Cloud Run, Render, Fly.io) with a simple CI/CD pipeline and no Kubernetes and no VM you manage yourself. Kubernetes earns its complexity when you have many services, need fine control over networking and scaling, or already have a platform team to run it. Reach for it because you have that problem, not because it is the well-known name.
Where does a plain virtual machine still fit once you have Docker and Kubernetes?Answer

Underneath both of them. Every Kubernetes cluster's worker nodes are themselves virtual machines — Kubernetes does not replace VMs, it automates what runs on a fleet of them. You reach for a raw VM yourself, outside that automation, for the cases that do not fit the container model well: a box you need full OS-level control over, a GPU machine you configure by hand, or a self-hosted CI runner.

Docker: packaging the app so it runs the same everywhere

💡
In plain English
"Works on my machine" is a real bug, not an excuse — it means the app depends on something about your laptop that production does not have. Docker's whole job is to remove that gap: you describe the exact environment the app needs once, in a file, and every machine that runs it — your laptop, the CI server, production — gets the identical thing.

An image is the packaged recipe — your code, the runtime, the dependencies, frozen. A container is a running instance of that image. You build one image and can start as many containers from it as you like, identical every time.

dockerfileDockerfile — a Node/Express API, multi-stage
# Stage 1: everything needed to INSTALL and BUILD, discarded afterwards.
FROM node:20-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: only what is needed to RUN. This is the image that ships —
# smaller image means a faster pull and a faster cold start.
FROM node:20-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist

EXPOSE 8080
CMD ["node", "dist/server.js"]
i
Order your Dockerfile from least to most likely to change. Docker caches each line as a layer and reuses the cache for every line above the first one that changed. Copying package*.json and running npm ci before copying the rest of the source means a source-only change reuses the cached, already-installed dependencies instead of reinstalling everything on every build. This one ordering choice is the difference between a ten-second rebuild and a two-minute one.

Local development: several containers, one command

A real app is rarely one container — it is an API, a database, maybe a frontend dev server. docker-compose.yml describes all of them together, so docker compose up gives every teammate the exact same local environment.

yamldocker-compose.yml — API + Postgres, for local development
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: devpassword
      POSTGRES_DB: quicktasks
    ports:
      - "5432:5432"
    volumes:
      - db-data:/var/lib/postgresql/data

  api:
    build: ./api                 # uses ./api/Dockerfile
    environment:
      DATABASE_URL: postgresql://postgres:devpassword@db:5432/quicktasks
    ports:
      - "8080:8080"
    depends_on:
      - db
    volumes:
      - ./api/src:/app/src        # live-reload: edit locally, see it inside the container

volumes:
  db-data:

Inside the Compose network, the API reaches the database at the hostname db — the service name — never localhost. That one detail catches almost everyone once.

Real world"Connection refused" that only happens inside Docker

The API's DATABASE_URL says localhost:5432. On your laptop this worked, because Postgres was running directly on it. Inside a container, localhost means that container itself — there is no Postgres listening there, only the API. The fix is always the same: point at the service name Compose (or Kubernetes) gives the other container, never localhost.

You change one line of application code and rebuild. It takes two minutes instead of the usual ten seconds. Why?Answer

Almost certainly the Dockerfile copies the whole source tree before installing dependencies, so any source change invalidates Docker's cache for the npm ci layer too, and every dependency reinstalls. Move COPY package*.json and RUN npm ci above COPY . ., and a source-only change no longer touches the dependency layer at all.

Building the pipeline: from git push to a deployed container

💡
In plain English
Continuous Integration means every change is automatically built and tested the moment it is pushed, so problems surface in minutes, not at the next release. Continuous Delivery means a passing change is automatically packaged and ready to ship. Continuous Deployment goes one step further and actually ships it, with no human clicking "approve". Most teams want CI plus delivery, with a deliberate human or automatic gate before production.
TermWhat happens automatically
CI — Continuous IntegrationEvery push is built, linted and tested. A broken change is caught in minutes, not discovered a week later by someone else's pull.
CD — Continuous DeliveryA change that passes CI is automatically packaged (a container image, built and pushed to a registry) and is one click away from production.
CD — Continuous DeploymentThe same, minus the click — a passing change on the main branch goes to production with no human step at all.
yaml.github/workflows/deploy.yml — a complete pipeline, GitHub Actions
name: build-test-deploy
on:
  push:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm run lint
      - run: npm test                     # gate: nothing below runs if this fails

  build-and-push-image:
    needs: build-and-test                 # only starts once tests pass
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - run: |
          docker build -t ghcr.io/acme/api:${{ github.sha }} ./api
          docker push ghcr.io/acme/api:${{ github.sha }}

  deploy:
    needs: build-and-push-image
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          # Point kubectl at the cluster (credentials come from a secret),
          # then update the running Deployment to the new image.
          kubectl set image deployment/api api=ghcr.io/acme/api:${{ github.sha }}
          kubectl rollout status deployment/api
i
Tag every image with the git commit SHA, never :latest. :latest means the thing running in production has no name you can trace back to a commit, rolling back is guesswork, and two deploys racing each other can push in any order. A commit SHA makes "what is actually running?" and "put yesterday's version back" both a single, unambiguous command.

Where the gates go

Why build the container image once and deploy that exact same image to staging and then production, rather than rebuilding for each?Answer

Rebuilding gives you a chance for the two environments to end up running different bytes — a dependency version resolved differently, a base image that updated between builds. Building once and promoting the identical, already-tested image means "it worked in staging" is a statement about the exact thing about to run in production, not about something similar to it.

Kubernetes: running many containers reliably

💡
In plain English
You tell Kubernetes "I want three copies of this container running, always" and it makes that true — starting them, restarting the ones that crash, moving them off a machine that dies, and spreading them across the machines you have. You describe the desired state; Kubernetes' whole job is closing the gap between that and reality, continuously.

Four objects cover most of what you will actually touch.

ObjectWhat it is
PodThe smallest unit — one or more containers that always run together, on the same machine. Usually one container per Pod.
Deployment"Keep N copies of this Pod running, and here is how to roll out a new version." You almost never create a Pod directly — you create a Deployment and it manages Pods for you.
ServiceA stable network address for a set of Pods, which come and go and change IP addresses constantly. Other things talk to the Service, never to a Pod directly.
IngressRoutes traffic from outside the cluster (the internet) to the right Service inside it, usually by hostname or path.
txtHow they relate
Internet
   |
   v
Ingress            "requests for api.quicktasks.app go to the api-service"
   |
   v
Service (api)      a stable address; picks one of the healthy Pods below
   |
   +---> Pod (api, replica 1)   \
   +---> Pod (api, replica 2)    }  managed by a Deployment,
   +---> Pod (api, replica 3)   /   which keeps exactly 3 running
yamldeployment.yaml — three replicas of the API, with resource limits
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/api:a1b2c3d      # the exact commit SHA, from CI
          ports:
            - containerPort: 8080
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef: { name: api-secrets, key: database-url }
          resources:
            requests: { cpu: "100m", memory: "128Mi" }   # what it's guaranteed
            limits:   { cpu: "500m", memory: "256Mi" }   # what it can't exceed
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 3
---
apiVersion: v1
kind: Service
metadata:
  name: api-service
spec:
  selector: { app: api }        # sends traffic to any Pod with this label
  ports:
    - port: 80
      targetPort: 8080
!
Always set resource requests and limits. Without them, one misbehaving Pod can consume an entire node's memory and take every other Pod on that machine down with it — the "noisy neighbour" failure, and it is the single most common way a Kubernetes cluster has a bad day. Without a readinessProbe, the Service starts sending traffic to a Pod before its process has actually finished starting up, and some fraction of requests fail for no reason a log will make obvious.

i
Teams often reach for Kubernetes because it is the well-known name, then spend the first few months operating a cluster instead of building the product. It earns its complexity once you have enough services that the orchestration itself becomes the hard problem — until then, a managed platform gives you the same "many containers, restarted automatically" guarantee for a fraction of the operational cost.
A Deployment says replicas: 3, but you only ever create or delete a Pod directly during testing. Two minutes later, three Pods are running again. Why?Answer

The Deployment is not describing what to do once — it is continuously reconciling reality against the desired state you gave it. Delete a Pod, and the Deployment notices the count dropped below 3 and starts a replacement immediately. This is the core idea of Kubernetes: you declare the end state, and a controller keeps making it true, indefinitely, without anyone re-running a command.

Where the virtual machine still fits

💡
In plain English
A virtual machine is a whole pretend computer — its own operating system, booted from scratch, running on top of a real one via a hypervisor. A container is much lighter: it shares the host machine's kernel and only packages the application layer on top. That difference is why containers start in milliseconds and VMs take tens of seconds, and why a single physical machine can run far more containers than VMs.
Virtual machineContainer
IncludesA full guest operating systemJust the app and its dependencies
IsolationStrong — a separate kernelWeaker — shares the host kernel
Startup timeTens of secondsMilliseconds to a couple of seconds
Density per machineA handfulDozens to hundreds

This is why the layers stack the way they do: every worker node in a Kubernetes cluster (or a Cloud Run instance, underneath the abstraction) is itself a virtual machine. Kubernetes does not remove VMs — it automates what runs on a fleet of them, so you stop thinking about any one of them individually.

When you still reach for a raw VM

Full OS-level control

Kernel modules, specific system libraries, licensing that assumes a dedicated machine — anything that does not fit the "just the app" container model.

A GPU box you configure yourself

Specific driver versions, a long-lived training or inference job that should not be interrupted by a scheduler moving it.

A self-hosted CI runner

Faster builds with a warm cache, or access to internal network resources a cloud-hosted runner cannot reach.

Legacy software

Something that was never designed to be containerised and is not worth the effort of making it so.

bashCreating one, when you need one
gcloud compute instances create ci-runner \
  --zone=europe-west2-a \
  --machine-type=e2-standard-4 \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --tags=ci-runner

# It is now a computer like any other: SSH in, install what you need.
gcloud compute ssh ci-runner --zone=europe-west2-a
!
A VM you provision by hand is a VM someone has to patch by hand. Unlike a managed container platform, nobody rotates its OS security updates for you. If you do reach for one, put it behind infrastructure-as-code (Terraform, or even just a documented creation script) so it can be recreated identically rather than becoming the one server nobody remembers how to rebuild.
Why do containers start in milliseconds while virtual machines take tens of seconds?Answer

A VM has to boot an entire guest operating system from scratch — its own kernel, its own init process — before your application even starts. A container skips all of that: it shares the host machine's already-running kernel and starts straight into your application process. The trade-off is isolation — a VM's separate kernel is a stronger security boundary than a container's shared one.

Common mistakes, and what to remember

Not this · deploy on green, no gate
on: push
jobs:
  deploy:
    steps:
      - run: docker build -t app .
      - run: docker push app:latest
      - run: kubectl set image ...
# No tests. No lint. ":latest" everywhere.
# A typo reaches production in under a minute.
Do this · tests gate the deploy
on: push
jobs:
  test:            # deploy job has "needs: test"
    steps: [lint, unit tests, integration tests]
  deploy:
    needs: test
    steps:
      - run: docker build -t app:${{ github.sha }} .
      - run: docker push app:${{ github.sha }}
      - run: kubectl set image ... app:${{ github.sha }}
!
Migrations must be backwards-compatible during a rollout. A rolling deploy means old and new code run against the same database at the same time, briefly. A migration that drops or renames a column the old code still reads breaks production for whichever users happen to be served by the old Pods. Add new columns first, deploy code that writes both old and new, then remove the old column in a later release — see the PostgreSQL note for the full pattern.
i
Do not run your database as a Pod in the same cluster unless you have a specific reason and the operational experience to back it up. A managed database (Cloud SQL, RDS) handles backups, failover and patching for you; a database Pod restarted by the same scheduler that just redeployed your API is one misconfigured rollout away from data loss.
✓ Worth remembering
  • VM, Docker, Kubernetes and CI/CD are four layers, not four competing choices — each sits on top of the one before it.
  • Order a Dockerfile from least to most likely to change, so the dependency layer stays cached.
  • Never point one container at another with localhost — use the service name.
  • Tag every image with the git commit SHA. Never deploy :latest.
  • Tests gate the deploy job — nothing ships if they fail.
  • Always set Kubernetes resource requests, limits and a readiness probe.
  • Reach for Kubernetes because you have many services to orchestrate, not because it's the well-known name.
  • Database migrations must tolerate old and new code running at once.
A rollout finishes, and for about thirty seconds a fraction of requests get errors before settling down. What's the most likely missing piece?Answer

A missing or too-eager readinessProbe. Without one, Kubernetes considers a Pod ready as soon as its container process starts, and the Service begins routing real traffic to it — even though the application inside might still be connecting to the database or warming up. A readiness probe that checks a real /healthz endpoint keeps a Pod out of rotation until it can actually serve a request.
