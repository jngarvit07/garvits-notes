The problem, before any tool

Every state-management library exists because of one sentence: two components need the same fact, and neither of them owns it. Until that sentence is true of your app, you do not need any of this, and adding it makes your code worse.

💡
In plain English
Think of a household whiteboard. While only one person cares what is on it, they can keep it in their head. The moment three people need to agree on the shopping list, you put it on the fridge where all three can read and change it. State management is deciding which facts go on the fridge — and resisting the urge to put everything there.

Here is the situation in code. A header shows the number of items in a cart. A product page adds to the cart. They are nowhere near each other in the tree.

tsxThe shape of the problem
<App>
  <Header />            <- needs to READ  cart.length
    <CartBadge />
  <Main>
    <ProductPage>
      <AddToCartButton />  <- needs to WRITE cart

useState inside AddToCartButton cannot help: state in React flows down, and CartBadge is not below it. So the fact has to live somewhere both of them can reach.

i
Notice that this is a structural problem, not a scale problem. It appears in a fifty-line app and is absent from a fifty-thousand-line one where every screen is independent. “My app is getting big, I should add Redux” is the wrong instinct. “These two distant components disagree about the same fact” is the right one.
You have a modal whose open/closed state is used only by the button that opens it and the modal itself, which is rendered right beside it. Do you need a state library?Answer

No. Both components have a common parent one level up, so a useState in that parent reaches both. That is the whole solution and it should stay the whole solution. Reaching for a global store here adds a file, an import and an indirection to replace one line.

Lifting state up, and where it stops

💡
In plain English
The first answer is not a library, it is moving the value. Put it in the nearest component that contains everybody who needs it and hand it down. For most shared state this is correct, final, and needs nothing installed.

The first answer is not a library. Move the state up to the nearest component that contains everybody who needs it, then pass it down as props. React calls this lifting state up, and for most shared state it is correct and final.

tsxLifting: the state moves up, the values come down
function Checkout() {
  // The one owner of this fact.
  const [coupon, setCoupon] = useState(null);

  return (
    <>
      <CouponField value={coupon} onApply={setCoupon} />
      <OrderTotal coupon={coupon} />
    </>
  );
}

Both children now agree about the coupon, because there is only one coupon and it lives above them both. Note the shape: the child that changes the value receives a function, the child that reads it receives the value.

Where it stops working

It stops when the nearest common parent is far away, because then every component in between has to accept a prop it does not use and pass it on. This is prop drilling.

tsxProp drilling — four components handling a prop none of them want
<App user={user}>
  <Layout user={user}>            // does not use it
    <Sidebar user={user}>         // does not use it
      <NavSection user={user}>    // does not use it
        <Avatar user={user} />    // finally
!
Drilling is a cost, not a crime. Two levels of it are fine and clearer than any abstraction you would replace them with. Four levels through components that never read the value is a genuine smell — the middle components can no longer be understood or moved on their own. That is the point at which the next tool earns its keep.
✓ Worth remembering
  • Lift first. Reach for a library only when lifting produces a long chain of pass-through props.
  • The owner of a piece of state is the nearest component that contains everyone who needs it.
  • Readers get the value; writers get the setter.

Context: skipping the chain

Context is React's built-in fix for drilling. A provider puts a value on a wire; any component below it, at any depth, taps that wire directly. The components in between never see it.

💡
In plain English
Props are handing a note person to person down a line. Context is the public address system: one announcement, and anyone in the building who is listening for it hears it. Everyone standing in the corridor between you and the listener is not involved.
tsxContext in three parts: create, provide, consume
// 1. Create the wire.
const ThemeContext = createContext('light');

// 2. Provide a value, once, near the top.
function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Layout />
    </ThemeContext.Provider>
  );
}

// 3. Consume it, at any depth, with no props in between.
function ThemeToggle() {
  const { theme, setTheme } = useContext(ThemeContext);
  return <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
    {theme}
  </button>;
}

The trap everybody hits

Context has no idea which part of its value you actually used. When the provider's value changes, every consumer re-renders — even one that only reads a field that did not change.

Not this · one context for everything
// user, theme, cart, notifications
// all on one wire.
<AppContext.Provider value={{
  user, theme, cart, notifications
}}>

// A cart change re-renders every
// component that reads the theme.
Do this · one context per concern
<ThemeContext.Provider value={theme}>
  <UserContext.Provider value={user}>
    <CartContext.Provider value={cart}>

// A cart change re-renders only
// what reads the cart.
!
Never pass a fresh object literal as the value. value={{ user, setUser }} builds a new object on every render of the provider, so every consumer re-renders every time — even when user is untouched. Wrap it: const v = useMemo(() => ({ user, setUser }), [user]).
Real worldWhere Context is exactly right

The signed-in user, the colour theme, the interface language, the current workspace. Notice what these have in common: they are read almost everywhere and they change almost never. That is Context's ideal load. The re-render cost of a change does not matter when the change happens twice a session.

The inverse — a value read by three components and changed on every keystroke — is exactly where Context performs worst and where a real store starts to pay for itself.

Context solves prop drilling. Does it replace Redux?Answer

It solves distribution — getting a value to a distant component. It does not solve what a store solves: selective subscription (only re-render the components that read the part that changed), a disciplined way to describe changes, time-travel debugging, or middleware. For low-frequency values, distribution is the entire problem and Context is enough. For high-frequency values, it is the smaller half.

The distinction that decides everything

💡
In plain English
One question sorts almost everything. Is this fact a copy of something that really lives on a server, or does it exist only in this browser tab? Those two need completely different handling, and teams unhappy with their state management have usually never made the cut.

Before comparing any library, sort your state into two piles. This single cut removes most of the difficulty, and most teams that are unhappy with their state management never made it.

Server state

A copy of something that really lives in a database somewhere else. The list of orders. The user's profile. A search result. You did not create it, you borrowed it, and the original can change without telling you.

Client state

A fact that only exists in this browser tab. Which tab is selected. Whether the sidebar is open. What is typed into a form that has not been submitted. Close the tab and it is gone, correctly.

These have completely different problems. Client state needs to be stored and read. Server state needs caching, re-fetching, deduplication, staleness, retries, loading and error states, and a decision about what to show while it refreshes.

!
The most common architecture mistake in React apps is putting server state in Redux: fetch in a thunk, store the rows in a slice, then hand-write loading flags, error flags, and a refresh mechanism nobody trusts. You have written a cache library by accident, badly. A server-state library does this correctly in one line.
✓ Worth remembering
  • Server state is a cache. Treat it like one and use a tool built for caches.
  • Client state is yours alone. It is genuinely simple and needs a simple tool.
  • Sort first, choose second. Choosing first is how teams end up with three stores.

Redux, and what it is actually doing

Redux has a reputation for complexity that belongs to its boilerplate, not its idea. The idea is small enough to write out in full.

💡
In plain English
A bank does not let you edit your balance. You submit a transaction — “deposit 50” — and the bank applies it to produce a new balance, keeping the slip. Redux is that: components never change state, they submit a description of what happened, and one function works out the new state from it. The list of slips is why you can replay exactly how you got here.
jsRedux from scratch — the whole idea, no library
function createStore(reducer, initial) {
  let state = initial;
  const listeners = [];

  return {
    getState: () => state,
    // The ONLY way state changes: hand in a description of what happened.
    dispatch(action) {
      state = reducer(state, action);      // pure: old + action -> new
      listeners.forEach((l) => l());
    },
    subscribe(l) { listeners.push(l); },
  };
}

// A reducer never edits. It returns the next version.
function cart(state = { items: [] }, action) {
  switch (action.type) {
    case 'cart/added':
      return { ...state, items: [...state.items, action.payload] };
    case 'cart/cleared':
      return { ...state, items: [] };
    default:
      return state;
  }
}

That is Redux. Twenty lines. Everything else in the ecosystem is tooling around those twenty lines.

The three rules, and why each one exists

RuleWhat it buys you
One store for the whole appThere is exactly one answer to “what is true right now”. Two stores can disagree; one cannot.
State is read-only; you dispatch actionsEvery change has a name and a cause. A log of actions is a log of everything that happened, which is why time-travel debugging is possible at all.
Reducers are pure functionsSame input, same output, no side effects. That is what makes them trivially testable and replayable.
i
Why “reducer”? Because it has the shape you pass to Array.reduce: (accumulated, next) => accumulated. Your entire application state is the result of reducing the list of every action ever dispatched. That is not an analogy — it is literally what happens.

Redux Toolkit — the version to actually write

💡
In plain English
If you have seen Redux with constants, action creators and a switch statement in three separate files, you have seen the old version. The modern one is a single file per feature and the official position is not to write it by hand any more. Most of Redux’s reputation for pain is attached to code nobody should be writing today.

If you have seen Redux code with action-type constants, action creators, switch statements and three files per feature, you have seen old Redux. Redux Toolkit (RTK) is the official current way, and the team's position is unambiguous: do not write Redux by hand any more.

tsA whole feature, in one file
import { createSlice, configureStore } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    // This LOOKS like mutation. It is not — see the note below.
    added(state, action) {
      state.items.push(action.payload);
    },
    cleared(state) {
      state.items = [];
    },
  },
});

// Action creators are generated for you from the reducer names.
export const { added, cleared } = cartSlice.actions;

export const store = configureStore({
  reducer: { cart: cartSlice.reducer },
});
i
That push is not a mutation. RTK wraps your reducer in a library called Immer, which hands you a draft — a proxy that records the changes you make and then produces a brand-new object from them. You write the readable version; you get the immutable result. This works only inside createSlice; the same line in a plain reducer is a real bug.
tsxReading and writing from a component
import { useSelector, useDispatch } from 'react-redux';

function CartBadge() {
  // A selector picks the ONE piece you need. This component re-renders
  // only when that number changes — not when anything else in the store does.
  const count = useSelector((s) => s.cart.items.length);
  return <span>{count}</span>;
}

function AddToCartButton({ product }) {
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(added(product))}>Add</button>;
}

useSelector is the thing Context cannot do. It subscribes to a slice of the store, so a component that reads items.length is untouched by a change to user.name.

!
A selector that builds a new object re-renders every time. useSelector((s) => s.cart.items.filter(inStock)) returns a new array on each run, which never equals the previous one, so the component re-renders on any store change. Either select the raw value and filter during rendering, or memoise the selector with RTK's createSelector.
Real worldA multi-step form that survives navigation

A five-step onboarding flow where the user can go back, jump to step two, refresh, and where step four's options depend on answers given in step one. This is genuinely Redux-shaped: the state is client-owned, shared across five screens, changed by many actions, and every change benefits from having a name you can read in a devtools log when a customer says “it forgot my answers”.

The DevTools extension matters more than people expect here. You get the ordered list of every action, the state before and after each one, and the ability to step backwards through them. When a bug is “the total was wrong but only sometimes”, that list is the difference between a five-minute fix and an afternoon.

Zustand: the small one

💡
In plain English
The same useful core — one store, and components that only re-render when the part they read changes — with the ceremony removed. What you give up is the enforced trail: anything can change state from anywhere, which is quicker to write and harder to reconstruct six months later.

Zustand takes the useful half of Redux — one store, selective subscription — and drops the actions, the reducers and the provider.

tsThe same cart, in Zustand
import { create } from 'zustand';

export const useCart = create((set) => ({
  items: [],
  add:   (p) => set((s) => ({ items: [...s.items, p] })),
  clear: () => set({ items: [] }),
}));

// In a component. No Provider anywhere in the tree.
function CartBadge() {
  // Same selective subscription as useSelector.
  const count = useCart((s) => s.items.length);
  return <span>{count}</span>;
}

function AddButton({ product }) {
  const add = useCart((s) => s.add);
  return <button onClick={() => add(product)}>Add</button>;
}

SetupStore, provider, slicesOne create call

Conventions in a big teamStrong — everyone writes it the same wayWeak — two developers will structure it differently

i
The trade is ceremony for traceability. Redux's boilerplate is what produces a readable, ordered history of every change. Zustand lets you call set from anywhere, which is faster to write and harder to reconstruct six months later when something sets a value and you cannot find what. Neither is wrong; they are priced differently.
When is Redux Toolkit’s extra ceremony actually worth paying for?Answer

When several people work on the codebase and you need every change to state to have a name you can read back. That ordered, reviewable history is what the boilerplate buys, and it is what makes a “the total was wrong but only sometimes” bug a five-minute job rather than an afternoon.

For a small app with one or two developers, the same discipline can be kept by convention, and Zustand’s smaller surface is the better trade. Neither is the correct answer in general — they are priced differently and you are choosing what to pay for.

React Query: server state, done properly

This is the most consequential thing in the note. Most of what people put in Redux is server state, and a server-state library removes it entirely.

Not this · a hand-built cache
// A slice, a thunk, three flags,
// and no answer for "is it stale?"
const [orders, setOrders] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

useEffect(() => {
  setLoading(true);
  fetch('/api/orders')
    .then((r) => r.json())
    .then(setOrders)
    .catch(setError)
    .finally(() => setLoading(false));
}, []);
// Two components doing this = two requests.
// Nothing refetches. Nothing retries.
Do this · React Query
const { data, isLoading, error } = useQuery({
  queryKey: ['orders'],
  queryFn: () => fetch('/api/orders')
                   .then((r) => r.json()),
});

// Two components with the same key =
//   ONE request, both get the data.
// Refetches when the tab regains focus.
// Retries failures with backoff.
// Serves cached data instantly, then
//   updates in the background.

The idea that makes it click

A query is identified by a key. Everything follows from that: the same key anywhere in the app is the same cache entry, so two components asking for ['orders'] share one request and one result. Invalidating that key tells every component holding it to refresh.

tsWriting, and telling the cache it is now wrong
const queryClient = useQueryClient();

const createOrder = useMutation({
  mutationFn: (order) => api.post('/orders', order),
  onSuccess: () => {
    // "Everything filed under ['orders'] is now out of date."
    // Every component showing that list refetches. You wire nothing up.
    queryClient.invalidateQueries({ queryKey: ['orders'] });
  },
});
💡
In plain English
A library card catalogue. Ask for a book by its reference number and you either get the copy already on the desk, or the librarian fetches it once no matter how many people asked at the same time. When a new edition arrives, the librarian marks that reference as out of date, and everyone holding the old copy gets the new one. You never manage any of that yourself.
i
In a Next.js App Router codebase, a Server Component that fetches on the server covers a large share of this need already — the data arrives with the HTML and there is no client cache to manage. React Query earns its place for data that changes while the user is looking at it: dashboards, inboxes, anything polled or refetched on focus. See the Next.js note for where that line sits.
Your app has a list of projects from the API, a “sidebar collapsed” flag, and a half-finished form. Which goes where?Answer

Projects are server state — React Query, keyed ['projects']. The sidebar flag is client state used in one place and worth persisting — a tiny Zustand store or Context, plus localStorage. The half-finished form is ephemeral client state owned by one screen — useState, and nothing more. Three different tools, and that is the correct outcome, not a failure of consistency.

Choosing, honestly

💡
In plain English
Four tools and a lot of opinion. The decision is much easier than the internet makes it look, because two questions settle nearly every case: does this data come from a server, and is it used in more than one place? Answer those honestly and the tree below resolves in under a minute.
Starting something new today

React Query for everything from the server, useState for everything else, and add a client store the first time you genuinely miss one. Most apps never reach that day, and the ones that do know exactly which state pushed them there.

Joining something that already uses Redux

Do not campaign to remove it. Learn RTK properly, and if server state is in there, move that out to React Query first. It is the change with the highest ratio of code deleted to risk taken.

!
Using more than one client store is a real cost. Redux and Zustand and three Contexts means no one can answer “where does this value live?” without searching. One client store plus one server-state library is a complete, defensible architecture. Anything beyond that needs a reason you could say out loud.

The mistakes everybody makes

💡
In plain English
Four mistakes account for most of the trouble people have here, and none of them are subtle once named. Storing everything globally, storing a number you could have calculated, editing state in place, and writing a selector that builds something new every time.

1. Putting everything in the store

A store is not a filing cabinet for all your data. State that one component uses belongs in that component. A global store full of single-use values is harder to read than the props it replaced, and every value in it is a value you now have to remember to clear.

2. Storing what you could calculate

Not this · a total that can drift
{
  items: [...],
  total: 240,      // must be updated
                   // by every single action
                   // that touches items
}
Do this · derive it on read
{ items: [...] }

// In the selector — cannot be wrong:
const total = useSelector((s) =>
  s.cart.items.reduce((n, i) => n + i.price, 0)
);

Any value stored twice will eventually disagree with itself. If it can be computed from what you already have, compute it.

3. Mutating state outside createSlice

state.items.push(x) is correct inside an RTK slice and a silent bug everywhere else — in a plain reducer, in a Zustand set, in a useState updater. The array is the same object, so React sees no change and does not redraw. In Zustand, write set((s) => ({ items: [...s.items, x] })).

4. Selectors that return something new every time

Covered above, and worth repeating because it is the number-one cause of “Redux made my app slow”. A selector returning .filter(), .map(), or an object literal produces a new reference on every store change, so the component re-renders on every store change.

✓ Worth remembering
  • Sort state into server and client before choosing anything.
  • Lift first, Context for values that rarely change, a store only for shared client state that changes often.
  • Never store what you can derive; never mutate outside a slice.
  • Keep selectors returning primitives or stable references.
  • One client store and one server-state library is a complete architecture.

Open any React app you have and list its state on paper in two columns, server and client. Then, for each client item, write the name of the component that owns it.
