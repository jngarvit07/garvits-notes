What architecture actually means here

Architecture is the small set of decisions that are costly to change later on. Everything else is just code, and code is cheap to move around. The value of drawing a system is not the picture itself; it is that drawing forces you to name the decisions you already made without noticing.

💡
In plain English
When you build a house, shifting a cupboard is easy and shifting a wall that holds up the roof is not. Architecture is those walls that hold up the roof. Which database you choose, where the line sits between your code and the model, what happens when something you depend on goes down — those are walls. The exact wording of a prompt is a cupboard. Teams get into trouble by arguing about cupboards while the walls go up with nobody looking.

The test for an architectural decision

Ask yourself: if we change our mind about this in six months, what will it cost us?

DecisionCost to reverseArchitectural?
Wording of a promptMinutesNo
Which model you callHours — as long as you put it behind one function of your ownOnly if you did not
Whether the search happens before the model call or inside itDaysYes
Whether the system stores conversation history at allWeeks, plus a conversation with the legal teamYes
Whether the model can take actions with real effectsEverything downstream of itYes — and it is the biggest one
i
Look at the second row. “Which model” feels like the most important choice and is usually the least architectural one — as long as you called it through one function of your own. The architecture is that function; the model behind it is just a setting. Getting that one thing right turns your biggest-looking decision into a small one.

The five layers every AI feature has

💡
In plain English
Every AI feature has the same five layers, whether or not anybody drew them. Naming them gives you the most useful question there is when something breaks: which layer was it? Teams that cannot answer that end up rewriting prompts to fix search problems.

Every AI system, from a weekend hobby project to a product with its own compliance team, has these same five layers. You do not get to choose whether you have them; you only choose whether you built them on purpose.

Layer 3 is where quality lives

Almost every “the AI gave a bad answer” bug is a context bug: the right passage was never fetched, the history got cut short, the system prompt never mentioned the rule. Fix the context before you touch a single word of the prompt.

Layer 4 is where risk lives

A model that can only read is just a quality problem when it gets things wrong. A model that can write, send, pay or delete is an incident. Every new ability you add multiplies the damage every context bug can do.

!
The single most useful question when something breaks: which layer was it? Teams that cannot answer this end up rewriting prompts to fix search bugs, and swapping models to fix control-flow bugs. Logging enough to be able to answer it — see the AI Ops note — is worth more than any framework.
A support bot confidently states a refund policy that was changed last month. Which layer failed?Answer

Layer 3, the context — almost certainly. Either the search index still holds the old policy document, or it holds both and the old one ranked higher. Neither the model nor the prompt is at fault, and changing either one would look like sensible action while fixing nothing. The repair is in the indexing pipeline: how documents get in, and how replaced ones get taken out.

Four reference architectures

💡
In plain English
Four shapes cover nearly every AI product there is. Recognising which one you are building — and which one somebody is talking you into — turns a long design argument into a short one, because the question stops being “how should we build this” and becomes “which of these four, and why not the simpler one”.

Nearly every AI product is one of four shapes, or a mix of them. Knowing all four by name shortens most design conversations down to “which of these, and why”.

A — The single call

txtShape A
request -> build prompt -> model -> validate -> response

Summarise this. Sort that. Rewrite this in a friendlier tone. No searching, no tools, no memory. Always start here. A surprising number of shipped AI features never need to go beyond this shape, and every shape below it is harder to debug, slower and more expensive.

B — Retrieval augmented (RAG)

txtShape B
request -> embed query -> search index -> top passages
        -> build prompt WITH passages -> model -> validate
        -> response + citations

  offline, on a schedule:
  documents -> chunk -> embed -> index

The answer depends on knowledge the model was never trained on: your documentation, your policies, this customer's history. Notice the second half — the background indexing pipeline is a real system with its own ways of failing, and it is the half people forget to design.

C — The workflow (a fixed chain)

txtShape C
request -> classify -+-> [billing prompt]  -> model -> response
                     +-> [technical]       -> model + docs search
                     +-> [everything else] -> hand to a human

  YOU decide the path. The model fills in the steps.

Several model calls, but you wrote the path through them. Predictable cost, predictable speed, and every branch can be tested. Most problems people describe as “we need an agent” are actually this shape.

D — The agent (a loop)

txtShape D
request -> +--------------------------------------+
           |  model decides: answer, or use a tool |
           |         |                     |       |
           |     answer                 tool call  |
           |         |                     |       |
           |         |              run it, feed   |
           |         |              result back  --+
           +---------|----------------------------+
                     v
                  response

  THE MODEL decides the path. You set the limits.

Use this only when the order of steps genuinely cannot be known in advance. It buys you real ability and costs you predictability: loops with no end, cost with no ceiling, and far more damage possible when it goes wrong. The Agents note covers how to keep it on a leash in detail.

A — Single callB — RAGC — WorkflowD — Agent
Cost per requestKnownKnownKnownNo ceiling until you put one there
LatencyOne callOne call plus a searchPredictableUnpredictable
DebuggableVery easilyTwo places to checkBranch by branchNeeds a full trace of every step
Failure modesWrong answerWrong passage, wrong answerWrong branchWrong plan, endless loops, wrong actions
Reach for it whenAlways firstThe answers need your own dataYou know the stepsYou genuinely cannot know the steps in advance
!
Climb this ladder one step at a time, and only when the step below has clearly failed. Starting at D because it is the most powerful is the most common and most expensive design mistake in this field. Every step up adds a whole new kind of failure that did not exist below it.

The six boundaries, and the trade at each

💡
In plain English
A boundary is a place where two parts of the system meet and somebody has to decide how they meet. Six of them come up every single time. None of these decisions is hard on its own; the trouble is that they get made silently, by whoever wrote that bit first, and then become expensive to change.

An architecture is really just a set of choices made at boundaries. These six cover most of what you will have to decide.

1. Where does the model call live?

Not this · from the browser
// Your API key is now public.
// Anyone can read it in devtools
// and spend your budget.
fetch('https://api.provider.com/v1', {
  headers: { authorization: `Bearer ${KEY}` }
});
Do this · through your own server
// Browser calls YOU. You call the
// provider. The key never leaves
// the server, and you get to apply
// auth, rate limits and logging.
fetch('/api/assistant', {
  method: 'POST', body: JSON.stringify(input)
});

There is no version of the left-hand side that is acceptable in a real product. Everything else on this page is a genuine trade-off; this one is not a trade-off at all.

2. Streaming, or wait for the whole answer?

Streaming makes a ten-second answer feel like a one-second answer, which is a big win in how good it feels. What it costs you is the chance to check the answer before the user sees any of it: once the first word is on screen, you cannot take it back. Stream writing to a human; never stream a result that another program has to read.

3. Synchronous or queued?

SynchronousQueued
User experienceThe answer comes back in the same request“We'll email you”, or the page keeps checking for it
Holds a connectionYes — for the whole length of the callNo
RetriesAwkward, because the user is sitting there waitingEasy — the job just gets retried
Right forChat, autocomplete, anything that finishes in about 30 secondsBulk work, long agent runs, processing documents

4. What is the unit of caching?

The cheapest model call is the one you never make. Three levels, cheapest first: an exact-match cache for identical inputs; a meaning-based cache for similar inputs (fast, and occasionally wrong in ways that are hard to spot); and the prompt caching the provider offers, which reuses the expensive unchanging opening block of a long system prompt. The first and the third are safe. The second one needs a cut-off value you have actually tested.

5. Where is the guardrail?

You can filter the input, filter the output, or do both. Filtering the output is the one that matters, because it is the last thing standing between a wrong answer and a user. It also slows things down, and a filter that has to work on a live stream is a design problem all of its own.

6. What does the model touch directly?

This is one of those walls that holds up the roof. Give the model tools that are narrow and specific — refund_order(order_id, reason) — rather than broad and general — run_sql(query). The narrow tool can have permissions checked, be rate-limited, be logged and be reasoned about. The broad one walks straight past every control you have.

i
A rule that stands the test of time: anything that cannot be undone gets a human involved, and that human sees exactly what will happen before it happens. Not “are you sure?” — the actual changes, the actual amount, the actual recipient. Confirmation boxes that do not show consequences just get clicked through.

Drawing it so people agree

💡
In plain English
A diagram is not documentation, it is an argument. Its job is to make people disagree with you early, while disagreeing is still cheap. A diagram everybody nods along to has usually failed — it means nobody found the thing they actually disagree about.

The point of a diagram is to bring disagreement out into the open early, while it is still cheap to fix. A diagram everybody nods at has usually failed, because agreement that easy means nobody found the thing they really disagree about.

1. Context diagram

Your system as one box in the middle. Around it: every person and every other system that talks to it, with one arrow each. Nothing at all about the inside. Takes ten minutes and settles most arguments about scope.

2. Container diagram

Open the box up. The pieces you actually deploy — web app, API, worker, database, vector index, model provider — and the protocol written on each arrow. This is the one a new engineer joining next week actually needs.

3. Sequence diagram

One single request, top to bottom, across every piece it touches. This is where slowness and failure become obvious, because you can see both in the length and the number of the hops.

4. Data flow diagram

Follow the data, not the request: where it comes in, where it gets copied, where it sits, where it leaves. This is the diagram a privacy or security review asks for, and the one that catches “hang on, we send that to an outside company?”

What makes a diagram useful

One thing: write labels on the arrows. A box diagram with blank arrows tells you almost nothing. The same diagram with what travels along each arrow, over which protocol, and what happens when it fails, is a proper design document.

txtAn arrow, labelled properly
  weak:     [ API ] ------------> [ Model provider ]

  useful:   [ API ] ------------> [ Model provider ]
                   HTTPS, ~2-8s
                   sends: system prompt + retrieved passages
                          + last 6 turns (PII redacted)
                   on failure: retry x2 with backoff,
                          then a cached generic reply

Try this
Draw the container diagram for something you have already built, then label every arrow with what breaks when the thing on the right-hand end is down. You will find at least one arrow where nobody knows the answer. That arrow is your next piece of work, and you found it with a pen instead of with an outage.
What is the single change that most improves a box-and-arrow diagram?Answer

Labelling the arrows. Boxes are the easy part, and the disagreement is almost never in them. On each arrow, write what travels along it, over what protocol, roughly how long it takes, and what happens when the other end is down.

You will usually find at least one arrow where nobody has decided what happens when it fails. That arrow is your next piece of work, and a pen found it for you instead of an outage.

Designing for the failure you will actually have

💡
In plain English
A model provider is an outside company with unpredictable speed and a real failure rate. Every normal lesson about depending on somebody else applies — timeouts, retries, fallbacks — plus two failures normal dependencies never have: an answer that is confidently wrong, and an answer that is not in the shape you asked for. Both of those need designing for, not hoping about.

A model provider is something outside your control, with unpredictable speed and a real failure rate. Treat it exactly like any other outside dependency, plus two extra kinds of failure that normal ones do not have.

FailureWhat the user sees if you did nothingThe design that handles it
Provider is downA spinning wheel, then an error pageA timeout, then a fallback: a second provider, a smaller model, or an honest “this is not available right now” with the non-AI route still working.
Rate limitedFailures that come and go under heavy useA queue that waits longer between attempts. Never retry straight away in a tight loop — that is how a small limit turns into a full outage.
Very slow responseA stuck request holding a connection openA hard timeout set below your own request timeout, plus streaming, so that slow at least still feels alive.
Confidently wrong answerThe user believes itShow the sources, show how confident it is, and design so that being wrong can be recovered from. There is no technical fix for this one.
Output is not the shape you asked forA parse error, or worse, a quiet one nobody noticesCheck it against a schema; if it fails, retry once with the error message included, then fall back. Never run JSON.parse on a model's output without protection.
tsThe wrapper every AI system should have exactly one of
// One function. Every model call in the codebase goes through it.
// This is what turns "which provider" from a wall into a cupboard.
export async function complete(input: Input): Promise<Result> {
  const started = Date.now();
  try {
    const raw = await withTimeout(provider.call(input), 20_000);

    // Never trust the shape. Validate before anything downstream sees it.
    const parsed = ResultSchema.safeParse(raw);
    if (!parsed.success) {
      metrics.count('llm.invalid_shape');
      return await retryOnce(input, parsed.error);
    }

    log({ ...trace(input), ms: Date.now() - started, ok: true });
    return parsed.data;

  } catch (err) {
    log({ ...trace(input), ms: Date.now() - started, ok: false, err });
    metrics.count('llm.failed');
    return fallback(input);        // degraded, not broken
  }
}
!
“Working, but reduced” is a product decision, not an engineering one. Decide in advance what your feature does when the model is not available, and make sure somebody outside the engineering team agrees with that answer. A search box that falls back to keyword search is fine. A checkout that quietly skips the fraud check is not.
Why validate the model's output shape even when you asked for JSON and the provider supports a structured-output mode?Answer

Because the schema promises you the shape, never the content. You can get perfectly valid JSON with an order_id that does not exist, a refund bigger than the order, or a date in the wrong century. Structured output removes parse errors; it does not remove wrong answers. The checking you actually need is the business-rule kind, sitting on top of the schema kind.

A worked architecture, end to end

💡
In plain English
One system designed all the way down, with the reasoning written next to each decision and a clear list of what has been left out on purpose. The things left out are the more useful half — knowing what you are not building, and why, is what keeps a first version small enough to actually ship.
Real world“Ask a question about your own documents” — the full design

A team uploads their documents and then asks questions about them in ordinary language. Every answer must show its sources. This is the most common AI product shape there is, and it is worth designing all the way down at least once.

Every decision, and why

DecisionChoiceWhy this one
ShapeB, RAG — not an agentAll the steps are known in advance. There is nothing here for a model to plan.
Chunk size~800 tokens, 100 overlapBig enough to hold one complete idea, small enough that five of them fit in the context. The overlap stops a sentence getting cut in half at the join.
Permission filterApplied in the search queryFiltering after the search means the forbidden chunk was already loaded into memory and one bug away from reaching the prompt. This is the single most commonly skipped line in RAG systems.
Rerank20 → 5Vector similarity is cheap and rough; a reranker is expensive and accurate. Use each one where it is good.
StreamingYes, to a humanIt feels much faster. The citations travel alongside as proper structured data, not pulled out of the stream by hand.
HistoryLast 3 turns onlyCost stays capped, speed stays capped, and it stops an old turn spoiling a new answer.
ModelBehind complete()So the choice stays a single setting. A cheaper model rewrites the query; the capable one writes the actual answer.
What is loggedWhich chunks were usedWithout this you cannot tell a search failure apart from a writing failure, and that is 80% of debugging this system.

What is deliberately not in version one

No agent loop. No meaning-based cache. No fine-tuning. No second provider to fall back on. Every one of those is a real technique, and every one is a step you climb only when the step below has clearly failed — with a test set to prove that it did. Building all of them up front gives you a system nobody can debug and whose quality nobody can measure.

✓ Worth remembering
  • Architecture is the decisions that are costly to undo. Everything else is just code.
  • Five layers: interface, control flow, context, ability, model. Quality problems live in the context; risk lives in the ability.
  • Four shapes: single call, RAG, workflow, agent. Climb one step at a time.
  • One wrapper around every model call turns the choice of provider into a single setting.
  • Label the arrows. A box diagram with blank arrows is just decoration.
  • Decide what “working, but reduced” looks like before the day you need it.
