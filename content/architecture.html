What architecture actually means here

Architecture is the small set of decisions that are expensive to change later. Everything else is just code, and code is cheap to move. The value of drawing a system is not the picture; it is that drawing forces you to name the decisions you have already made without noticing.

💡
In plain English
When you build a house, moving a cupboard is easy and moving a load-bearing wall is not. Architecture is the load-bearing walls. Choosing which database, where the boundary between your code and the model sits, what happens when a dependency is down — those are walls. Which prompt wording you use is a cupboard. Teams get into trouble by arguing about cupboards while walls go up unexamined.

The test for an architectural decision

Ask: if we changed our mind about this in six months, what would it cost?

DecisionCost to reverseArchitectural?
Wording of a promptMinutesNo
Which model you callHours — if you put it behind an interfaceOnly if you did not
Whether retrieval happens before or inside the model callDaysYes
Whether the system stores conversation history at allWeeks, plus a legal conversationYes
Whether the model can take actions with real effectsEverything downstream of itYes — the biggest one
i
Notice the second row. “Which model” feels like the most important choice and is usually the least architectural, provided you called it through one function of your own. The architecture is the interface; the model behind it is a configuration value. Getting that one right converts your biggest-looking decision into a small one.

The five layers every AI feature has

💡
In plain English
Every AI feature has the same five layers whether or not anyone drew them. Naming them gives you the most useful diagnostic question there is: when something goes wrong, which layer was it? Teams that cannot answer that end up rewriting prompts to fix retrieval problems.

Every AI system, from a weekend prototype to a product with a compliance team, has the same five layers. You do not choose whether to have them; you only choose whether they are deliberate.

Layer 3 is where quality lives

Almost every “the AI gave a bad answer” bug is a context bug: the right passage was not retrieved, the history was truncated, the system prompt did not mention a rule. Fix context before you touch the prompt wording.

Layer 4 is where risk lives

A model that can only read is a quality problem when it is wrong. A model that can write, send, pay or delete is an incident. Every capability you add multiplies the consequence of every context bug.

!
The single most useful diagnostic question: when something goes wrong, which layer was it? Teams that cannot answer this end up rewriting prompts to fix retrieval bugs, and swapping models to fix orchestration bugs. Logging enough to answer it — see the AI Ops note — is worth more than any framework.
A support bot confidently states a refund policy that was changed last month. Which layer failed?Answer

Layer 3, context — almost certainly. Either the retrieval index still holds the old policy document, or it holds both and the old one ranked higher. Neither the model nor the prompt is at fault, and changing either would be a plausible-looking action that fixes nothing. The repair is in the indexing pipeline: how documents get in, and how superseded ones get out.

Four reference architectures

💡
In plain English
Four shapes cover nearly every AI product there is. Recognising which one you are building — and which one you are being talked into — turns a long design argument into a short one, because the question stops being “how should we build this” and becomes “which of these four, and why not the simpler one”.

Nearly every AI product is one of four shapes, or a composition of them. Knowing the four by name shortens most design conversations to “which of these, and why”.

A — The single call

txtShape A
request -> build prompt -> model -> validate -> response

Summarise this. Classify that. Rewrite this in a friendlier tone. No retrieval, no tools, no memory. Start here always. A surprising share of shipped AI features never need to leave this shape, and every shape below is harder to debug, slower and more expensive.

B — Retrieval augmented (RAG)

txtShape B
request -> embed query -> search index -> top passages
        -> build prompt WITH passages -> model -> validate
        -> response + citations

  offline, on a schedule:
  documents -> chunk -> embed -> index

The answer depends on knowledge the model was never trained on: your documentation, your policies, this customer's history. Note the second half — the offline indexing pipeline is a real system with its own failures, and it is the half people forget to design.

C — The workflow (a fixed chain)

txtShape C
request -> classify -+-> [billing prompt]  -> model -> response
                     +-> [technical]       -> model + docs search
                     +-> [everything else] -> hand to a human

  YOU decide the path. The model fills in the steps.

Several model calls, but you wrote the control flow. Predictable cost, predictable latency, and every branch is testable. Most problems people describe as “we need an agent” are this shape.

D — The agent (a loop)

txtShape D
request -> +--------------------------------------+
           |  model decides: answer, or use a tool |
           |         |                     |       |
           |     answer                 tool call  |
           |         |                     |       |
           |         |              run it, feed   |
           |         |              result back  --+
           +---------|----------------------------+
                     v
                  response

  THE MODEL decides the path. You set the limits.

Use this only when the sequence of steps genuinely cannot be known in advance. It buys real capability and costs you predictability: unbounded loops, unbounded cost, and a much larger blast radius. The Agents note covers the leash in detail.

!
Climb this ladder one rung at a time and only when the rung below has visibly failed. Starting at D because it is the most capable is the most common and most expensive architecture mistake in this field. Every rung adds a category of failure that did not exist below it.

The six boundaries, and the trade at each

💡
In plain English
A boundary is a place where two parts of the system meet and somebody has to decide how. Six of them come up every time. None of these decisions is hard on its own; the trouble is that they get made implicitly, by whoever wrote that bit first, and then become expensive to revisit.

An architecture is really a set of choices at boundaries. These six cover most of what you will decide.

1. Where does the model call live?

Not this · from the browser
// Your API key is now public.
// Anyone can read it in devtools
// and spend your budget.
fetch('https://api.provider.com/v1', {
  headers: { authorization: `Bearer ${KEY}` }
});
Do this · through your own server
// Browser calls YOU. You call the
// provider. The key never leaves
// the server, and you get to apply
// auth, rate limits and logging.
fetch('/api/assistant', {
  method: 'POST', body: JSON.stringify(input)
});

There is no version of the left-hand side that is acceptable in production. Everything else on this page is a genuine trade-off; this one is not.

2. Streaming, or wait for the whole answer?

Streaming makes a ten-second answer feel like a one-second answer, which is a large perceived-quality win. It costs you the ability to validate before the user sees anything: once the first token is on screen you cannot unsend it. Stream prose to a human; do not stream a result another system will parse.

3. Synchronous or queued?

SynchronousQueued
User experienceAnswer arrives in the request“We'll email you” / poll for it
Holds a connectionYes — for the whole callNo
RetriesAwkward; the user is waitingNatural — the job is retried
Right forChat, autocomplete, anything under ~30sBatch, long agent runs, document processing

4. What is the unit of caching?

The cheapest model call is the one you do not make. Three levels, cheapest first: an exact-match cache on identical inputs; a semantic cache on similar inputs (fast, and occasionally wrong in ways that are hard to spot); and prompt caching offered by the provider, which reuses the expensive shared prefix of a long system prompt. The first and third are safe. The second needs a threshold you have actually tested.

5. Where is the guardrail?

Input filtering, output filtering, or both. Output filtering is the one that matters, because it is the last thing between a wrong answer and a user. It also costs latency, and a filter that runs on a stream is a design problem of its own.

6. What does the model touch directly?

This is the load-bearing wall. Give the model tools that are narrow and specific — refund_order(order_id, reason) — rather than broad and general — run_sql(query). The narrow tool can be permission-checked, rate-limited, logged and reasoned about. The broad one is a bypass of every control you have.

i
A rule that ages well: anything irreversible gets a human in the loop, and the human sees what will happen before it happens. Not “are you sure?” — the actual diff, the actual amount, the actual recipient. Confirmation dialogues that do not show consequences get clicked through.

Drawing it so people agree

💡
In plain English
A diagram is not documentation, it is an argument. Its job is to make people disagree with you early, while disagreeing is still cheap. A diagram everyone nods along to has usually failed — it means nobody found the thing they actually disagree about.

The point of a diagram is to make disagreement visible early, while it is still cheap. A diagram everyone nods at has usually failed, because agreement that easy means nobody found the thing they disagree about.

1. Context diagram

Your system as one box in the middle. Around it: every human and every other system that talks to it, with an arrow each. Nothing about the inside. Takes ten minutes and settles most scope arguments.

2. Container diagram

Open the box. The deployable pieces — web app, API, worker, database, vector index, model provider — and the protocol on each arrow. This is the one an engineer joining next week actually needs.

3. Sequence diagram

One request, top to bottom, across every component it touches. This is where latency and failure become obvious, because both are visible as the length and the number of the hops.

4. Data flow diagram

Follow the data, not the request: where it enters, where it is copied, where it rests, where it leaves. This is the diagram a privacy or security review asks for, and the one that catches “wait, we send that to a third party?”

What makes a diagram useful

One thing: label the arrows. A box diagram with unlabelled arrows tells you almost nothing. The same diagram with what travels on each arrow, over which protocol, and what happens when it fails, is a design document.

txtAn arrow, labelled properly

  useful:   [ API ] ------------> [ Model provider ]
                   HTTPS, ~2-8s
                   sends: system prompt + retrieved passages
                          + last 6 turns (PII redacted)
                   on failure: retry x2 with backoff,
                          then a cached generic reply

Try this
Draw the container diagram for something you have already built, then label every arrow with what fails when the thing on the right is down. You will find at least one arrow with no answer. That arrow is your next piece of work, and you found it with a pen instead of an outage.
What is the single change that most improves a box-and-arrow diagram?Answer

Labelling the arrows. Boxes are the easy part and rarely where the disagreement lives. Write on each arrow what travels along it, over what protocol, roughly how long it takes, and what happens when the far end is down.

You usually find at least one arrow whose failure behaviour nobody has decided. That arrow is your next piece of work, and a pen found it instead of an outage.

Designing for the failure you will actually have

💡
In plain English
A model provider is a third party with variable latency and a real error rate. Every ordinary dependency lesson applies — timeouts, retries, fallbacks — plus two failures ordinary dependencies do not have: an answer that is confidently wrong, and an answer that is not in the shape you asked for. Both need designing for, not hoping about.

A model provider is a third-party dependency with variable latency and a non-zero error rate. Treat it exactly like any other one, plus two failure modes normal dependencies do not have.

FailureWhat the user sees if you did nothingThe design that handles it
Provider is downA spinner, then a 500Timeout, then a fallback: a second provider, a smaller model, or an honest “this is unavailable” with the non-AI path still working.
Rate limitedRandom failures under loadA queue with backoff. Never retry immediately in a tight loop — that is how a small limit becomes an outage.
Very slow responseA hung request holding a connectionA hard timeout below your own request timeout, and a streaming interface so slow still feels alive.
Confidently wrong answerThe user believes itCitations, a visible confidence signal, and a design where being wrong is recoverable. This one has no technical fix.
Output is not the shape you asked forA parse error, or worse, a silent oneValidate against a schema; on failure, retry once with the error text, then fall back. Never JSON.parse a model's output unguarded.
tsThe wrapper every AI system should have exactly one of
// One function. Every model call in the codebase goes through it.
// This is what turns "which provider" from a wall into a cupboard.
export async function complete(input: Input): Promise<Result> {
  const started = Date.now();
  try {
    const raw = await withTimeout(provider.call(input), 20_000);

    // Never trust the shape. Validate before anything downstream sees it.
    const parsed = ResultSchema.safeParse(raw);
    if (!parsed.success) {
      metrics.count('llm.invalid_shape');
      return await retryOnce(input, parsed.error);
    }

    log({ ...trace(input), ms: Date.now() - started, ok: true });
    return parsed.data;

  } catch (err) {
    log({ ...trace(input), ms: Date.now() - started, ok: false, err });
    metrics.count('llm.failed');
    return fallback(input);        // degraded, not broken
  }
}
!
“Degraded, not broken” is a product decision, not an engineering one. Decide in advance what your feature does when the model is unavailable, and make sure someone outside engineering agrees with the answer. A search box that falls back to keyword search is fine. A checkout that silently skips fraud checking is not.
Why validate the model's output shape even when you asked for JSON and the provider supports a structured-output mode?Answer

Because the schema guarantees the shape, never the content. You can get valid JSON with an order_id that does not exist, a refund amount larger than the order, or a date in the wrong century. Structured output removes parse errors; it does not remove wrong answers. The validation you need is the business-rule kind, on top of the schema kind.

A worked architecture, end to end

💡
In plain English
One system designed all the way down, with the reasoning next to each decision and an explicit list of what is deliberately left out. The omissions are the more useful half — knowing what you are not building, and why, is what keeps a first version shippable.
Real world“Ask a question about your own documents” — the full design

A team uploads their documents and asks questions about them in natural language. Answers must cite their sources. This is the most common AI product shape there is, and it is worth designing all the way down once.

Every decision, and why

DecisionChoiceWhy this one
ShapeB, RAG — not an agentThe steps are known in advance. There is nothing for a model to plan.
Chunk size~800 tokens, 100 overlapBig enough to hold a whole argument, small enough that five fit in context. Overlap stops a sentence being cut in half at a boundary.
Permission filterApplied in the search queryFiltering after retrieval means the forbidden chunk was already in memory and one bug away from the prompt. This is the single most commonly skipped line in RAG systems.
Rerank20 → 5Vector similarity is cheap and approximate; a reranker is expensive and accurate. Use each where it is good.
StreamingYes, to a humanPerceived latency. The citations are sent as structured data alongside, not parsed out of the stream.
HistoryLast 3 turns onlyBounded cost, bounded latency, and it stops an old turn poisoning a new answer.
ModelBehind complete()So the choice stays a configuration value. A cheaper model handles query rewriting; the capable one writes the answer.
What is loggedWhich chunks were usedWithout this you cannot tell a retrieval failure from a generation failure, which is 80% of debugging this system.

What is deliberately not in version one

No agent loop. No semantic cache. No fine-tuning. No multi-provider fallback. Each of those is a real technique and each is a rung you climb when the rung below has visibly failed — with an eval set to prove it did. Building all of them up front produces a system nobody can debug, whose quality nobody can measure.

✓ Worth remembering
  • Architecture is the decisions that are expensive to reverse. Everything else is code.
  • Five layers: interface, orchestration, context, capability, model. Quality problems live in context; risk lives in capability.
  • Four shapes: single call, RAG, workflow, agent. Climb one rung at a time.
  • One wrapper around every model call turns the provider choice into a configuration value.
  • Label the arrows. An unlabelled box diagram is decoration.
  • Decide what “degraded” looks like before you need it.
