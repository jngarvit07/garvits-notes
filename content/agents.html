What an agent actually is

The word has been stretched until it means almost nothing. Strip the marketing away and an agent is one specific thing: a loop where a model decides what to do next, your code does it, and the result goes back into the model’s context — repeating until the model says it is finished.

💡
In plain English

A normal API call is a vending machine: you put a prompt in, an answer comes out, the transaction is over. An agent is closer to hiring a contractor. You describe the outcome, they decide the steps, they ask you for tools and materials as they go, and they tell you when they are done. You do not know in advance how many trips to the hardware shop it will take.

That last point is the whole difference. In a workflow you know the steps and write them down. In an agent the model chooses the steps at runtime, which is powerful exactly when the steps cannot be known in advance — and reckless when they can.

!

Most things called agents should not be. If you can draw the flowchart, write the flowchart. An agent costs more, takes longer, fails in more ways, and is much harder to test than the equivalent chain of ordinary calls. Reach for one when the flowchart genuinely cannot be drawn.

The ladder: start at the bottom

There are four rungs between “one API call” and “an agent”. Each is cheaper, faster and easier to reason about than the one above it. Climb only when the rung you are on genuinely cannot do the job.

Four questions before you build an agent

Complexity

Is the task genuinely hard to specify up front? “Turn this design doc into a pull request” qualifies. “Pull the title out of this PDF” does not.

Value

Does the outcome justify several times the cost and latency of a single call? An agent that saves ten minutes of your time is worth it; one that saves ten seconds is not.

Viability

Is the model actually good at this class of task today? Test on twenty real cases before you build infrastructure around the answer.

Cost of error

Can a mistake be caught and undone — by tests, review, a rollback? An agent that can send money or delete rows without a gate is a liability, not a feature.

A “no” to any one of those means stay on a lower rung.

Five workflow patterns worth knowing by name

Rung three covers more ground than people expect. These five shapes solve most of what gets reached for an agent to solve, and every one of them is ordinary code you can unit-test.

PatternShapeUse it when
Prompt chainingOutput of call A becomes input of call B, with a check in between.The task decomposes cleanly into fixed steps. Outline → draft → polish. Extract → validate → store.
RoutingA cheap classifier picks which specialised prompt or model handles the input.Inputs fall into distinct categories that want different handling. Refund vs. technical vs. sales, each with its own prompt and its own model tier.
ParallelisationRun several calls at once, then combine. Either the same task voted on, or different subtasks joined.Latency matters and the pieces are independent. Or you want three opinions on a judgement call and a majority vote.
Orchestrator–workerOne call plans the subtasks, workers do them, one call synthesises.The number of subtasks is only known once you have looked at the input. Searching six sources; editing the files a change happens to touch.
Evaluator–optimiserGenerate, critique against explicit criteria, revise. Loop with a hard cap.Quality is judgeable and revision genuinely helps — translation, code that must pass tests, writing with a rubric.
i

Routing pays for itself faster than any other pattern. A small model classifying inbound messages, then only escalating the hard ones to a capable model, typically cuts the bill by most of it while improving quality on the narrow cases — a focused prompt beats a general one.

tsrouting: cheap triage, expensive handling, only where needed
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

// Step one: a small model decides where this goes. Cheap, called on everything.
async function route(message: string) {
  const res = await client.messages.create({
    model: 'claude-haiku-4-5',
    max_tokens: 16,
    system: 'Classify the support message. Reply with exactly one word: billing, technical, or other.',
    messages: [{ role: 'user', content: message }],
  });
  const text = res.content.find((b) => b.type === 'text');
  return text?.text.trim().toLowerCase() ?? 'other';
}

// Step two: the specialist. A focused prompt, and only the hard lane pays for
// the capable model.
const LANES = {
  billing:   { model: 'claude-haiku-4-5', system: 'You answer billing questions. Cite the invoice number.' },
  technical: { model: 'claude-opus-5',    system: 'You debug technical problems. Ask for logs before guessing.' },
  other:     { model: 'claude-haiku-4-5', system: 'You triage. Summarise the request in one sentence.' },
} as const;

export async function handle(message: string) {
  const lane = LANES[await route(message) as keyof typeof LANES] ?? LANES.other;
  return client.messages.create({
    model: lane.model,
    max_tokens: 16000,
    thinking: { type: 'adaptive' },
    system: lane.system,
    messages: [{ role: 'user', content: message }],
  });
}

The agent loop, drawn

Every agent framework you will ever read about is this loop with decoration on top. Understanding it once means you can read any of them.

i

The model cannot do anything. It emits a request — a name and some JSON. Your code decides whether that request runs. Every piece of agent security follows from taking that sentence seriously.

tsthe loop, by hand, so you have seen it once
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();
const MAX_STEPS = 12;   // never ship an agent without this

let messages: Anthropic.MessageParam[] = [{ role: 'user', content: task }];

for (let step = 0; step < MAX_STEPS; step++) {
  const res = await client.messages.create({
    model: 'claude-opus-5',
    max_tokens: 16000,
    thinking: { type: 'adaptive' },
    tools,
    messages,
  });

  if (res.stop_reason === 'end_turn') return res;

  // A server-side tool hit its internal limit. Hand the turn back and continue;
  // do not add a "please continue" message, the API resumes on its own.
  if (res.stop_reason === 'pause_turn') {
    messages.push({ role: 'assistant', content: res.content });
    continue;
  }

  messages.push({ role: 'assistant', content: res.content });

  const calls = res.content.filter(
    (b): b is Anthropic.ToolUseBlock => b.type === 'tool_use',
  );

  // All results go back in ONE user message. Splitting them across several
  // messages quietly teaches the model to stop asking for tools in parallel.
  const results: Anthropic.ToolResultBlockParam[] = [];
  for (const call of calls) {
    try {
      results.push({
        type: 'tool_result',
        tool_use_id: call.id,
        content: await runTool(call.name, call.input),
      });
    } catch (err) {
      // Return the failure as a result. Never drop it — a missing tool_result
      // for a requested tool_use is a malformed conversation.
      results.push({
        type: 'tool_result',
        tool_use_id: call.id,
        content: String(err),
        is_error: true,
      });
    }
  }

  messages.push({ role: 'user', content: results });
}

throw new Error(`Agent did not finish within ${MAX_STEPS} steps`);
💡
In plain English

You have now seen the entire mechanism. In practice you would use the SDK’s tool runner, which writes this loop for you and still lets you intervene each turn — but knowing what it is doing underneath is the difference between debugging an agent and rebooting it and hoping.

Your agent asks for three tools at once. You run them and send back three separate user messages, one result each. What breaks?Answer

Two things. First, the conversation is malformed: the API expects every tool_use in one assistant turn to be answered by tool_result blocks in one following user message. Second — and this is the one that bites quietly — even where it is tolerated, you are demonstrating to the model that parallel calls get handled serially, and it stops requesting them. Your agent gets slower over the course of a conversation and you will not find it in a log.

Designing the tool surface

The tools you expose are your agent’s design. A vague tool set produces a confused agent no prompt can rescue, and the most common cause of a bad agent is not the model — it is fifteen overlapping tools with descriptions written as an afterthought.

Write the description for a competent new colleague

The description is not documentation, it is the instruction the model actually follows. It should say what the tool does, when to reach for it, when not to, and what it returns.

Not this · a name restated
{
  name: 'search',
  description: 'Searches.',
  input_schema: {
    type: 'object',
    properties: { q: { type: 'string' } },
  },
}
Do this · when, when not, and what comes back
{
  name: 'search_invoices',
  description:
    'Full-text search over invoice line items for ONE customer. ' +
    'Use when the user names a product or description but not an ' +
    'invoice number. Do not use to fetch a known invoice — use ' +
    'get_invoice, which is exact and cheaper. Returns at most 20 ' +
    'matches, newest first, each with number, date and total.',
  input_schema: {
    type: 'object',
    properties: {
      customer_id: { type: 'string', description: 'Customer UUID.' },
      query: { type: 'string', description: 'Words to match in line items.' },
    },
    required: ['customer_id', 'query'],
    additionalProperties: false,
  },
  strict: true,
}

Broad tool or specific tool?

One run_sql tool can do anything a hundred narrow tools can. That breadth is exactly the problem: your harness sees an opaque string and cannot tell a harmless SELECT from a DROP TABLE. Promoting an action to its own tool gives your code a typed hook it can gate, log, render and parallelise.

Promote it to a dedicated tool when…Why breadth fails there
It crosses a security boundary or is hard to reverse.send_email is trivial to gate behind a confirmation. bash("curl -X POST ...") is not.
It needs an invariant enforced.An edit_file tool can refuse a write if the file changed since the model last read it. A shell command cannot.
It should render as something in your UI.A question to the user is worth its own tool so it can appear as a modal and block the loop until answered.
It is safe to run in parallel.Your harness can run five read_file calls at once. It cannot know whether five shell commands are safe to interleave.

The rule of thumb: start broad for reach, promote to specific tools the moment you need to gate, render, audit or parallelise.

Context over a long run

An agent that runs for forty steps has a problem a single call never has: the transcript grows on every turn, you pay for all of it on every request, and eventually it does not fit. Three different mechanisms address three different versions of that problem, and they are routinely confused.

Context editing

Prunes. Clears stale tool results and old thinking blocks out of the transcript. Within one session. Use when the history is full of large results nobody needs any more.

Compaction

Summarises. Condenses earlier context into a summary block when you approach the window limit. Within one session. Use for conversations that genuinely run long.

Memory

Persists. Files the agent reads and writes that outlive the process. Across sessions. Use when tomorrow’s run needs to know what today’s learned.

!

Compaction has one non-obvious rule. Append the whole response.content back onto your messages each turn, not just the extracted text. The compaction blocks in the response are what the API uses to replace the compacted history on the next request — pull out only the text string and you silently lose the compaction state, and the context starts growing again with no error to tell you.

Caching is the other half of the cost story

Because every request resends the whole conversation, a long agent run re-reads the same system prompt and tool definitions dozens of times. Prompt caching makes that stable prefix nearly free — but it is a prefix match, so one changed byte early in the request invalidates everything after it.

i

The order rendered is tools, then system, then messages. Keep everything stable at the front and everything volatile at the back. A timestamp in the system prompt, an unsorted JSON blob, or a tool list you rebuild per request will each silently drop your hit rate to zero. Check usage.cache_read_input_tokens — if it stays at zero across repeated calls, something up front is changing.

A folder structure that survives contact

Agent code sprawls faster than ordinary code, because prompts, tool implementations, schemas and evaluation data all want to live somewhere and none of them are obviously “source”. This layout has one rule behind it: anything you would want to diff in a review gets its own file.

i

Why prompts are files and not string literals. A prompt is the highest-leverage, most-frequently-edited artefact in the whole system. As a .md file it gets reviewed, blamed, and reverted like anything else. Buried in a template literal three levels deep, it gets edited by whoever is nearest and nobody notices the regression for a week.

Real worldWhy tools/index.ts is a single registry

Assembling the tool array in one place sounds like bureaucracy until the first incident. When the tool list is built inline at three different call sites, nobody can answer “what could this agent actually do at 4pm on Tuesday?” — and that is precisely the question a security review, a bug report and an audit all ask.

It also protects your cache. The tool block is rendered first, so a tool list assembled in a different order per request invalidates the cached prefix on every single call. One registry, one order, one cache.

Keeping it on a leash

An agent is a loop with a model in it. Loops need exit conditions, and a model is not one.

ControlWhat it stopsSensible default
Iteration capA model that keeps calling tools forever, usually because a tool keeps failing in the same way.10–20 steps. If real work needs more, raise it deliberately — do not remove it.
Cost budgetThe bill. A single stuck agent can spend real money overnight before anybody looks.Track tokens per run; abort past a threshold and alert.
Wall-clock timeoutA run nobody is waiting for any more.Match it to the user’s patience, not the task’s ambition.
Approval gatesIrreversible actions taken on a bad instruction.Every action that spends money, sends a message, or deletes data.
Effort settingPaying for deep reasoning on routine work.high for the main loop; low for sub-tasks and classification.
!

An approval gate that always says yes is not a gate. If a human is asked to confirm forty times a run, they will click through all forty without reading. Gate the few actions that genuinely matter and let the rest run — a gate people actually read is worth more than a gate on everything.

Where agents actually go wrong

SymptomUsual causeFix
It loops on the same tool call.The tool returns an error the model cannot act on — often a bare stack trace or an empty result with no explanation.Return errors as sentences: what failed, and what to try instead. Cap iterations regardless.
It picks the wrong tool.Two tools with overlapping descriptions, or a description that says what the tool is rather than when to use it.Rewrite the descriptions to say when not to use each. Merge tools that overlap.

An agent that summarises support tickets starts taking 40 seconds and costing five times what it did last month. Nothing in the prompt changed. Where do you look first?Answer

At usage.cache_read_input_tokens, and at what sits in front of the request. The prompt did not change, but something in the cached prefix probably did — a tool list now assembled in a non-deterministic order, a “today is…” line in the system prompt, a retrieved-context block that moved above the stable content. The cost jump is the tell: you are paying full price for a prefix you used to get at a discount.

Latency confirms it. A cache miss means the whole prefix is processed from scratch on every call. Look at the request shape before you look at the model.

Building one on this stack

Nothing here needs a framework. The pieces map onto what notes 03 and 04 already covered.

The loop belongs on the server

An agent loop in the browser ships your API key to a stranger. It runs in Express, behind auth, exactly like any other route that touches money.

Tools are just functions you already have

Your existing service functions are the tools. Wrap them with a schema and a description; do not write a second implementation for the agent.

Long runs outlive the request

An agent that takes two minutes cannot live inside an HTTP handler. Start a job, return an id, stream progress — the same shape as any long task.

Traces are rows

You already have Postgres. One row per step, indexed by run id, is a better observability story than most purpose-built tools give you.

▶
Practice

Build the smallest real agent: two tools — list_files and read_file, both scoped to one directory — and the task “find where X is configured in this project and explain it”. Cap it at eight steps.

Then break it deliberately. Make read_file throw on one path and watch what the model does with the error. Change the error message from a stack trace to a sentence and watch it recover instead. That single experiment teaches more about tool design than any amount of reading.

Finally, log every step to a file and read the trace end to end. You will find at least one step you did not expect.

✓ Worth remembering
  • An agent is a loop where the model chooses the next step. If you can draw the flowchart, write the flowchart instead.
  • The model never executes anything — it asks. Everything you can control sits between the asking and the doing.
  • Your tool descriptions are your real prompt. Say when not to use each tool, not just what it does.
  • Send all results from one turn back in a single user message, and never drop a failed one — mark it is_error.
  • Iteration cap, cost budget, approval gates. An agent without exit conditions is an outage waiting for a quiet weekend.
  • Prompts are files. Tools are files. Evals live next to them. Anything worth reviewing gets a diff.
