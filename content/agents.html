What an agent actually is

The word has been stretched until it means almost nothing. Take the marketing away and an agent is one specific thing: a loop where a model decides what to do next, your code does it, and the result goes back into the model's context — repeating until the model says it has finished.

💡
In plain English

A normal API call is like a vending machine: put a prompt in, an answer comes out, done. An agent is more like hiring a contractor to renovate your kitchen. You describe what you want at the end, they decide the steps, they keep asking you for tools and materials as they go, and they tell you when it is finished. You do not know in advance how many trips to the hardware shop it will take.

That last point is the whole difference. In a workflow you know the steps and you write them down. In an agent the model chooses the steps while it is running, which is powerful exactly when the steps cannot be known in advance — and careless when they can.

!

Most things called agents should not be agents. If you can draw the flowchart, write the flowchart. An agent costs more, takes longer, fails in more ways, and is much harder to test than the same thing done as a chain of ordinary calls. Reach for one only when the flowchart genuinely cannot be drawn.

The ladder: start at the bottom

💡
In plain English
There is a ladder from "ask the model once" up to "let the model decide what to do next, again and again". Every step up buys you more ability and costs you predictability. The discipline is to start at the bottom and climb only when the step you are standing on has clearly failed at the real job — not when the one above sounds more impressive.

There are four steps between "one API call" and "an agent". Each one is cheaper, faster and easier to think about than the one above it. Climb only when the step you are on genuinely cannot do the job.

Four questions before you build an agent

Is it genuinely complex?

Is the task really hard to write down in advance? "Turn this design document into a pull request" qualifies. "Pull the title out of this PDF" does not.

Is it worth it?

Does the result justify several times the cost and waiting time of a single call? An agent that saves ten minutes of your time is worth it; one that saves ten seconds is not.

Can the model do it?

Is the model actually good at this kind of task today? Test it on twenty real cases before you build a whole system around the answer.

What does a mistake cost?

Can a mistake be caught and undone — by tests, a review, a rollback? An agent that can send money or delete rows with no gate is a liability, not a feature.

A "no" to any one of those means stay on a lower step.

Five workflow patterns worth knowing by name

💡
In plain English
A workflow is a route you drew on the map; an agent is a route the model works out as it drives. Most problems people describe as needing an agent have a set of steps that is perfectly well known in advance — which means a workflow will be cheaper, faster, testable branch by branch, and far easier to debug at 3am.

Step three covers far more ground than people expect. These five shapes solve most of what people reach for an agent to solve, and every one of them is ordinary code you can unit-test.

PatternShapeUse it when
Prompt chainingThe output of call A becomes the input of call B, with a check in between.The task splits cleanly into fixed steps. Outline → draft → polish. Extract → check → store.
RoutingA cheap sorter decides which special prompt or model handles the input.Inputs fall into clearly different types that want different handling. Refund vs technical vs sales, each with its own prompt and its own model tier.
ParallelisationRun several calls at the same time, then combine. Either the same task voted on, or different sub-tasks joined together.Speed matters and the pieces do not depend on each other. Or you want three opinions on a judgement call and a majority vote.
Orchestrator–workerOne call plans the sub-tasks, workers do them, one call puts the results together.You only find out how many sub-tasks there are once you have looked at the input. Searching six sources; editing whichever files a change happens to touch.
Evaluator–optimiserWrite, criticise against clear criteria, revise. Loop with a hard limit.Quality can be judged and revising genuinely helps — translation, code that must pass tests, writing against a marking scheme.
i

Routing pays for itself faster than any other pattern. A small model sorting incoming messages, and only sending the hard ones up to a capable model, usually cuts most of the bill while improving quality on the narrow cases — a focused prompt beats a general one.

tsrouting: cheap triage, expensive handling only where it is needed
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

// Step one: a small model decides where this goes. Cheap, called on everything.
async function route(message: string) {
  const res = await client.messages.create({
    model: 'claude-haiku-4-5',
    max_tokens: 16,
    system: 'Classify the support message. Reply with exactly one word: billing, technical, or other.',
    messages: [{ role: 'user', content: message }],
  });
  const text = res.content.find((b) => b.type === 'text');
  return text?.text.trim().toLowerCase() ?? 'other';
}

// Step two: the specialist. A focused prompt, and only the hard lane pays for
// the capable model.
const LANES = {
  billing:   { model: 'claude-haiku-4-5', system: 'You answer billing questions. Cite the invoice number.' },
  technical: { model: 'claude-opus-5',    system: 'You debug technical problems. Ask for logs before guessing.' },
  other:     { model: 'claude-haiku-4-5', system: 'You triage. Summarise the request in one sentence.' },
} as const;

export async function handle(message: string) {
  const lane = LANES[await route(message) as keyof typeof LANES] ?? LANES.other;
  return client.messages.create({
    model: lane.model,
    max_tokens: 16000,
    thinking: { type: 'adaptive' },
    system: lane.system,
    messages: [{ role: 'user', content: message }],
  });
}
“Read the support email, decide if it is billing or technical, and reply using the right template.” Agent or workflow?Answer

Workflow. You know every step before the email even arrives: sort it, then branch, then write the reply. Nothing needs planning, so nothing needs an agent.

The sign that you genuinely need an agent is different: you cannot write down the steps because they depend on what gets discovered halfway through — as in "find out why this customer was charged twice", where every answer changes what you look at next.

The agent loop, drawn

Every agent framework you will ever read about is this one loop with decoration on top. Understand it once and you can read all of them.

i

The model cannot do anything. It sends out a request — a name and some JSON. Your code decides whether that request runs. Every piece of agent security follows from taking that one sentence seriously.

tsthe loop, written by hand, so you have seen it once
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();
const MAX_STEPS = 12;   // never ship an agent without this

let messages: Anthropic.MessageParam[] = [{ role: 'user', content: task }];

for (let step = 0; step < MAX_STEPS; step++) {
  const res = await client.messages.create({
    model: 'claude-opus-5',
    max_tokens: 16000,
    thinking: { type: 'adaptive' },
    tools,
    messages,
  });

  if (res.stop_reason === 'end_turn') return res;

  // A tool running on the provider's side hit its own limit. Hand the turn
  // back and carry on; do not add a "please continue" message, because the
  // API picks up again on its own.
  if (res.stop_reason === 'pause_turn') {
    messages.push({ role: 'assistant', content: res.content });
    continue;
  }

  messages.push({ role: 'assistant', content: res.content });

  const calls = res.content.filter(
    (b): b is Anthropic.ToolUseBlock => b.type === 'tool_use',
  );

  // All the results go back in ONE user message. Splitting them across
  // several messages quietly teaches the model to stop asking for tools
  // in parallel.
  const results: Anthropic.ToolResultBlockParam[] = [];
  for (const call of calls) {
    try {
      results.push({
        type: 'tool_result',
        tool_use_id: call.id,
        content: await runTool(call.name, call.input),
      });
    } catch (err) {
      // Send the failure back as a result. Never drop it — a tool_use with
      // no matching tool_result is a broken conversation.
      results.push({
        type: 'tool_result',
        tool_use_id: call.id,
        content: String(err),
        is_error: true,
      });
    }
  }

  messages.push({ role: 'user', content: results });
}

throw new Error(`Agent did not finish within ${MAX_STEPS} steps`);
💡
In plain English

You have now seen the whole machine. In practice you would use the SDK's tool runner, which writes this loop for you and still lets you step in on each turn — but knowing what it is doing underneath is the difference between debugging an agent and restarting it and hoping for the best.

Your agent asks for three tools at once. You run them and send back three separate user messages, one result each. What breaks?Answer

Two things. First, the conversation is malformed: the API expects every tool_use in one assistant turn to be answered by tool_result blocks in one following user message. Second — and this is the one that bites you quietly — even where it is allowed, you are showing the model that parallel calls get handled one at a time, so it stops asking for them. Your agent gets slower over the course of a conversation and you will never find it in a log.

Designing the set of tools

💡
In plain English
Designing tools is like designing an API for a reader who cannot ask you a single question. The name and the description are the entire manual, and they are what the model uses to decide when to pick it up. A vague description gives you a tool that gets called at the wrong moment, and no amount of prompt tuning elsewhere will fix that.

The tools you offer are your agent's design. A vague set of tools produces a confused agent that no prompt can rescue, and the most common cause of a bad agent is not the model — it is fifteen overlapping tools with descriptions written as an afterthought.

Write the description for a capable new colleague

The description is not documentation, it is the instruction the model actually follows. It should say what the tool does, when to reach for it, when not to, and what it gives back.

Not this · the name said twice
{
  name: 'search',
  description: 'Searches.',
  input_schema: {
    type: 'object',
    properties: { q: { type: 'string' } },
  },
}
Do this · when, when not, and what comes back
{
  name: 'search_invoices',
  description:
    'Full-text search over invoice line items for ONE customer. ' +
    'Use when the user names a product or description but not an ' +
    'invoice number. Do not use to fetch a known invoice — use ' +
    'get_invoice, which is exact and cheaper. Returns at most 20 ' +
    'matches, newest first, each with number, date and total.',
  input_schema: {
    type: 'object',
    properties: {
      customer_id: { type: 'string', description: 'Customer UUID.' },
      query: { type: 'string', description: 'Words to match in line items.' },
    },
    required: ['customer_id', 'query'],
    additionalProperties: false,
  },
  strict: true,
}

Broad tool or specific tool?

One run_sql tool can do anything that a hundred narrow tools can do. That reach is exactly the problem: your code sees one opaque string and cannot tell a harmless SELECT from a DROP TABLE. Turning an action into its own tool gives your code a proper, typed place to gate it, log it, show it in the UI, and run several at once.

Give it its own tool when…Why one broad tool fails there
It crosses a security line, or cannot be undone.send_email is easy to put behind a confirmation. bash("curl -X POST ...") is not.
A rule has to be enforced.An edit_file tool can refuse a write if the file changed since the model last read it. A shell command cannot.
It should appear as something in your UI.A question to the user deserves its own tool, so it can appear as a popup and hold the loop until somebody answers.
It is safe to run several at once.Your code can safely run five read_file calls together. It cannot know whether five shell commands are safe to mix.

The rule of thumb: start broad so it can actually do things, then give an action its own tool the moment you need to gate it, show it, audit it, or run several in parallel.

Context over a long run

💡
In plain English
An agent that runs for twenty steps collects twenty steps of history, and there is a hard limit on how much it can hold. So you have to decide what to keep, what to summarise and what to throw away — and doing that badly is why long runs get slower, costlier and more confused as they go on.

An agent that runs for forty steps has a problem a single call never has: the transcript grows on every turn, you pay for all of it on every request, and eventually it stops fitting. Three different mechanisms solve three different versions of that problem, and people mix them up all the time.

Context editing

Trims. Clears out stale tool results and old thinking blocks from the transcript. Inside one session. Use it when the history is full of big results nobody needs any more.

Compaction

Summarises. Squeezes earlier context into a summary block as you approach the window limit. Inside one session. Use it for conversations that genuinely run long.

Memory

Keeps. Files the agent reads and writes that outlive the process. Across sessions. Use it when tomorrow's run needs to know what today's run learned.

!

Compaction has one rule that is easy to miss. Push the whole response.content back onto your messages each turn, not just the text you pulled out of it. The compaction blocks inside that response are what the API uses to replace the squeezed-down history on the next request — take out only the text string and you quietly lose the compaction state, and the context starts growing again with no error to warn you.

Caching is the other half of the cost story

Because every request re-sends the whole conversation, a long agent run re-reads the same system prompt and tool definitions dozens of times. Prompt caching makes that unchanging opening block nearly free — but it matches on an exact opening block, so one changed byte early in the request throws away everything after it.

i

The order sent is tools, then system, then messages. Keep everything unchanging at the front and everything that varies at the back. A timestamp in the system prompt, an unsorted JSON blob, or a tool list you rebuild in a different order each request will each quietly drop your cache hit rate to zero. Check usage.cache_read_input_tokens — if it stays at zero across repeated calls, something up front is changing.

A folder structure that survives real use

💡
In plain English
Agent code turns into one giant function faster than most code, because everything really is connected to everything. Splitting the loop, the tools, the prompts and the limits into their own places is what keeps it possible to change one without breaking the others.

Agent code spreads faster than ordinary code, because prompts, tool code, schemas and test data all want a home and none of them are obviously "source code". This layout has one rule behind it: anything you would want to see in a code review gets its own file.

i

Why prompts are files and not strings inside the code. A prompt is the highest-value, most-often-edited thing in the whole system. As a .md file it gets reviewed, blamed and reverted like anything else. Buried in a template string three levels deep, it gets edited by whoever is nearest and nobody notices the damage for a week.

Real worldWhy tools/index.ts is one single registry

Building the tool list in one place sounds like unnecessary paperwork until your first incident. When the tool list is assembled inline at three different places in the code, nobody can answer "what could this agent actually do at 4pm on Tuesday?" — and that is exactly the question a security review, a bug report and an audit all ask.

It also protects your cache. The tool block is sent first, so a tool list assembled in a different order on each request throws away the cached opening block on every single call. One registry, one order, one cache.

Keeping it on a leash

💡
In plain English
An agent decides its own steps, which means that without limits it can loop forever, spend without any ceiling, or take an action nobody approved. The leash is not one thing: a limit on steps, a limit on spending, a list of what it may touch, and a human approval on anything that cannot be undone. Every one of them will one day be the one that saves you.

An agent is a loop with a model inside it. Loops need a way to stop, and a model is not one.

ControlWhat it stopsSensible default
Step limitA model that keeps calling tools forever, usually because a tool keeps failing in the same way.10–20 steps. If real work needs more, raise it on purpose — do not remove it.
Cost budgetThe bill. One stuck agent can spend real money overnight before anybody looks.Track tokens per run; stop past a limit and raise an alert.
Clock timeoutA run that nobody is waiting for any more.Match it to the user's patience, not to how ambitious the task is.
Approval gatesOne-way actions taken on a bad instruction.Every action that spends money, sends a message, or deletes data.
Effort settingPaying for deep thinking on routine work.high for the main loop; low for sub-tasks and sorting.
!

An approval gate that always gets a yes is not a gate. If a person is asked to confirm forty times in one run, they will click through all forty without reading a word. Put a gate on the few actions that genuinely matter and let the rest run — a gate people actually read is worth far more than a gate on everything.

Why do you need a maximum-steps limit even when your agent has always finished in four steps?Answer

Because "always" only describes the inputs you have tried so far. One badly formed document, one tool that keeps returning an error the model keeps trying to work around, and the loop has no natural end — it will keep going as long as you let it, spending real money.

The limit costs you nothing on the normal path and puts a ceiling on your worst case. That is the best deal available anywhere in this subject.

Where agents actually go wrong

💡
In plain English
Agents fail in ways you can recognise once you have seen them: looping on a tool that keeps failing, losing the thread over a long run, confidently taking a wrong action, or being handed tools so broad that nothing can hold them back. Each one has a specific fix, and none of those fixes is "write a better prompt".
SymptomUsual causeFix
It calls the same tool over and over.The tool returns an error the model cannot act on — often a bare stack trace, or an empty result with no explanation.Return errors as sentences: what failed, and what to try instead. Cap the steps anyway.
It picks the wrong tool.Two tools with overlapping descriptions, or a description that says what the tool is rather than when to use it.Rewrite the descriptions to say when not to use each one. Merge tools that overlap.
It gets slower every turn.The transcript keeps growing and nothing trims it. Big tool results make it worse.Trim tool results at the source, then add context editing or compaction.
It works in testing and fails in production.Your test inputs were tidy. Real inputs contain other people's text — and other people's instructions.See note 12. Treat every tool result as untrusted input, not just the user's messages.
The bill is far bigger than expected.Cache hit rate near zero, the capable model on every step, no routing.Check cache_read_input_tokens first — it is usually an opening block that keeps changing. Then add routing.
Nobody can say why it did that.No trace. Logging the final answer tells you nothing about a twelve-step run.One structured record per step: model, input, tool, result, tokens, decision.
An agent that summarises support tickets suddenly takes 40 seconds and costs five times what it did last month. Nothing in the prompt changed. Where do you look first?Answer

At usage.cache_read_input_tokens, and at whatever sits at the front of the request. The prompt did not change, but something in the cached opening block probably did — a tool list now assembled in a different order each time, a "today is..." line in the system prompt, a block of fetched context that moved above the unchanging part. The jump in cost is the giveaway: you are paying full price for an opening block you used to get at a discount.

The slowness confirms it. A cache miss means the whole opening block is processed from scratch on every call. Look at the shape of the request before you start looking at the model.

Building one on this stack

💡
In plain English
What building one on this stack actually looks like — where the loop lives, where the tools live, and what the limits are set to.

Nothing here needs a framework. The pieces map onto what notes 03 and 04 already covered.

The loop belongs on the server

An agent loop running in the browser hands your API key to a stranger. It runs in Express, behind your login check, exactly like any other route that touches money.

Tools are just functions you already have

Your existing service functions are the tools. Wrap them with a schema and a description; do not write a second copy just for the agent.

Long runs outlive the request

An agent that takes two minutes cannot live inside an HTTP handler. Start a job, return an id, stream the progress — the same shape as any other long task.

Traces are just rows

You already have Postgres. One row per step, indexed by run id, gives you a better view of what happened than most purpose-built tools do.

▶
Practice

Build the smallest real agent you can: two tools — list_files and read_file, both limited to one folder — and the task "find where X is configured in this project and explain it". Cap it at eight steps.

Then break it on purpose. Make read_file throw an error on one path and watch what the model does with that error. Change the error message from a stack trace into a plain sentence and watch it recover instead. That single experiment teaches more about tool design than any amount of reading.

Finally, log every step to a file and read the whole trace from start to finish. You will find at least one step you did not expect.

✓ Worth remembering
  • An agent is a loop where the model chooses the next step. If you can draw the flowchart, write the flowchart instead.
  • The model never runs anything — it asks. Everything you can control sits between the asking and the doing.
  • Your tool descriptions are your real prompt. Say when not to use each tool, not only what it does.
  • Send all the results from one turn back in a single user message, and never drop a failed one — mark it is_error.
  • Step limit, cost budget, approval gates. An agent with no way to stop is an outage waiting for a quiet weekend.
  • Prompts are files. Tools are files. Tests live next to them. Anything worth reviewing gets its own diff.
