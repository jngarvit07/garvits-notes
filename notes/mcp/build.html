Building a server

2 min read Some experience helps
💡
In plain English
Building a server is smaller than it sounds. You declare what your tools are called, what arguments they take and what they do, then write an ordinary function for each. The protocol handles the conversation; you are really just writing well-described functions.

Smaller than you think. This is a complete, working stdio server exposing two tools over your existing Prisma database.

tsmcp/invoices/src/index.ts — a whole server
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';
import { prisma } from './db.js';

const server = new McpServer({ name: 'invoices', version: '1.0.0' });

// A precise, exact lookup. Cheap, and the one the model should prefer.
server.registerTool(
  'get_invoice',
  {
    title: 'Get invoice',
    description:
      'Fetch ONE invoice by its exact number, e.g. INV-2043. ' +
      'Use this whenever the number is known — it is exact and cheap. ' +
      'For vaguer requests use search_invoices instead.',
    inputSchema: { number: z.string().describe('Invoice number, e.g. INV-2043') },
  },
  async ({ number }) => {
    const invoice = await prisma.invoice.findUnique({ where: { number } });

    if (!invoice) {
      // Errors are content, not exceptions. Say what to do next — the model
      // reads this and acts on it.
      return {
        content: [{ type: 'text', text: `No invoice numbered ${number}. Try search_invoices.` }],
        isError: true,
      };
    }

    return { content: [{ type: 'text', text: JSON.stringify(invoice, null, 2) }] };
  },
);

// The fuzzy one. Bounded on purpose: an unbounded result set is how you fill
// a context window with rows nobody reads.
server.registerTool(
  'search_invoices',
  {
    title: 'Search invoices',
    description:
      'Full-text search over invoice line items for one customer. ' +
      'Use when the user describes a product but has no invoice number. ' +
      'Returns at most 20 matches, newest first.',
    inputSchema: {
      customerId: z.string().uuid().describe('Customer UUID'),
      query: z.string().min(2).describe('Words to match in line items'),
    },
  },
  async ({ customerId, query }) => {
    const rows = await prisma.invoice.findMany({
      where: { customerId, lineItems: { some: { description: { contains: query, mode: 'insensitive' } } } },
      orderBy: { issuedAt: 'desc' },
      take: 20,
      select: { number: true, issuedAt: true, totalCents: true },
    });

    return {
      content: [{
        type: 'text',
        text: rows.length
          ? JSON.stringify(rows, null, 2)
          : `No invoices for that customer matching "${query}".`,
      }],
    };
  },
);

// stdout is the protocol. Diagnostics go to stderr or they corrupt it.
console.error('invoices MCP server ready');

await server.connect(new StdioServerTransport());

The SDK’s exact registration API has changed once or twice as MCP has matured — older examples use server.tool(...). Check the version you have installed rather than trusting any snippet, this one included. The shape is stable: a name, a description, a schema, and an async function returning content.

Why does get_invoice return isError: true with a sentence, instead of throwing?Answer

Because the model is the one reading it. A thrown exception becomes a transport-level failure the model cannot interpret and often retries verbatim, producing the same failure again. An error result arrives in context as text, so the model can read “no invoice with that number, try search_invoices” and do exactly that.

The general rule from note 07 holds here: a tool failure is a normal outcome that must be described, not an exception to be propagated.
