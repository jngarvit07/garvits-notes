Context over a long run

2 min read Some experience helps
💡
In plain English
An agent that runs for twenty steps accumulates twenty steps of history, and there is a hard limit on how much it can hold. So you have to decide what to keep, what to summarise and what to throw away — and doing that badly is why long runs get slower, more expensive and confused as they go.

An agent that runs for forty steps has a problem a single call never has: the transcript grows on every turn, you pay for all of it on every request, and eventually it does not fit. Three different mechanisms address three different versions of that problem, and they are routinely confused.

Context editing

Prunes. Clears stale tool results and old thinking blocks out of the transcript. Within one session. Use when the history is full of large results nobody needs any more.

Compaction

Summarises. Condenses earlier context into a summary block when you approach the window limit. Within one session. Use for conversations that genuinely run long.

Memory

Persists. Files the agent reads and writes that outlive the process. Across sessions. Use when tomorrow’s run needs to know what today’s learned.

!

Compaction has one non-obvious rule. Append the whole response.content back onto your messages each turn, not just the extracted text. The compaction blocks in the response are what the API uses to replace the compacted history on the next request — pull out only the text string and you silently lose the compaction state, and the context starts growing again with no error to tell you.

Caching is the other half of the cost story

Because every request resends the whole conversation, a long agent run re-reads the same system prompt and tool definitions dozens of times. Prompt caching makes that stable prefix nearly free — but it is a prefix match, so one changed byte early in the request invalidates everything after it.

i

The order rendered is tools, then system, then messages. Keep everything stable at the front and everything volatile at the back. A timestamp in the system prompt, an unsorted JSON blob, or a tool list you rebuild per request will each silently drop your hit rate to zero. Check usage.cache_read_input_tokens — if it stays at zero across repeated calls, something up front is changing.
