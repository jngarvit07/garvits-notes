Designing the tool surface

2 min read Some experience helps
💡
In plain English
Tool design is API design for a reader who cannot ask you a question. The name and description are the entire documentation, and they are what the model uses to decide when to reach for it. A vague description produces a tool called at the wrong moment, and no amount of prompt tuning elsewhere fixes that.

The tools you expose are your agent’s design. A vague tool set produces a confused agent no prompt can rescue, and the most common cause of a bad agent is not the model — it is fifteen overlapping tools with descriptions written as an afterthought.

Write the description for a competent new colleague

The description is not documentation, it is the instruction the model actually follows. It should say what the tool does, when to reach for it, when not to, and what it returns.

Not this · a name restated
{
  name: 'search',
  description: 'Searches.',
  input_schema: {
    type: 'object',
    properties: { q: { type: 'string' } },
  },
}
Do this · when, when not, and what comes back
{
  name: 'search_invoices',
  description:
    'Full-text search over invoice line items for ONE customer. ' +
    'Use when the user names a product or description but not an ' +
    'invoice number. Do not use to fetch a known invoice — use ' +
    'get_invoice, which is exact and cheaper. Returns at most 20 ' +
    'matches, newest first, each with number, date and total.',
  input_schema: {
    type: 'object',
    properties: {
      customer_id: { type: 'string', description: 'Customer UUID.' },
      query: { type: 'string', description: 'Words to match in line items.' },
    },
    required: ['customer_id', 'query'],
    additionalProperties: false,
  },
  strict: true,
}

Broad tool or specific tool?

One run_sql tool can do anything a hundred narrow tools can. That breadth is exactly the problem: your harness sees an opaque string and cannot tell a harmless SELECT from a DROP TABLE. Promoting an action to its own tool gives your code a typed hook it can gate, log, render and parallelise.

Promote it to a dedicated tool when…Why breadth fails there
It crosses a security boundary or is hard to reverse.send_email is trivial to gate behind a confirmation. bash("curl -X POST ...") is not.
It needs an invariant enforced.An edit_file tool can refuse a write if the file changed since the model last read it. A shell command cannot.
It should render as something in your UI.A question to the user is worth its own tool so it can appear as a modal and block the loop until answered.
It is safe to run in parallel.Your harness can run five read_file calls at once. It cannot know whether five shell commands are safe to interleave.

The rule of thumb: start broad for reach, promote to specific tools the moment you need to gate, render, audit or parallelise.
