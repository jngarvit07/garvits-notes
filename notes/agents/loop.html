The agent loop, drawn

2 min read Some experience helps

Every agent framework you will ever read about is this loop with decoration on top. Understanding it once means you can read any of them.

i

The model cannot do anything. It emits a request — a name and some JSON. Your code decides whether that request runs. Every piece of agent security follows from taking that sentence seriously.

tsthe loop, by hand, so you have seen it once
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();
const MAX_STEPS = 12;   // never ship an agent without this

let messages: Anthropic.MessageParam[] = [{ role: 'user', content: task }];

for (let step = 0; step < MAX_STEPS; step++) {
  const res = await client.messages.create({
    model: 'claude-opus-5',
    max_tokens: 16000,
    thinking: { type: 'adaptive' },
    tools,
    messages,
  });

  if (res.stop_reason === 'end_turn') return res;

  // A server-side tool hit its internal limit. Hand the turn back and continue;
  // do not add a "please continue" message, the API resumes on its own.
  if (res.stop_reason === 'pause_turn') {
    messages.push({ role: 'assistant', content: res.content });
    continue;
  }

  messages.push({ role: 'assistant', content: res.content });

  const calls = res.content.filter(
    (b): b is Anthropic.ToolUseBlock => b.type === 'tool_use',
  );

  // All results go back in ONE user message. Splitting them across several
  // messages quietly teaches the model to stop asking for tools in parallel.
  const results: Anthropic.ToolResultBlockParam[] = [];
  for (const call of calls) {
    try {
      results.push({
        type: 'tool_result',
        tool_use_id: call.id,
        content: await runTool(call.name, call.input),
      });
    } catch (err) {
      // Return the failure as a result. Never drop it — a missing tool_result
      // for a requested tool_use is a malformed conversation.
      results.push({
        type: 'tool_result',
        tool_use_id: call.id,
        content: String(err),
        is_error: true,
      });
    }
  }

  messages.push({ role: 'user', content: results });
}

throw new Error(`Agent did not finish within ${MAX_STEPS} steps`);
💡
In plain English

You have now seen the entire mechanism. In practice you would use the SDK’s tool runner, which writes this loop for you and still lets you intervene each turn — but knowing what it is doing underneath is the difference between debugging an agent and rebooting it and hoping.

Your agent asks for three tools at once. You run them and send back three separate user messages, one result each. What breaks?Answer

Two things. First, the conversation is malformed: the API expects every tool_use in one assistant turn to be answered by tool_result blocks in one following user message. Second — and this is the one that bites quietly — even where it is tolerated, you are demonstrating to the model that parallel calls get handled serially, and it stops requesting them. Your agent gets slower over the course of a conversation and you will not find it in a log.
