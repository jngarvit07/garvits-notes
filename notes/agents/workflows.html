Five workflow patterns worth knowing by name

2 min read Some experience helps
💡
In plain English
A workflow is a route you drew; an agent is a route the model chooses. Most problems people describe as needing an agent have a sequence of steps that is perfectly well known in advance — which means a workflow will be cheaper, faster, testable per branch, and far easier to debug at 3am.

Rung three covers more ground than people expect. These five shapes solve most of what gets reached for an agent to solve, and every one of them is ordinary code you can unit-test.

PatternShapeUse it when
Prompt chainingOutput of call A becomes input of call B, with a check in between.The task decomposes cleanly into fixed steps. Outline → draft → polish. Extract → validate → store.
RoutingA cheap classifier picks which specialised prompt or model handles the input.Inputs fall into distinct categories that want different handling. Refund vs. technical vs. sales, each with its own prompt and its own model tier.
ParallelisationRun several calls at once, then combine. Either the same task voted on, or different subtasks joined.Latency matters and the pieces are independent. Or you want three opinions on a judgement call and a majority vote.
Orchestrator–workerOne call plans the subtasks, workers do them, one call synthesises.The number of subtasks is only known once you have looked at the input. Searching six sources; editing the files a change happens to touch.
Evaluator–optimiserGenerate, critique against explicit criteria, revise. Loop with a hard cap.Quality is judgeable and revision genuinely helps — translation, code that must pass tests, writing with a rubric.
i

Routing pays for itself faster than any other pattern. A small model classifying inbound messages, then only escalating the hard ones to a capable model, typically cuts the bill by most of it while improving quality on the narrow cases — a focused prompt beats a general one.

tsrouting: cheap triage, expensive handling, only where needed
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

// Step one: a small model decides where this goes. Cheap, called on everything.
async function route(message: string) {
  const res = await client.messages.create({
    model: 'claude-haiku-4-5',
    max_tokens: 16,
    system: 'Classify the support message. Reply with exactly one word: billing, technical, or other.',
    messages: [{ role: 'user', content: message }],
  });
  const text = res.content.find((b) => b.type === 'text');
  return text?.text.trim().toLowerCase() ?? 'other';
}

// Step two: the specialist. A focused prompt, and only the hard lane pays for
// the capable model.
const LANES = {
  billing:   { model: 'claude-haiku-4-5', system: 'You answer billing questions. Cite the invoice number.' },
  technical: { model: 'claude-opus-5',    system: 'You debug technical problems. Ask for logs before guessing.' },
  other:     { model: 'claude-haiku-4-5', system: 'You triage. Summarise the request in one sentence.' },
} as const;

export async function handle(message: string) {
  const lane = LANES[await route(message) as keyof typeof LANES] ?? LANES.other;
  return client.messages.create({
    model: lane.model,
    max_tokens: 16000,
    thinking: { type: 'adaptive' },
    system: lane.system,
    messages: [{ role: 'user', content: message }],
  });
}
“Read the support email, decide if it is billing or technical, and reply using the right template.” Agent or workflow?Answer

Workflow. You know every step before the email arrives: classify, then branch, then generate. Nothing needs planning, so nothing needs an agent.

The signal that you genuinely need an agent is different: you cannot write down the steps because they depend on what is discovered partway through — as in “find out why this customer was double-charged”, where each answer changes what to look at next.
