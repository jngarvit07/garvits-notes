Note 11

Evaluating AI Systems

Building a set of real cases, four kinds of grader and when to use each, making an LLM judge trustworthy, scoring RAG and agents, and wiring the whole thing into CI.

Some experience helps 35 min read 5 sections

Why you cannot ship without this

Ordinary code is deterministic: the same input gives the same output, so a test that passed yesterday means something today. A model gives you a distribution of outputs, and the distribution shifts when you change the prompt, the model version, the retrieval, or nothing at all.

💡
In plain English

Testing normal code is checking a calculator: 2 + 2 must be 4 every time. Testing a model is closer to marking exam papers — you cannot check for one exact string, you have to decide whether an answer is good, and you need enough papers that one lucky guess does not fool you.

An eval is that marking scheme, automated: a set of real inputs, a definition of a good outcome, and a score you can watch over time.

!

Without evals you are not engineering, you are gambling. Every prompt change becomes a vibe check on three examples somebody remembers. The regression you introduce on the fourth case ships, and you find out from a customer six weeks later — if at all.

What evals actually catch

ChangeWhat goes wrong without an eval set
You improve the prompt.It gets better on the case you were looking at and worse on two you were not. Nobody notices.
The model version updates.Behaviour your prompt quietly depended on changes. A newer model is better on average and not identical.
You switch to a cheaper model.You have no way to know whether the saving cost you anything, so you either never try it or try it blind.
You change chunking or retrieval.Answers get subtly less grounded. Nothing errors. Quality drifts down for a month.
Someone edits a tool description.The agent starts choosing the wrong tool in a class of cases nobody tests by hand.

Building the set — the part that matters

Almost all the value is here, and almost all the effort goes to the wrong place: people build elaborate scoring machinery on top of twelve examples they invented at their desk.

i

Your eval set is a real asset. Prompts get rewritten, models get replaced, frameworks come and go. The set of real cases with agreed-correct outcomes is the thing that stays valuable and gets more valuable every month. Keep it in the repository, next to the code it tests.

How to score an answer

Four kinds of grader, cheapest and most reliable first. Use the simplest one that can actually judge your task — and use several together, because most tasks have both a checkable part and a judgeable part.

GraderHow it worksGood forWatch out
Exact / structuralString match, JSON schema validation, a regex.Classification, extraction, routing, anything with one right answer.Nothing — use it wherever it applies. It is free and it never lies.
ProgrammaticCode that checks properties: does it parse, does it cite, is every cited id real, is it under the length limit.Grounding, format compliance, safety rules, anything expressible as an assertion.Only checks what you thought to check.
LLM-as-judgeA model scores the answer against a written rubric.Tone, helpfulness, reasoning quality — the genuinely subjective parts.Biased, and noisier than people expect. See below.
HumanA person reads and marks.Calibrating the other three. The ground truth everything else approximates.Slow and expensive — so spend it on calibration, not on volume.
!

Reach for the judge last, not first. “Have a model grade it” feels like the general solution, so it gets used for things a three-line assertion would check exactly. If the requirement is “returns valid JSON with these five fields”, that is JSON.parse and a schema, not a judgement call.

Making an LLM judge trustworthy

Write a real rubric

“Rate helpfulness 1–10” produces noise. Define what each score means, in sentences, with an example of the boundary between adjacent scores.

Prefer binary questions

“Is every factual claim supported by the provided context? Yes or no.” is far more stable than any 1–10 scale, and far easier to act on.

Show the criteria, not the answer key

Given a reference answer, judges drift towards rewarding similarity to it rather than correctness. Different wording is not a failure.

Calibrate against humans

Mark fifty cases by hand and check the judge agrees. If it does not, fix the rubric before trusting a single score it produces.

i

Known judge biases, all measurable: they prefer longer answers, they prefer answers that resemble their own style, and in pairwise comparisons the order you present the two options changes the winner. Randomise the order and check whether the result holds.

Evaluating RAG and agents specifically

RAG: score retrieval and generation separately

This is the single most useful idea in this note. Almost every disappointing RAG system fails at retrieval and gets blamed on the model — and one combined score cannot tell you which half is broken.

StageQuestionHow to score it
RetrievalDid the chunk containing the answer come back at all?Mark the correct chunk id per case; check whether it appears in the top k. Programmatic, exact, no judgement needed.
GroundingIs every claim in the answer supported by what was retrieved?A judge, with the retrieved context in front of it. Binary, per claim.
RefusalWhen the answer genuinely is not in the corpus, does it say so?Cases with no answer, and an exact expected refusal. This one catches the failure that damages trust most.
Answer qualityIs it actually useful to a person?A judge with a rubric — only meaningful once the three above pass.
💡
In plain English

If retrieval scores 60%, no prompt engineering will save you — the answer was never in the room. Fix the search before you touch the wording. Teams routinely spend weeks on the prompt for a retrieval bug.

Agents: score the trajectory, not just the ending

An agent can reach the right answer through twelve wasteful steps, or reach a wrong one having done everything sensibly. Only scoring the final output hides both.

What to measureWhy it matters
Task success — did it achieve the goal?The headline number, but on its own it is not diagnostic.
Steps takenA rising step count is the earliest signal that something in the tool set has become confusing.
Tool choice accuracyDid it pick the right tool at each decision point? This localises the fault to a description you can rewrite.
Tokens and cost per runThe thing that quietly ruins the economics. Track per run, not per request.
Gate hitsHow often it attempted something requiring approval. A sudden rise is worth investigating immediately.

Running them, and running them automatically

tsevals/run.ts — small enough that it actually gets used
import cases from './cases/support-qa.json';
import { answer } from '../src/answer.js';
import { judgeGrounded } from './graders.js';

type Case = {
  id: string;
  question: string;
  expectedChunkId: string | null;   // null = not answerable from the corpus
  mustRefuse?: boolean;
};

const results = [];

for (const c of (cases as Case[])) {
  const out = await answer(c.question);

  // 1. Retrieval — exact, cheap, and the first thing to look at when a score drops.
  const retrieved = c.expectedChunkId === null
    ? true
    : out.chunkIds.includes(c.expectedChunkId);

  // 2. Refusal — does it decline when there is genuinely nothing to say?
  const refusedCorrectly = c.mustRefuse
    ? out.text.includes('I do not have that information')
    : true;

  // 3. Grounding — the only part that needs a model, and only if the rest passed.
  const grounded = retrieved && !c.mustRefuse
    ? await judgeGrounded(out.text, out.context)
    : true;

  results.push({ id: c.id, retrieved, refusedCorrectly, grounded });
}

const rate = (k: keyof (typeof results)[0]) =>
  (results.filter((r) => r[k]).length / results.length * 100).toFixed(0) + '%';

console.log(`retrieval  ${rate('retrieved')}`);
console.log(`refusal    ${rate('refusedCorrectly')}`);
console.log(`grounding  ${rate('grounded')}`);

// Fail the build on a regression. Thresholds are a ratchet: raise them as the
// system improves, never lower them to make a red build go green.
const failed = results.filter((r) => !r.retrieved || !r.grounded || !r.refusedCorrectly);
if (failed.length > 3) {
  console.error(`${failed.length} failures:`, failed.map((f) => f.id).join(', '));
  process.exit(1);
}
i

Run it on every change to a prompt, a model id, or the retrieval pipeline. Those three files are exactly as dangerous as a database migration and get a fraction of the scrutiny. Wiring the eval into CI is what turns “we should test this” into something that actually happens.

!

Evals cost real money to run, because they make real API calls. Keep the CI set small and fast — thirty to fifty cases — and run the large set nightly. An eval suite too expensive to run is an eval suite nobody runs.

Your grounding score is 95% and users still complain the answers are wrong. What is the eval missing?Answer

Most likely retrieval, measured separately. Grounding asks “is the answer supported by the retrieved context?” — an answer can be perfectly grounded in the wrong chunk and score 95% while being useless. High grounding with unhappy users is the classic signature of a retrieval problem hiding behind a generation metric.

The second candidate is missing refusal cases. If your set only contains answerable questions, you have never measured what happens when the corpus has nothing — and confidently inventing an answer there is what destroys trust fastest.

▶
Practice

Take any AI feature you have. Open the logs, pull thirty real inputs, and write down for each what a good answer would be. That is an afternoon, and it is the whole job.

Now run your current system against them and count. Whatever number you get is your real baseline — almost certainly lower than you expected, and now you can improve it deliberately instead of guessing.

✓ Worth remembering
  • Without evals, every prompt change is a gamble and every regression ships silently.
  • Thirty real cases beat three hundred invented ones. Include the ambiguous, the hostile and the unanswerable.
  • Add every reported bug as a case. That habit compounds into your most valuable asset.
  • Use the simplest grader that works. Reach for an LLM judge last, and calibrate it against humans.
  • For RAG, score retrieval and generation separately — one number cannot tell you which half is broken.
  • For agents, score the trajectory: steps, tool choice, cost, gate hits — not only the final answer.
  • Wire it into CI. Prompts and model ids are as dangerous as migrations and get a fraction of the review.
