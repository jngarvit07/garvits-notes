Shipping it: the boring half

3 min read No experience needed
💡
In plain English
The demo is maybe one-fifth of the work. The rest is what happens when the provider is down, when the output is not the shape you asked for, when someone pastes in something nasty, when it is slow, and when you have to explain last Tuesday's answer to a customer. This part decides whether a good demo turns into a good product.

A demo is a prompt that worked once. A feature is a prompt that works ten thousand times, fails politely, costs what you said it would, and can be changed without breaking. The difference is almost entirely engineering you already know how to do.

  1. Stream long answers. A model writing a full page takes many seconds. Streaming shows the first words straight away and — just as important — stops the request from timing out on long answers.
  2. Set timeouts and retry on purpose. Retry rate limits and server errors, waiting a bit longer each time. Never retry a refusal or a badly formed request — those will fail in exactly the same way forever.
  3. Insist on structure when code reads the answer. Ask for a schema and check the result before using it. A failed parse is a normal event to handle, not a reason to crash.
  4. Cache hard. Cache the unchanging opening block at the provider. And cache your own answers: people ask the same question all the time, and the cheapest call is the one you never make.
  5. Batch anything nobody is waiting for. Sorting a backlog overnight belongs on the batch endpoint, usually at about half the price.
  6. Move slow work off the request path. Anything slow becomes a background job with a status, exactly like publishing does in this product. A user staring at a spinner for forty seconds is a design failure, not a limit of the model.
  7. Fail gracefully. The provider will have an outage one day. Decide right now what your feature does then: serve a cached answer, drop to a smaller model, or show an honest message. Never a spinner that spins forever.

What to log, for this kind of feature. For every call, record:

  • the model and the prompt version, so a change in quality can be traced back to a deploy;
  • input and output token counts — this is your cost, per user and per feature;
  • how long it took, and whether the answer came from a cache;
  • which chunk ids were fetched for a RAG answer, because that is the only way to debug retrieval;
  • refusals, failed checks and tool errors, treated as proper metrics rather than log noise.
i
Keep prompts in version control, like code. They belong in the repository, in a review, with the test set that proves the change is good. A prompt edited live in some dashboard is a deployment to production with no version number — and the only one nobody can roll back.
