Decoding: the settings on the request

2 min read No experience needed
💡
In plain English
The model produces a ranked list of possible next words, and these settings decide how it picks from that list. Turn the randomness down and you get consistent, predictable, slightly flat output. Turn it up and you get variety and more mistakes. There is no universally right value — extraction wants one end, brainstorming wants the other.

Generation picks one token at a time from a ranked list of candidates. The request parameters decide how that pick is made and when it stops — the cheapest quality lever you have, because changing them costs nothing.

SettingWhat it controlsSensible use
temperatureRandomness in the pick. 0 is nearly deterministic; high is adventurous.Low for extraction, classification and code; higher for drafting. Some current models drop it entirely in favour of reasoning depth.
top_p (nucleus)Only consider the likeliest candidates that together make up p of the probability.Adjust this or temperature, not both. The default is usually right.
top_kOnly consider the k likeliest candidates.Rarely needed — a blunter version of top_p.
max_tokensA hard ceiling on the answer.Set it generously. Hitting it truncates mid-sentence, and you pay for the wasted output anyway.
stop sequencesText that ends generation immediately.When the model must not run past a delimiter you rely on.
effort / thinkingHow much internal reasoning happens before answering.High for analysis and planning, low for routine work. On current models this matters far more than temperature.
!
Temperature 0 is not determinism. It makes the same answer much more likely and guarantees nothing: floating-point arithmetic, batching on the provider’s side and model updates all introduce variation. Never build a system whose correctness depends on two identical calls returning identical bytes.
Your extraction endpoint returns valid JSON nine times out of ten and prose the tenth. What do you change?Answer

Not the temperature first — ask for structured output against a schema, which constrains generation rather than requesting good behaviour. Then lower the temperature. Finally, treat a parse failure as a normal outcome: validate, retry once, fall back. Nine-in-ten is what happens when a model is assumed to be an API; the fix is to make it behave like one.
