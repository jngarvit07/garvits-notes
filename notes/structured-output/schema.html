Designing a schema the model reads well

2 min read Some experience helps
💡
In plain English
The schema is not just a checker bolted on at the end — the model sees it and reads it as part of your instructions. A field called d with no description gets filled in with a guess. A field called invoice_date described as "the date printed on the invoice in YYYY-MM-DD, not today's date" gets filled in correctly. Time spent on the schema is time you do not have to spend on prompt wording.
tsA schema that does most of the prompting for you
const InvoiceSchema = z.object({
  invoice_number: z.string()
    .describe('As printed on the document. Null if not present.')
    .nullable(),

  // An enum removes a whole category of variation. Without it you get
  // "INR", "inr", "₹", "rupees", "Indian Rupee" across the same set of files.
  currency: z.enum(['INR', 'USD', 'EUR', 'OTHER']),

  total: z.number()
    .describe('Grand total INCLUDING tax, as a number with no symbol.'),

  // Every optional field should be nullable rather than missing, and the
  // description must say when to use null. Otherwise the model invents
  // something believable instead of admitting the field was not there.
  due_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/)
    .describe('ISO date. Null if the invoice states no due date.')
    .nullable(),

  line_items: z.array(z.object({
    description: z.string(),
    quantity: z.number().int().positive(),
    unit_price: z.number(),
  })).describe('One entry per row of the itemised table.'),

  // The way out. Without one, a model asked for a structure will produce
  // that structure — even from a photograph of a cat.
  extraction_confidence: z.enum(['high', 'low'])
    .describe('low if the document was unclear or is not an invoice'),
});
Name fields as you would for a colleague

shipping_address_country, not c3. The name is the strongest clue the model has about what belongs in there.

Enums instead of free text

Any field with a known set of valid values should be an enum. It saves you cleaning up the values later and removes a whole class of nearly-right answers.

Nullable, not optional

A missing field is confusing — was it absent from the document, or did the model just forget? An explicit null, with a description saying when to use it, is a real answer.

Always give it a way out

A confidence field, a not_applicable enum value, or a reason_declined. Forced into a shape with no exit, a model will fill it in whether or not the input supported it.

!
Deeply nested schemas make the quality worse. Four levels of nesting, with arrays of objects containing more arrays, gives noticeably worse extraction than a flat structure, and it is slower too. If you need a complicated shape, extract it flat and assemble it in your own code — that assembly is code you can test, and the model's part of the job gets easier.
Your extractor returns a believable due_date for invoices that do not have one. The field is marked optional. What is wrong?Answer

Optional means the model is allowed to simply leave the key out, which feels to it like an unremarkable choice — and producing a believable date is a better next-token guess than producing nothing at all. Nothing has told it that "absent" is a valid and expected outcome.

Make it nullable and required, and describe when null applies: "Null if the invoice states no due date." You have turned "you may skip this" into "you must answer, and nothing is one of the allowed answers."
