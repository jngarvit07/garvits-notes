Designing a schema the model reads well

2 min read Some experience helps
💡
In plain English
The schema is not just a validator bolted on afterwards — the model sees it, and reads it as part of the instructions. A field called d with no description gets filled in with a guess. A field called invoice_date described as “the date on the invoice in YYYY-MM-DD, not today's date” gets filled in correctly. Time spent on the schema is time not spent on prompt wording.
tsA schema that does most of the prompting for you
const InvoiceSchema = z.object({
  invoice_number: z.string()
    .describe('As printed on the document. Null if not present.')
    .nullable(),

  // An enum removes an entire category of variation. Without it you
  // get "GBP", "gbp", "£", "pounds", "British Pound" across a corpus.
  currency: z.enum(['GBP', 'USD', 'EUR', 'OTHER']),

  total: z.number()
    .describe('Grand total INCLUDING tax, as a number with no symbol.'),

  // Every optional field must be nullable rather than absent, and the
  // description must say when to use null. Otherwise the model invents
  // something plausible rather than admitting the field was not there.
  due_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/)
    .describe('ISO date. Null if the invoice states no due date.')
    .nullable(),

  line_items: z.array(z.object({
    description: z.string(),
    quantity: z.number().int().positive(),
    unit_price: z.number(),
  })).describe('One entry per row of the itemised table.'),

  // The escape hatch. Without one, a model asked for structure will
  // produce structure — even from a photograph of a cat.
  extraction_confidence: z.enum(['high', 'low'])
    .describe('low if the document was unclear or is not an invoice'),
});
Name fields as you would for a colleague

shipping_address_country, not c3. The name is the strongest signal the model has about what belongs there.

Enums over free strings

Any field with a known set of valid values should be an enum. It removes normalisation work downstream and eliminates a whole class of near-miss values.

Nullable, not optional

An absent field is ambiguous — was it missing from the document, or did the model forget? An explicit null with a description saying when to use it is a real answer.

Always give it a way out

A confidence field, a not_applicable enum value, or a reason_declined. Forced to produce a shape with no exit, a model will fill it in regardless of whether the input supported it.

!
Deeply nested schemas degrade quality. Four levels of nesting with arrays of objects containing arrays produces noticeably worse extraction than a flat structure, and it is slower. If you need a complex shape, extract flat and assemble it in your own code — that assembly is code you can test, and the model's part gets easier.
Your extractor returns a plausible due_date for invoices that do not have one. The field is marked optional. What is wrong?Answer

Optional means the model may simply omit the key, which reads to it as an unremarkable choice — and producing a plausible date is a better next-token prediction than producing nothing. It has no instruction telling it that absence is a valid and expected outcome.

Make it nullable and required, and describe when null applies: “Null if the invoice states no due date.” You have converted “you may skip this” into “you must answer, and nothing is one of the answers.”
