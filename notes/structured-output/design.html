Designing the tool surface

2 min read Some experience helps
💡
In plain English
Every tool you expose is a permission you have granted to a system that can be talked into things. The design question is not “what would be convenient” but “what is the smallest capability that does the job”. A tool that runs arbitrary SQL is a convenient way to bypass every control you have ever written.
Not this · general purpose
run_sql(query: string)
read_file(path: string)
http_request(url, method, body)
send_email(to, subject, body)

// Each one is "do anything" wearing
// a specific-sounding name. There is
// no check you can write on
// run_sql(query) that is not itself
// a database engine.
Do this · one job each
get_order(order_id)
list_orders_for_current_user(limit)
refund_order(order_id, amount, reason)
read_project_file(project_id, name)
notify_customer(order_id, template_id)

// Every one can be permission-checked,
// rate-limited, logged and reasoned
// about. The blast radius is written
// into the signature.
RuleWhy
The description is the documentationIt is the only thing the model has when deciding whether to reach for this tool. Say what it does, when to use it, when not to, and what it returns.
Fewer tools, better chosenSelection accuracy falls as the list grows. Past roughly fifteen or twenty, route to a subset first rather than offering everything at once.
No overlapping toolsTwo tools that could both plausibly apply produces inconsistent behaviour that is very hard to debug. Merge them or make the boundary explicit in both descriptions.
Ids, not free text, wherever possiblerefund_order(order_id) is checkable. refund(customer_name) requires a fuzzy lookup that can match the wrong person.
Return littleEvery byte returned is a token in the next call, on every subsequent turn. Return the fields needed, not the whole record.
Idempotent where you canRetries happen. A tool called twice by accident should not refund twice. Take an idempotency key.
You need the assistant to answer arbitrary questions about your database. Is run_sql justified here?Answer

Almost never in a product. It grants read access to everything, cannot be permission-checked in any meaningful way, and a prompt injection in any retrieved text turns into data exfiltration.

The workable versions are narrower: run against a read-only replica, as a database user with row-level security enforcing the tenant, restricted to a set of views built for this purpose, with a statement timeout and a row cap. Notice that every one of those is a database-level constraint. The safety comes from the boundary, never from the wording of the tool description.
