The four levels of enforcement

2 min read Some experience helps
MethodGuaranteeVerdict
1Ask in the promptNoneWorks most of the time, which is the worst possible failure rate — often enough to ship, rarely enough to page you.
2Ask, plus few-shot examplesNone, but betterMeaningfully more reliable. Still a hope.
3Tool / function callingStrongThe provider validates arguments against your schema. Well supported everywhere.
4Constrained decodingAbsoluteInvalid tokens are removed from the choice at each step, so malformed output is not merely unlikely — it is unreachable.
💡
How constrained decoding actually works
Remember that the model produces a score for every token in the vocabulary, and something else picks from that list. Constrained decoding edits the list before the pick. If the schema says the next character must be " or }, every other token has its score set to negative infinity. The model cannot emit invalid JSON in the same way you cannot walk through a wall — not discipline, geometry.
txtGrammar-constrained generation, step by step
schema:  { "total": number }
so far:  {"total":

  full vocabulary        after the grammar mask
    "  0.72   ->  -inf     (a string cannot start a number)
    1  0.09   ->   0.09
    2  0.04   ->   0.04
    -  0.02   ->   0.02    (negative is allowed)
    the 0.01  ->  -inf
    ...                    everything not a valid continuation: -inf

  The model still CHOOSES. It just cannot choose wrongly.
i
Constrained decoding is available on most hosted providers under a name like “strict” or “structured outputs”, and on self-hosted stacks through libraries like Outlines or llama.cpp's grammars. Where it is offered, it is strictly better than level 3 for extraction. It usually restricts which JSON Schema features you can use — expect no anyOf at the root, and required fields everywhere.
