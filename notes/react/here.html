React in this product

2 min read No experience needed

In plain English
Everything above was the idea. This is where it lands in a real codebase — which files, doing which job. Reading the note and then reading the actual code is worth far more than reading the note twice: the second example you meet should always be a real one.

Every screen you are looking at right now is React. Some places worth opening once you have the ideas above, in increasing order of difficulty:

  • components/admin/GuideDocument.tsx — small components, props and children, plus one useEffect that watches which section is on screen. Nothing else.
  • app/contexts/AuthContext.tsx — the context that holds who is signed in. Every page that greets you by name reads it.
  • components/system/AdminShell.tsx — the sidebar around this page: state for what is open, an effect for the narrow-screen behaviour, and lists keyed by id.
  • app/studio/[draftId]/ — the editor. Large, and a fair demonstration of what happens when a lot of state has to stay consistent at once.
▶
Practice

Build a to-do list in a single component, and do not look anything up until you are stuck. It needs: state for the items, state for the input, adding on submit, removing by id, a key on each row, and a count of what is left. It is about forty lines, and it uses every idea in this note except context.

Then break it deliberately: use the array index as the key, add a row at the top and watch the wrong item get ticked. That is the bug you will otherwise spend an afternoon on later.

✓ Worth remembering
  • A component is a function that turns data into a description of the screen.
  • Props come in from the parent and are read-only; state is owned and changeable.
  • Setting state replaces rather than edits, and takes effect on the next render.
  • Keys must be stable ids, never array indexes.
  • Effects are for reaching outside React, and most of them should not exist.
