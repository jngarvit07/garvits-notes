Transactions: all of it, or none of it

2 min read No experience needed
💡
In plain English
Moving money between two accounts is two writes: take from one, add to the other. If the power fails between them, the money has vanished. A transaction wraps both so that either both happen or neither does — there is no moment when the outside world can observe a half-finished operation.

A transaction groups several statements so they either all happen or none do. It is the answer to “what if the server dies halfway through”.

jsThe canonical example
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'a';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'b';
COMMIT;      -- both, or ROLLBACK: neither. Money is never in flight.

The guarantees have a well-known acronym, and each letter is a real promise:

Means
AtomicAll of the statements, or none. There is no halfway.
ConsistentConstraints hold at the end. A transaction cannot leave broken rules behind.
IsolatedConcurrent transactions do not see each other’s half-finished work.
DurableOnce it commits, it survives the power going out.
Lock

A claim on a row while you change it. Other transactions touching the same row wait — which is correct, and why long transactions hurt.

Deadlock

Two transactions each holding what the other needs. Postgres kills one; the fix is to touch rows in a consistent order.

Race condition

Check-then-act with a gap. Two requests both see "no row yet" and both insert. Use a UNIQUE constraint or ON CONFLICT rather than checking first.

Isolation level

How much concurrent transactions can see of each other. The default is sensible; raise it only with a reason.

prismaIn Prisma
await prisma.$transaction(async (tx) => {
  const project = await tx.project.create({ data: { name, userId } });
  await tx.auditLog.create({
    data: { action: 'project.create', targetId: project.id, userId },
  });
  // Throw anywhere in here and both are undone.
});
!
Keep transactions short, and never await a network call inside one. An open transaction holds locks; other requests touching the same rows queue behind it. Calling an email provider inside a transaction means a slow provider becomes a database-wide stall. Do the database work, commit, then send the email.
Which of these needs a transaction: updating a user’s display name, or creating an order along with its line items?Answer

The second. The display name is a single write, and a single write is already all-or-nothing. An order and its line items are several writes that are only meaningful together — an order with no items, or items with no order, is corrupt data that nothing later will know how to fix.

The test: if a crash halfway through would leave the data in a state that makes no sense, it needs a transaction.
