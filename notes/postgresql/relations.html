Relations and joins

2 min read No experience needed
💡
In plain English
Rather than repeating a customer’s address on every one of their orders, you store the customer once and have each order point at them. A join is the moment you put those pieces back together to answer a question. Storing each fact once is why correcting an address corrects it everywhere, and joins are the price you pay for that.

Three shapes cover essentially every relationship, and picking the wrong one is a schema problem you feel for years.

ShapeExample hereHow it is stored
One to manyA user has many projectsThe child holds the parent id: projects.user_id.
One to oneA user has at most one siteSame, plus a UNIQUE on the foreign key.
Many to manyComponents belong to many templatesA third table holding the two ids.

A join reads across a relationship — one query, one round trip, instead of a query per row.

sqlJoins
-- Every project, with its owner's email.
SELECT p.name, u.email
FROM projects p
JOIN users u ON u.id = p.user_id;        -- INNER: only rows with a match

-- Every user, and their projects if they have any.
SELECT u.email, p.name
FROM users u
LEFT JOIN projects p ON p.user_id = u.id;  -- keeps users with none; p.name is NULL

-- Users who have never made a project.
SELECT u.email
FROM users u
LEFT JOIN projects p ON p.user_id = u.id
WHERE p.id IS NULL;

The performance trap here has a name — the N+1 query — and it is the single most common cause of a page that is fine in development and unusable with real data.

Not this · 1 + 100 queries
const projects = await db.project.findMany();

for (const project of projects) {
  // One database round trip per project.
  project.owner = await db.user.findUnique({
    where: { id: project.userId },
  });
}
Do this · 1 query
const projects = await db.project.findMany({
  include: { user: true },
});

// Prisma fetches the related rows together
// instead of once per project.
i
It hides well: with ten test rows the loop version is imperceptibly slower. With ten thousand rows it is thousands of round trips, and the fix is one word. Any loop containing an await on the database deserves a second look.
What is the practical difference between an inner join and a left join?Answer

An inner join returns only rows that have a match on both sides. A left join keeps every row from the left table and fills in blanks where there is no match.

The difference shows up as a bug when you count things: “every customer and how many orders they have placed” written with an inner join silently omits every customer who has never ordered — which is usually the group you most wanted to see.
