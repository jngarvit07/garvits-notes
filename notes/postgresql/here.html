The database in this product

2 min read No experience needed
💡
In plain English
The schema this product actually runs on, and why the tables are shaped the way they are.
  • backend/prisma/schema.prisma — every model, heavily commented. Start at User and follow the relations out.
  • backend/prisma/migrations/ — the history of every schema change, in order.
  • npm run db:studio — a browser view of the development data. The fastest way to understand a schema is to look at real rows in it.
  • npm run db:prod:status — what is pending in production. Safe: it reads.
▶
Practice
  1. Open db:studio, find your own user row, and follow it to a project. That is a foreign key, in the flesh.
  2. In psql or a SQL console, write a query that returns each user’s email and their project count, highest first. You will need a LEFT JOIN, GROUP BY and ORDER BY.
  3. Run EXPLAIN ANALYZE on it. Find whether any step says Seq Scan, and on which table.
  4. Add a field to a model in the schema, run migrate dev, and read the generated SQL before it runs. Then revert both.
✓ Worth remembering
  • The database is the only layer where a mistake is permanent — put the rules in it.
  • Constraints prevent bad rows; application checks only discourage them.
  • Index what you filter, join and sort on; prove it with EXPLAIN ANALYZE.
  • A loop with an await on the database is an N+1 query waiting for real data.
  • Migrations only go forward, and in production here they are run by hand, first.
