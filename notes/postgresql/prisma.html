Prisma: the layer this product actually types

2 min read No experience needed
💡
In plain English
Prisma sits between your code and the database so queries are written in TypeScript instead of SQL strings, and the compiler knows the shape of what comes back. The real benefit is that a typo in a column name is a build error rather than a runtime one. The real cost is that it hides what SQL is actually being run, which matters the moment something is slow.

Prisma is an ORM: you describe your tables once in a schema file, and it generates a typed client. Your editor then knows every model and field, and a typo is a build error instead of a runtime one.

prismaprisma/schema.prisma
model User {
  id        String    @id @default(cuid())
  email     String    @unique
  role      Role      @default(USER)
  isActive  Boolean   @default(true)
  createdAt DateTime  @default(now())

  projects  Project[]           // the other side of the relation

  @@index([email])
}

model Project {
  id       String @id @default(cuid())
  name     String
  userId   String
  user     User   @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}

enum Role {
  USER
  ADMIN
}
prismaQuerying
// One row
const user = await prisma.user.findUnique({ where: { email } });

// A page of rows, with a related record, choosing the fields
const projects = await prisma.project.findMany({
  where: { userId, name: { contains: search, mode: 'insensitive' } },
  select: { id: true, name: true, user: { select: { email: true } } },
  orderBy: { createdAt: 'desc' },
  skip: (page - 1) * 20,
  take: 20,
});

// Create, update, upsert
await prisma.project.create({ data: { name, userId } });
await prisma.project.update({ where: { id }, data: { name } });
await prisma.project.upsert({
  where: { id },
  create: { id, name, userId },
  update: { name },
});

// Counting and aggregating
const total = await prisma.project.count({ where: { userId } });
PrismaSQL it becomes
findManySELECT ... FROM ... WHERE ...
includeA join, or a second query — Prisma decides. Fetches the whole related row.
selectSELECT with named columns. Prefer it: fetching what you need is faster and leaks less.
skip / takeOFFSET and LIMIT.
$transactionBEGIN ... COMMIT.
$queryRawRaw SQL, for what the client cannot express.
!
Raw SQL must still be parameterised. Prisma’s $queryRaw tagged-template form is safe because the values travel separately from the query text. Building a query by concatenating strings — in any language, with any library — is how SQL injection happens, and it is the one mistake in this note that can hand over the entire database.
Not this · string concatenation
// email = "x'; DROP TABLE users; --"
const rows = await prisma.$queryRawUnsafe(
  "SELECT * FROM users WHERE email = '" + email + "'"
);
Do this · parameterised
const rows = await prisma.$queryRaw`
  SELECT * FROM users WHERE email = ${email}
`;
// The value is sent as a parameter, never as query text.
