How to actually use AI to build a project

2 min read Read CI/CD, Docker & Kubernetes first
💡
In plain English
The failure mode is asking for the whole app in one prompt and hoping. It can write a lot of code fast, which is exactly the danger — a hundred lines you didn't read is a hundred lines you don't understand when they break at 2am. The fix isn't asking for less; it's asking for it in an order you can review as it arrives, the same discipline you'd want from any engineer moving fast.

Four habits separate a project an AI helped build well from one that collapses under its own code six weeks in.

1. Write the spec first, yourself

One page: what it does, the main entities, the endpoints, what "done" looks like for the first slice. An AI given a clear spec produces focused code; given "build me a task tracker" it guesses at every decision you didn't make.

2. Build one vertical slice before the next

One real feature, end to end — one API endpoint, wired to one UI screen, actually working — before starting the second. Not "all the backend, then all the frontend."

3. Give it the real context, not a blank page

The actual file it's editing, the actual API response shape, the project's existing conventions. A model guessing at a schema it was never shown produces plausible code against the wrong one.

4. Read every diff before it merges

Not skim — read. You are the one who has to debug it in production later, and "I don't know, the AI wrote it" is not a debugging strategy.

Not this · one giant prompt
"Build me a full task tracker app with
auth, a Postgres backend, a React frontend,
and deploy it to Kubernetes."

# Thousands of lines land at once.
# Nothing has been run. Nothing has been read.
# The first bug report has no obvious starting point.

# Then asks for the next slice.

This note works through one real scenario end to end — QuickTasks, a small task tracker — applying exactly this discipline: a spec, then the backend slice, then the frontend slice, then wiring them together, then shipping it with the Docker/CI-CD/Kubernetes pipeline from the previous note.
Why does giving the model the existing file it's editing produce better code than describing the feature from scratch?Answer

Without it, the model has to guess at your naming conventions, your error-handling pattern, your validation style, and the exact shape of your schema — and a guess that's 90% right is often worse than one that's obviously wrong, because the mismatch is subtle and easy to merge without noticing. Given the real file, it matches what's already there instead of inventing a plausible-looking alternative.
