Wiring frontend, backend and database together locally

2 min read Read CI/CD, Docker & Kubernetes first
💡
In plain English
Three pieces built separately need one place where they actually run together — this is where a schema mismatch, a missing environment variable, or a CORS setting nobody configured finally shows up, before any of it reaches production.
yamldocker-compose.yml — the whole app, one command
services:
  db:
    image: postgres:16-alpine
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: quicktasks }

  api:
    build: ./api
    environment:
      DATABASE_URL: postgresql://postgres:dev@db:5432/quicktasks
      CORS_ORIGIN: http://localhost:3000
    ports: ["8080:8080"]
    depends_on: [db]

  web:
    build: ./web
    environment:
      NEXT_PUBLIC_API_URL: http://localhost:8080
    ports: ["3000:3000"]
    depends_on: [api]
jsapi/src/server.ts — the CORS line every scaffold forgets
import cors from 'cors';
// Without this, the browser blocks every request from the web
// container to the api container — even though curl works fine,
// because curl doesn't enforce CORS. Only browsers do.
app.use(cors({ origin: process.env.CORS_ORIGIN }));
Your frontend's fetch call to the API fails with a CORS error in the browser console, but running the exact same request with curl works perfectly. Why the difference?Answer

CORS is a browser-enforced rule, not a server-enforced one. The browser sends an Origin header and refuses to hand the response to your page's JavaScript unless the server explicitly allows that origin back — a protection against a malicious page silently calling APIs on your behalf using your logged-in session. curl has no such page context to protect, so it never triggers the check at all; the API responds identically either way.
