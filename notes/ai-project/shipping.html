Shipping it: containers, CI/CD and Kubernetes for this app

2 min read Read CI/CD, Docker & Kubernetes first
💡
In plain English
Everything from here is a direct application of the DevOps note, not new ideas — two Dockerfiles, one pipeline that builds and tests both, and two Kubernetes Deployments behind one Ingress. The scenario was never separate from that note; this is the point where they meet.
yaml.github/workflows/deploy.yml — both services, one pipeline
on: { push: { branches: [main] } }
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cd api && npm ci && npm test
      - run: cd web && npm ci && npm run build   # a type error here fails CI

  build-and-push:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - run: |
          docker build -t ghcr.io/acme/api:${{ github.sha }} ./api
          docker build -t ghcr.io/acme/web:${{ github.sha }} ./web
          docker push ghcr.io/acme/api:${{ github.sha }}
          docker push ghcr.io/acme/web:${{ github.sha }}

  migrate-and-deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - run: npx prisma migrate deploy          # BEFORE the new code goes live
      - run: |
          kubectl set image deployment/api api=ghcr.io/acme/api:${{ github.sha }}
          kubectl set image deployment/web web=ghcr.io/acme/web:${{ github.sha }}
          kubectl rollout status deployment/api
          kubectl rollout status deployment/web
yamlingress.yaml — one address, two services behind it
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: quicktasks
spec:
  rules:
    - host: quicktasks.app
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend: { service: { name: api-service, port: { number: 80 } } }
          - path: /
            pathType: Prefix
            backend: { service: { name: web-service, port: { number: 80 } } }

One push to main now means: AI-assisted code change → reviewed and merged → tested in CI → two images built and tagged with that commit → migration applied → both Deployments updated → live, with the DevOps note's rollout and rollback discipline covering the last step.

✓ Worth remembering
  • Spec first, one vertical slice at a time — not the whole app in one prompt.
  • Give the model the real schema and the real existing file, not a description of them.
  • Share types between frontend and backend so a rename fails a build instead of shipping silently.
  • localhost inside one container never reaches another — use the Compose/Kubernetes service name.
  • CORS is enforced by the browser, not the server — that's why curl "works" when the browser doesn't.
  • The deploy pipeline for an AI-assisted project is identical to any other project's: tests gate it, migrations run before the new code, images are tagged by commit.
Why does prisma migrate deploy run before the images are rolled out, rather than after?Answer

The new code is written expecting the new schema to already exist — a column it reads or writes has to be there before that code receives any traffic. Running the migration first means by the time the new Pods start serving requests, the database already matches what they expect. It also has to stay backwards-compatible, because the old Pods are still running against the same database until the rollout finishes.
