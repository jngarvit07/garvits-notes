Getting it deployed automatically

2 min read No experience needed
💡
In plain English
Deploying from a laptop works right up until the day the wrong branch goes out, or the only person who knows the command is on holiday. A pipeline is that command written down, with gates in front of it — and for an AI system, one of those gates has to be a quality check, because every ordinary test can pass while the answers get worse.

Deploying by hand from a laptop works exactly until the day it does not: the wrong branch, an uncommitted change, or the only person who knows the command is away.

yamlThe pipeline, in the order the steps must happen
on: push to main
steps:
  1. install and typecheck
  2. run tests                      # gate: fails here, nothing deploys
  3. run the eval set               # gate: AI quality, see the Evals note
  4. build the container, tag it with the commit SHA
  5. push to Artifact Registry
  6. run database migrations        # BEFORE the new code, and additive only
  7. deploy the revision with NO traffic
  8. smoke-test the revision's own URL
  9. shift traffic: 10% -> wait -> 100%
 10. on error rate rising: shift back to the previous revision

The two gates

Step 3 is the one specific to AI systems. A prompt change that passes every unit test can still make answers worse, and nothing in a normal pipeline will notice. An eval set that runs on every push is what turns “it seems better” into a number.

Steps 7 to 10 are the ordinary discipline that most teams skip. Cloud Run keeps every revision and can split traffic between them, so a rollback is one command against a revision that is already there — not a rebuild under pressure.

!
Migrations must be backwards-compatible. During a gradual rollout, old code and new code are running at the same time against one database. A migration that drops a column the old revision still reads will break production for the users on the old revision. Add columns first, deploy code that writes both, then remove the old column in a later release. See the PostgreSQL note for the full pattern.
✓ Worth remembering
  • A cloud rents compute, storage, networking and identity. Everything else is a combination of the four.
  • Separate projects for dev, staging and production, from day one.
  • Cloud Run unless you have a specific reason. Always set max-instances.
  • Instances are ephemeral: nothing that must survive goes on local disk.
  • One service account per service, smallest roles, and never a downloaded key file.
  • Secrets in Secret Manager, mounted as environment variables at deploy.
  • Budget alerts and labels on day one; log tokens per feature from the first call.
Why must database migrations be backwards-compatible during a gradual rollout?Answer

Because for a while the old code and the new code are both running against the same database. A migration that drops a column the old version still reads breaks production for exactly the users still being served by it.

Add first, deploy code that handles both shapes, and only remove in a later release. It turns a risky moment into three unremarkable ones.
