Chunking: the decision you make once

2 min read Read the AI note first
💡
In plain English
A chunk is the unit of retrieval — the smallest thing that can come back. Cut too small and an answer gets split across two pieces so neither is convincing on its own. Cut too large and one relevant sentence arrives wrapped in three pages of noise that dilutes it. Where you cut is not a tuning parameter; it decides what your system is capable of answering.
StrategyHow it cutsGood forFails on
Fixed sizeEvery N tokens, with an overlapNothing much. It is the default because it is easy.Cuts mid-sentence and mid-table. Ignores every structural clue the document gives you.
RecursiveSplit on paragraphs; if still too big, sentences; then wordsThe sensible baseline. Respects natural boundaries where it can.Still blind to what the document means.
StructuralOn headings, sections, list items, table rowsUsually the right answer for documentation, policies, manuals, wikis, code.Documents with no structure — scanned pages, transcripts.
SemanticWhere the topic shifts, measured by embedding distanceLong unstructured prose. Transcripts, interviews, articles.Costs an embedding pass over everything, and the threshold needs tuning.
Parent–childIndex small pieces, return the larger section around a hitBest of both. Precise matching, full context in the answer.Two stores to keep consistent. Worth it.
tsParent–child, which is what most systems should be doing
// Index the SMALL piece — a precise thing to match against.
// Return the BIG piece — enough context for the model to answer from.
for (const section of doc.sections) {
  const parentId = store.saveParent(section.text);        // ~2000 tokens

  for (const para of section.paragraphs) {                // ~200 tokens
    index.add({
      vector: embed(para.text),
      text:   para.text,
      parent: parentId,        // <- the hit points at the fuller section
      meta:   { doc: doc.id, heading: section.heading,
                updatedAt: doc.updatedAt, orgId: doc.orgId },
    });
  }
}

// At query time: match on paragraphs, but send the parent sections.
const hits    = index.search(embed(question), { k: 20 });
const parents = dedupe(hits.map((h) => store.getParent(h.parent)));

Two things to put in every chunk

Its heading trail

Prefix the chunk text with Document › Section › Subsection. A paragraph reading “the limit is 30 days” is useless alone and precise once it says which policy and which section it came from. Costs a handful of tokens, and it improves both retrieval and the answer.

Metadata you can filter on

Owner, date, document type, permissions, version. Filtering during the search is what lets you exclude superseded documents and other people's data — and doing it after retrieval is not the same thing at all.

i
Sensible defaults if you need to start somewhere: structural chunking on headings; a target of 400–800 tokens; 10–15% overlap when you must split mid-section; heading trail prefixed to every chunk. Then measure on your own retrieval eval set before touching any of those numbers, because the right values differ enormously by corpus.
