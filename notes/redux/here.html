State in this product

2 min read Read React first
💡
In plain English
Where the lines actually fall in this codebase — and why there is far less global state here than a React app of this size usually carries.

The honest answer for this codebase is that there is very little global client state, and that is by design rather than by neglect.

WhatWhere it livesWhy
Page data — projects, pages, assetsFetched in Server ComponentsIt arrives with the HTML. There is no client cache to keep honest, because the client never holds the authoritative copy.
Signed-in userContext, provided once in the root layoutRead nearly everywhere, changes on sign-in and sign-out. Context's exact use case.
Editor draft — what you are typinguseState in the editor, autosavedOne screen owns it. Nothing else in the app has a legitimate reason to read a draft mid-keystroke.
Theme, sidebar open/closedContext + localStorageSmall, rarely changed, and must survive a reload.
i
The rule this codebase follows: the server is the source of truth, and the client holds as little as it can get away with. Every piece of state on the client is a copy that can go stale, so the smallest set of copies is the easiest system to reason about. When a screen does need shared, fast-changing client state, that is the moment to add a store — and to add it for that screen's problem, not as an architecture up front.
✎
Try this
Open any React app you have and list its state on paper in two columns, server and client. Then, for each client item, write the name of the component that owns it. Anything you cannot assign an owner to is either derivable from something else, or is the state that actually needs a store. That exercise takes fifteen minutes and usually settles the question a library comparison cannot.
