Next.js

The framework around React: routing by folder, rendering on the server, and shipping less JavaScript. Written against Next 14's App Router, which is what this product runs.

Some experience helps 30 min read 12 sections

What Next.js adds to React

React draws a screen. It has no opinion about how somebody gets to that screen, where the HTML comes from the first time, or what happens if they have a slow phone. Next.js is the answer to all of that: a framework that wraps React and supplies the parts a real website needs.

💡
In plain English
React is an engine. Next.js is the car built around it — wheels, steering, a chassis and a number plate. You can build your own car around the engine, and for the first month it goes well.
Problem React does not solveWhat Next.js does
How does a URL become a screen?Folders under app/ are the routes. No routing configuration exists.
What does the first response contain?HTML, rendered on the server, so the page appears before any JavaScript loads.
How much JavaScript reaches the browser?Only components you mark as interactive. The rest never ships.
Where does the API live?route.ts files, if you want them in the same project.
Images, fonts, page titles, sitemaps?Built in, and correct by default.
i
This product does not use Next.js for its API. The backend is a separate Express service, and the frontend calls it over HTTP through services/api.ts. That is a deliberate split: the API has to serve published sites and jobs that have nothing to do with this frontend, so it lives on its own.

Routing by folder

A folder under app/ is a URL segment; a page.tsx inside it makes that URL real. Nothing is registered anywhere. The file tree is the routing table, which means you can read the whole site’s map with ls.

tsxThis product, abbreviated
app/
  page.tsx                      ->  /
  dashboard/page.tsx            ->  /dashboard
  admin/
    layout.tsx                  ->  wraps everything under /admin
    overview/page.tsx           ->  /admin/overview
    learning/
      page.tsx                  ->  /admin/learning
      react/page.tsx            ->  /admin/learning/react
    users/
      page.tsx                  ->  /admin/users
      [userId]/page.tsx         ->  /admin/users/anything

The filenames that mean something, and only these:

FileWhat it is
page.tsxThe screen for this URL. Without one, the folder is just a path segment nobody can visit.
layout.tsxChrome wrapped around this folder and everything under it. Survives navigation between children — it does not re-mount.
loading.tsxShown automatically while this route is being prepared.
error.tsxShown when the route throws. Must be a Client Component, and receives a reset() to try again.
not-found.tsxShown for notFound() and unmatched URLs.
route.tsAn HTTP endpoint instead of a screen. Cannot live in the same folder as a page.tsx.
[id]/A dynamic segment: matches anything, and hands you the value.
(group)/A folder purely for organisation. The parentheses keep it out of the URL.

Navigation between routes uses <Link>, not <a>. A plain anchor reloads the whole application — the JavaScript, the styles, the auth state, all of it — while Link fetches only what the next screen needs and swaps it in. Use <a> only for genuinely external addresses.

tsNavigating
import Link from 'next/link';
import { useRouter, usePathname, useSearchParams } from 'next/navigation';

<Link href="/admin/users">Users</Link>

// Navigating from code — after a save, say.
const router = useRouter();
router.push('/admin/users');
router.refresh();     // re-fetch the current route's server data, keeping local state

// Where am I?
const pathname = usePathname();                        // "/admin/users"
const page = useSearchParams().get('page');            // "?page=2" -> "2"

Server Components vs Client Components

This is the idea that makes the App Router different from everything before it, and the one worth reading twice. By default, your components run on the server only. They execute during the request, produce HTML, and their code is never sent to the browser.

Adding 'use client' at the top of a file opts that file — and everything it imports — into also running in the browser. That is what buys you state, effects and event handlers, and it is what costs you the download.

Server Component (default)Client Component ('use client')
RunsOn the server, during the requestOn the server once for the HTML, then in the browser
Can useawait, databases, secrets, the filesystemuseState, useEffect, onClick, window, localStorage
Cannot useHooks, event handlers, browser APIsSecrets, direct database access, Node modules
Ships to the browserNothingIts code, and its imports
Server Component

The default. Runs during the request, can await a database, ships no JavaScript.

Client Component

Marked 'use client'. Gets state and events, and is downloaded by every visitor.

The boundary

A prop crossing into a client component crosses into the browser. That is the security line.

Hydration

The browser attaching behaviour to HTML the server already rendered.

!
Everything in a Client Component is public. Its source, and any value you pass into it as a prop, is in the browser and readable by anyone. An API key read in a Server Component and then handed to a client child is a leaked API key — the boundary is the prop, not the file.

The practical rule: keep pages as Server Components, and push 'use client' down to the smallest piece that actually needs to be interactive. A page marked client-side drags every component it renders into the browser bundle with it.

Not this · whole page goes client-side
'use client';         // at the top of the page

export default function Page() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <HugeStaticArticle />   {/* shipped too */}
      <button onClick={() => setOpen(!open)}>Menu</button>
    </>
  );
}
Do this · only the button is interactive
// page.tsx — a Server Component, ships no JS
export default function Page() {
  return (
    <>
      <HugeStaticArticle />
      <MenuButton />
    </>
  );
}

// MenuButton.tsx
'use client';
export function MenuButton() {
  const [open, setOpen] = useState(false);
  ...
}
i
A Client Component can still render server-rendered content: pass it as children from a Server Component parent. The child was already rendered on the server, so wrapping it in something interactive does not drag it into the bundle.

Every page in this admin area is a Client Component, and deliberately so: they are behind a login, they are dense with interaction, and they read the session from React context. The pages that a stranger sees first — the public site, published pages — are the ones where the server/client line is worth being strict about.

Layouts, loading and error states

You read an API key in a page and pass it to a chart component marked 'use client'. Who can see the key?Answer

Everybody. The value is serialised into the HTML so the browser can hand it to the component when it hydrates — it is visible in view-source and in the network tab. The file it was read in makes no difference; the prop crossing the boundary is what matters.

The fix is to keep the key server-side and pass the result of using it: fetch the data on the server, send the numbers to the chart.

A layout.tsx wraps its folder and everything below it. Layouts nest, and — crucially — a layout does not re-mount when you navigate between its children. A sidebar keeps its scroll position and its open sections; state inside it survives.

tsxapp/admin/layout.tsx — this product's, shortened
export default function AdminLayout({ children }: { children: React.ReactNode }) {
  return (
    <ProtectedRoute requiredRole="admin">
      <AdminShell>{children}</AdminShell>
    </ProtectedRoute>
  );
}

One file gives every admin screen its navigation and its access check. Add a page anywhere under app/admin/ and it is protected without doing anything — which is why the Learning notes did not need a line of authentication code.

!
A layout is a courtesy, not a lock. Checking the role here stops an ordinary user seeing a panel of empty tables; it does not stop anyone requesting the data. The server has to refuse it too, and in this product it does — see the Express note on middleware.

loading.tsx and error.tsx are the two states every screen has and most codebases forget. Next wires them up automatically: a route that is still loading shows the former, a route that throws shows the latter with a reset() to try again.

Dynamic routes

A folder in square brackets matches anything and hands you the value. One file serves every user, every project, every template.

export default function UserDetailPage({

  params: { userId: string };

  // /admin/users/abc123  ->  params.userId === 'abc123'

On Next 15 this changes. params and searchParams become promises: const { userId } = await params. This product is on 14, so the synchronous form above is correct here — but it is the first thing to fix on an upgrade, and the error message when you forget is not obvious.

When a page is built

The same React code can produce a page at four different moments, and choosing the moment is most of what performance work in Next.js is.

StrategyRenderedRight forHow
StaticOnce, at build timeMarketing pages, docs, terms — anything the same for everyoneThe default when a page uses no request-specific data
Incremental (ISR)At build, then re-made on a timerContent that changes hourly, not per visitorexport const revalidate = 3600
Dynamic (SSR)On every requestAnything personalised — a dashboard, a signed-in viewexport const dynamic = 'force-dynamic'
ClientIn the browser, after loadHighly interactive screens behind a login'use client' plus fetching in an effect

You rarely set these by hand. Using a request-bound API — cookies, headers, a searchParams read — makes a route dynamic on its own; using none of them leaves it static. The explicit exports are for when you need to override that guess.

Real worldWhy the marketing page and the dashboard differ

A public landing page has no visitor-specific content, so it is built once and served from a cache — the fastest thing a website can do. A dashboard is different for every person, so building it in advance is meaningless: it must be produced per request, or fetched in the browser once we know who is asking.

Get this backwards and the symptoms are opposite and equally bad: a static dashboard shows one person’s data to everybody, and a dynamic landing page burns a server render on a page that never changes.

Fetching and caching

In a Server Component you fetch data by awaiting it. There is no useEffect, no loading state, no waterfall of requests from the browser — the component is already running on a server that can talk to the database.

jsServer Component fetching
// No 'use client'. This runs on the server only.
export default async function ProjectsPage() {
  const projects = await db.project.findMany();   // safe here — never shipped
  return <ProjectList projects={projects} />;
}

In a Client Component you fetch the way the React note describes: an effect, a loading flag, an error state — which is what every screen in this admin area does, because it talks to a separate API with the signed-in user’s token.

Caching is where Next surprises people. On Next 14, fetch inside the App Router caches by default, so a request that looks live may be served from a store made minutes ago. Three controls decide it:

jsThe three cache instructions
// Cached forever until the build changes it:
await fetch(url);

// Re-fetched at most once a minute:
await fetch(url, { next: { revalidate: 60 } });

// Never cached — always fresh:
await fetch(url, { cache: 'no-store' });
!
A page showing stale data on a deployment while being perfectly fresh on your machine is almost always this. It is also the default that Next 15 reversed — there, fetches are uncached unless you ask. Being explicit costs one line and survives the upgrade either way.

Route handlers and middleware

A route.ts file is an HTTP endpoint: you export a function per method, and it runs on the server.

tsapp/api/health/route.ts
import { NextResponse } from 'next/server';

export async function GET() {
  return NextResponse.json({ ok: true });
}

export async function POST(request: Request) {
  const body = await request.json();
  if (!body.email) {
    return NextResponse.json({ error: 'Email required' }, { status: 400 });
  }
  return NextResponse.json({ created: true }, { status: 201 });
}

middleware.ts at the project root runs before a matching request reaches any route — the place for redirects, locale switching and coarse auth gates. It runs on the Edge runtime, which is fast and narrow: no Node APIs, no database clients, no heavy dependencies.

i
Middleware is the wrong place for real authorisation. It sees a cookie, not your database, so it can say “this looks signed out, go to the login page” and nothing stronger. The decision that matters belongs where the data is.

Images, fonts and page titles

  • next/image — resizes, converts to modern formats, and reserves the space so the page does not jump while it loads. A raw <img> of a 4 MB photo is one of the most common real-world causes of a slow page.
  • next/font — downloads the font at build time and serves it from your own domain. No request to a font host at page load, and no flash of the wrong typeface.
  • Metadata — a metadata export sets the title, description and social preview. generateMetadata does the same when the values depend on the data.
tsMetadata, static and dynamic
export const metadata = {
  title: 'OnePage Studio',
  description: 'Build and publish a page without writing code.',
};

// When the title depends on the record:
export async function generateMetadata({ params }: { params: { id: string } }) {
  const project = await getProject(params.id);
  return { title: project.name + ' — OnePage Studio' };
}

Environment variables and deploying

Environment variables keep configuration out of the code. In Next there is one rule that matters more than all the others:

!
NEXT_PUBLIC_ means public. A variable with that prefix is baked into the JavaScript sent to every browser. Anything without it stays on the server. A secret given that prefix — an API key, a database URL — is published the moment you deploy, and rotating it is the only fix.
jsfrontend/.env.local
# Readable by the browser. Only ever put non-secrets here.
NEXT_PUBLIC_API_URL=http://localhost:5000/api/v1

# Server-side only. Never reaches the browser.
INTERNAL_WEBHOOK_SECRET=...

Also worth knowing: these values are read at build time for client-side variables, not at boot. Changing one on a hosting dashboard does nothing until the next deployment — a genuinely confusing hour if you have not met it before.

Deployment is next build followed by next start, or a platform that does both for you. This frontend deploys to Vercel; the Express API deploys separately, which is why NEXT_PUBLIC_API_URL exists at all.

The mistakes everybody makes

SymptomCauseFix
useState throws “only works in a Client Component”.The file is a Server Component — the default.Add 'use client', to the smallest file that needs it.
The whole app is in the browser bundle.'use client' sits at the top of a page or layout.Move it down to the interactive leaf component.
window is not defined during the build.Browser APIs touched while rendering on the server.Read them inside useEffect, which only runs in the browser.
Data is stale in production, fresh locally.The default fetch cache on Next 14.cache: 'no-store' or a revalidate value, stated explicitly.

Next.js in this product

  • app/admin/layout.tsx — nine words of routing that protect every admin screen at once.
  • app/admin/users/[userId]/page.tsx — a dynamic segment feeding a detail screen.
  • next.config.js — image hosts, redirects and headers, all commented.

Practice
  1. Add app/admin/learning/scratch/page.tsx exporting a component that renders your name. Visit /admin/learning/scratch. No configuration — that is the point of file routing.
  2. Delete the 'use client' line from a page in this section and add a useState. Read the error carefully: it is the clearest description of the server/client boundary you will find.
  3. Put it back, then delete your scratch folder.
✓ Worth remembering
  • Folders under app/ are routes; page.tsx makes one real.
  • Components are server-side until a file says otherwise, and only client files ship.
  • Anything a Client Component can see, a visitor can see.
  • Layouts wrap and persist; loading.tsx and error.tsx come free.
  • Say what you mean about caching rather than relying on the default.
