Building the pipeline: from git push to a deployed container

2 min read No experience needed
💡
In plain English
Continuous Integration means every change is automatically built and tested the moment it is pushed, so problems surface in minutes, not at the next release. Continuous Delivery means a passing change is automatically packaged and ready to ship. Continuous Deployment goes one step further and actually ships it, with no human clicking "approve". Most teams want CI plus delivery, with a deliberate human or automatic gate before production.
TermWhat happens automatically
CI — Continuous IntegrationEvery push is built, linted and tested. A broken change is caught in minutes, not discovered a week later by someone else's pull.
CD — Continuous DeliveryA change that passes CI is automatically packaged (a container image, built and pushed to a registry) and is one click away from production.
CD — Continuous DeploymentThe same, minus the click — a passing change on the main branch goes to production with no human step at all.
yaml.github/workflows/deploy.yml — a complete pipeline, GitHub Actions
name: build-test-deploy
on:
  push:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm run lint
      - run: npm test                     # gate: nothing below runs if this fails

  build-and-push-image:
    needs: build-and-test                 # only starts once tests pass
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - run: |
          docker build -t ghcr.io/acme/api:${{ github.sha }} ./api
          docker push ghcr.io/acme/api:${{ github.sha }}

  deploy:
    needs: build-and-push-image
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          # Point kubectl at the cluster (credentials come from a secret),
          # then update the running Deployment to the new image.
          kubectl set image deployment/api api=ghcr.io/acme/api:${{ github.sha }}
          kubectl rollout status deployment/api
i
Tag every image with the git commit SHA, never :latest. :latest means the thing running in production has no name you can trace back to a commit, rolling back is guesswork, and two deploys racing each other can push in any order. A commit SHA makes "what is actually running?" and "put yesterday's version back" both a single, unambiguous command.

Where the gates go

Why build the container image once and deploy that exact same image to staging and then production, rather than rebuilding for each?Answer

Rebuilding gives you a chance for the two environments to end up running different bytes — a dependency version resolved differently, a base image that updated between builds. Building once and promoting the identical, already-tested image means "it worked in staging" is a statement about the exact thing about to run in production, not about something similar to it.
