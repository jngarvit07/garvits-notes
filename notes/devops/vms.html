Where the virtual machine still fits

2 min read No experience needed
💡
In plain English
A virtual machine is a whole pretend computer — its own operating system, booted from scratch, running on top of a real one via a hypervisor. A container is much lighter: it shares the host machine's kernel and only packages the application layer on top. That difference is why containers start in milliseconds and VMs take tens of seconds, and why a single physical machine can run far more containers than VMs.
Virtual machineContainer
IncludesA full guest operating systemJust the app and its dependencies
IsolationStrong — a separate kernelWeaker — shares the host kernel
Startup timeTens of secondsMilliseconds to a couple of seconds
Density per machineA handfulDozens to hundreds

This is why the layers stack the way they do: every worker node in a Kubernetes cluster (or a Cloud Run instance, underneath the abstraction) is itself a virtual machine. Kubernetes does not remove VMs — it automates what runs on a fleet of them, so you stop thinking about any one of them individually.

When you still reach for a raw VM

Full OS-level control

Kernel modules, specific system libraries, licensing that assumes a dedicated machine — anything that does not fit the "just the app" container model.

A GPU box you configure yourself

Specific driver versions, a long-lived training or inference job that should not be interrupted by a scheduler moving it.

A self-hosted CI runner

Faster builds with a warm cache, or access to internal network resources a cloud-hosted runner cannot reach.

Legacy software

Something that was never designed to be containerised and is not worth the effort of making it so.

bashCreating one, when you need one
gcloud compute instances create ci-runner \
  --zone=europe-west2-a \
  --machine-type=e2-standard-4 \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --tags=ci-runner

# It is now a computer like any other: SSH in, install what you need.
gcloud compute ssh ci-runner --zone=europe-west2-a
!
A VM you provision by hand is a VM someone has to patch by hand. Unlike a managed container platform, nobody rotates its OS security updates for you. If you do reach for one, put it behind infrastructure-as-code (Terraform, or even just a documented creation script) so it can be recreated identically rather than becoming the one server nobody remembers how to rebuild.
Why do containers start in milliseconds while virtual machines take tens of seconds?Answer

A VM has to boot an entire guest operating system from scratch — its own kernel, its own init process — before your application even starts. A container skips all of that: it shares the host machine's already-running kernel and starts straight into your application process. The trade-off is isolation — a VM's separate kernel is a stronger security boundary than a container's shared one.
