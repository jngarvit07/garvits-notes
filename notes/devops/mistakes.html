Common mistakes, and what to remember

2 min read No experience needed
Not this · deploy on green, no gate
on: push
jobs:
  deploy:
    steps:
      - run: docker build -t app .
      - run: docker push app:latest
      - run: kubectl set image ...
# No tests. No lint. ":latest" everywhere.
# A typo reaches production in under a minute.
Do this · tests gate the deploy
on: push
jobs:
  test:            # deploy job has "needs: test"
    steps: [lint, unit tests, integration tests]
  deploy:
    needs: test
    steps:
      - run: docker build -t app:${{ github.sha }} .
      - run: docker push app:${{ github.sha }}
      - run: kubectl set image ... app:${{ github.sha }}
!
Migrations must be backwards-compatible during a rollout. A rolling deploy means old and new code run against the same database at the same time, briefly. A migration that drops or renames a column the old code still reads breaks production for whichever users happen to be served by the old Pods. Add new columns first, deploy code that writes both old and new, then remove the old column in a later release — see the PostgreSQL note for the full pattern.
i
Do not run your database as a Pod in the same cluster unless you have a specific reason and the operational experience to back it up. A managed database (Cloud SQL, RDS) handles backups, failover and patching for you; a database Pod restarted by the same scheduler that just redeployed your API is one misconfigured rollout away from data loss.
✓ Worth remembering
  • VM, Docker, Kubernetes and CI/CD are four layers, not four competing choices — each sits on top of the one before it.
  • Order a Dockerfile from least to most likely to change, so the dependency layer stays cached.
  • Never point one container at another with localhost — use the service name.
  • Tag every image with the git commit SHA. Never deploy :latest.
  • Tests gate the deploy job — nothing ships if they fail.
  • Always set Kubernetes resource requests, limits and a readiness probe.
  • Reach for Kubernetes because you have many services to orchestrate, not because it's the well-known name.
  • Database migrations must tolerate old and new code running at once.
A rollout finishes, and for about thirty seconds a fraction of requests get errors before settling down. What's the most likely missing piece?Answer

A missing or too-eager readinessProbe. Without one, Kubernetes considers a Pod ready as soon as its container process starts, and the Service begins routing real traffic to it — even though the application inside might still be connecting to the database or warming up. A readiness probe that checks a real /healthz endpoint keeps a Pod out of rotation until it can actually serve a request.
