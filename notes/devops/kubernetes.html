Kubernetes: running many containers reliably

3 min read No experience needed
💡
In plain English
You tell Kubernetes "I want three copies of this container running, always" and it makes that true — starting them, restarting the ones that crash, moving them off a machine that dies, and spreading them across the machines you have. You describe the desired state; Kubernetes' whole job is closing the gap between that and reality, continuously.

Four objects cover most of what you will actually touch.

ObjectWhat it is
PodThe smallest unit — one or more containers that always run together, on the same machine. Usually one container per Pod.
Deployment"Keep N copies of this Pod running, and here is how to roll out a new version." You almost never create a Pod directly — you create a Deployment and it manages Pods for you.
ServiceA stable network address for a set of Pods, which come and go and change IP addresses constantly. Other things talk to the Service, never to a Pod directly.
IngressRoutes traffic from outside the cluster (the internet) to the right Service inside it, usually by hostname or path.

yamldeployment.yaml — three replicas of the API, with resource limits
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/api:a1b2c3d      # the exact commit SHA, from CI
          ports:
            - containerPort: 8080
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef: { name: api-secrets, key: database-url }
          resources:
            requests: { cpu: "100m", memory: "128Mi" }   # what it's guaranteed
            limits:   { cpu: "500m", memory: "256Mi" }   # what it can't exceed
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 3
---
apiVersion: v1
kind: Service
metadata:
  name: api-service
spec:
  selector: { app: api }        # sends traffic to any Pod with this label
  ports:
    - port: 80
      targetPort: 8080
!
Always set resource requests and limits. Without them, one misbehaving Pod can consume an entire node's memory and take every other Pod on that machine down with it — the "noisy neighbour" failure, and it is the single most common way a Kubernetes cluster has a bad day. Without a readinessProbe, the Service starts sending traffic to a Pod before its process has actually finished starting up, and some fraction of requests fail for no reason a log will make obvious.

Kubernetes, or a managed container platform?

Cloud Run / Fargate / App ServiceKubernetes (GKE / EKS / AKS)
You manageNothing below the containerCluster shape, node upgrades, networking, scaling policy
Scales to zeroYesNo — nodes cost money even idle
Good forAlmost everything — one or a few servicesMany services, complex internal networking, a platform team to run it
Setup for "hello world"MinutesHours, and there is a cluster to keep patched afterwards
i
Teams often reach for Kubernetes because it is the well-known name, then spend the first few months operating a cluster instead of building the product. It earns its complexity once you have enough services that the orchestration itself becomes the hard problem — until then, a managed platform gives you the same "many containers, restarted automatically" guarantee for a fraction of the operational cost.
A Deployment says replicas: 3, but you only ever create or delete a Pod directly during testing. Two minutes later, three Pods are running again. Why?Answer

The Deployment is not describing what to do once — it is continuously reconciling reality against the desired state you gave it. Delete a Pod, and the Deployment notices the count dropped below 3 and starts a replacement immediately. This is the core idea of Kubernetes: you declare the end state, and a controller keeps making it true, indefinitely, without anyone re-running a command.
