Docker: packaging the app so it runs the same everywhere

2 min read No experience needed
💡
In plain English
"Works on my machine" is a real bug, not an excuse — it means the app depends on something about your laptop that production does not have. Docker's whole job is to remove that gap: you describe the exact environment the app needs once, in a file, and every machine that runs it — your laptop, the CI server, production — gets the identical thing.

An image is the packaged recipe — your code, the runtime, the dependencies, frozen. A container is a running instance of that image. You build one image and can start as many containers from it as you like, identical every time.

dockerfileDockerfile — a Node/Express API, multi-stage
# Stage 1: everything needed to INSTALL and BUILD, discarded afterwards.
FROM node:20-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: only what is needed to RUN. This is the image that ships —
# smaller image means a faster pull and a faster cold start.
FROM node:20-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist

EXPOSE 8080
CMD ["node", "dist/server.js"]
i
Order your Dockerfile from least to most likely to change. Docker caches each line as a layer and reuses the cache for every line above the first one that changed. Copying package*.json and running npm ci before copying the rest of the source means a source-only change reuses the cached, already-installed dependencies instead of reinstalling everything on every build. This one ordering choice is the difference between a ten-second rebuild and a two-minute one.

Local development: several containers, one command

A real app is rarely one container — it is an API, a database, maybe a frontend dev server. docker-compose.yml describes all of them together, so docker compose up gives every teammate the exact same local environment.

yamldocker-compose.yml — API + Postgres, for local development
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: devpassword
      POSTGRES_DB: quicktasks
    ports:
      - "5432:5432"
    volumes:
      - db-data:/var/lib/postgresql/data

  api:
    build: ./api                 # uses ./api/Dockerfile
    environment:
      DATABASE_URL: postgresql://postgres:devpassword@db:5432/quicktasks
    ports:
      - "8080:8080"
    depends_on:
      - db
    volumes:
      - ./api/src:/app/src        # live-reload: edit locally, see it inside the container

volumes:
  db-data:

Inside the Compose network, the API reaches the database at the hostname db — the service name — never localhost. That one detail catches almost everyone once.

Real world"Connection refused" that only happens inside Docker

The API's DATABASE_URL says localhost:5432. On your laptop this worked, because Postgres was running directly on it. Inside a container, localhost means that container itself — there is no Postgres listening there, only the API. The fix is always the same: point at the service name Compose (or Kubernetes) gives the other container, never localhost.

You change one line of application code and rebuild. It takes two minutes instead of the usual ten seconds. Why?Answer

Almost certainly the Dockerfile copies the whole source tree before installing dependencies, so any source change invalidates Docker's cache for the npm ci layer too, and every dependency reinstalls. Move COPY package*.json and RUN npm ci above COPY . ., and a source-only change no longer touches the dependency layer at all.
