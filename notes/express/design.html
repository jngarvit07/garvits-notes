Designing the API

2 min read Some experience helps
💡
In plain English
An API is a user interface for programmers, and it is judged the same way: is it predictable? Consistent naming, consistent shapes, consistent status codes, and errors that say what to do about them. The cost of getting this wrong is not aesthetic — it is every future developer, including you, having to look up how each endpoint behaves because none of them behave the same way.
Idempotent

Running it twice is the same as once. GET, PUT and DELETE should be; POST usually is not, which is why double-clicks create two of things.

Stateless

The server keeps no per-caller memory between requests. Everything needed arrives with the request.

Versioning

A prefix like /api/v1 so a breaking change can ship beside the old one instead of instead of it.

One error shape

Every failure looks the same on the wire, so the frontend has one thing to handle.

REST is a convention: the path names a thing, the method says what to do with it. Following it means a new endpoint is guessable rather than documented.

jsNouns in the path, verbs in the method
GET    /api/v1/projects            list
POST   /api/v1/projects            create
GET    /api/v1/projects/:id        read one
PATCH  /api/v1/projects/:id        change some fields
PUT    /api/v1/projects/:id        replace
DELETE /api/v1/projects/:id        remove

GET    /api/v1/projects/:id/versions      a sub-resource

# Not this — the verb belongs in the method:
POST   /api/v1/getProjectById
POST   /api/v1/deleteProject
StatusMeansUse for
200 / 201 / 204It worked201 when something was created, 204 when there is nothing to return
400The request is malformedMissing or invalid fields
401Not signed inMissing, expired or invalid token
403Signed in, not allowedOnly where the caller may know the thing exists — otherwise 404
404No such thingAlso: a record that is not yours
409ConflictAn email already registered; an edit against a stale version
422Understood, but unprocessableSemantic validation failures, where 400 feels too blunt
429Too many requestsRate limit hit
500We brokeNever for a bad request — that is the caller’s 400

Two more conventions worth adopting early: version the API in the path — this one is at /api/v1 — so a breaking change can ship alongside the old one rather than instead of it; and keep one error shape everywhere, so the frontend has a single thing to handle.
