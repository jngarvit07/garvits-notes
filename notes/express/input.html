Reading and validating input

2 min read Some experience helps
💡
In plain English
Input arrives in three places: in the address itself, in the query string after the question mark, and in the body of the request. All three come from outside your control, which means all three are claims rather than facts until you have checked them. Validation is where you turn a claim into something you are willing to act on.

Input arrives in four places and every one of them is written by whoever is calling you:

WhereReached byNotes
Pathreq.params.idFrom the pattern — /projects/:id.
Query stringreq.query.pageAlways strings, and can arrive as arrays if repeated. Convert deliberately.
Bodyreq.bodyUndefined unless a parser like express.json() ran.
Headers & cookiesreq.headers.authorizationHeader names are lower-cased for you.

Validate before you use any of it, at the edge, in one place — not scattered through the handler as a series of if statements that each forgot a case.

Not this · trusting the caller
router.patch('/:id', async (req, res) => {
  // Whatever was sent goes straight into the row —
  // including "role": "ADMIN" and "credits": 999999.
  const user = await db.user.update({
    where: { id: req.params.id },
    data: req.body,
  });
  res.json(user);
});
Do this · accept only what you meant
router.patch('/:id', async (req, res) => {
  const { name, email } = req.body;

  if (typeof name !== 'string' || name.trim().length === 0) {
    return res.status(400).json({ error: 'name is required' });
  }

  const user = await db.user.update({
    where: { id: req.params.id },
    data: { name: name.trim(), email },   // an explicit list of fields
  });
  res.json(user);
});
!
Mass assignment — the left-hand version above — is one of the most reliably exploitable bugs in any API. The caller does not need a form; they need one extra key in a JSON body. Name the fields you accept, every time.

Pagination belongs in this section too, because an endpoint that returns everything is fine for the first year and then is not. Take page and limit, clamp the limit to something sane, and return the total so the caller can draw the controls.

Your endpoint expects { quantity: 3 } and receives { quantity: "3; DROP TABLE orders" }. Where should that be stopped?Answer

At the edge, by a schema that says quantity is an integer between 1 and some maximum. It never reaches your business logic, so nothing downstream has to be defensive about it.

Validating at the boundary rather than at the point of use is what lets the rest of the codebase assume its inputs are sane. Scattering checks through the middle is how one gets missed.
