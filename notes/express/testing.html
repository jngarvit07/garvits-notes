Testing and debugging

2 min read Some experience helps
💡
In plain English
The useful test for an API is not “does this function return the right value” but “if I send this request, do I get the right response”. That kind of test goes through the real routing, the real middleware and the real validation, so it catches the wiring mistakes that unit tests step around entirely.

An HTTP API is unusually pleasant to test, because a test is just a request and an assertion about the answer. curl is enough to start.

jsPoking at it by hand
curl http://localhost:5000/api/v1/health

curl -X POST http://localhost:5000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"a@b.com","password":"secret"}'

curl http://localhost:5000/api/v1/projects \
  -H 'Authorization: Bearer eyJhbGciOi...'

# -i to see the status and headers; -v when you need the whole conversation.
  • A request hangs forever — some middleware neither responded nor called next(), or an async handler threw without a wrapper.
  • “Cannot set headers after they are sent” — two responses. Look for a missing return.
  • req.body is undefined — no body parser, or the caller did not send Content-Type: application/json.
  • A CORS error in the browser, but curl works — the browser is enforcing something curl does not. It is a configuration problem on the server, never a frontend one.
  • The wrong handler runs — route order; a parameterised path is shadowing a literal one.
Why is a test that sends a real HTTP request to your app usually worth more than a test that calls the route handler function directly?Answer

Because most bugs in an API are not inside the handler — they are in the wiring around it. Middleware in the wrong order, a validator not applied, an auth check missing on one route, a body parser absent. Calling the function directly bypasses every one of those and passes happily while the endpoint is broken.
