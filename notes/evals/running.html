Running them, and running them automatically

3 min read Some experience helps
💡
In plain English
A test set nobody runs is just a document. The value only appears when it runs automatically — on every change to a prompt, and on a schedule against the live system — so that a break is caught by your pipeline instead of by a customer.
tsevals/run.ts — small enough that it actually gets used
import cases from './cases/support-qa.json';
import { answer } from '../src/answer.js';
import { judgeGrounded } from './graders.js';

type Case = {
  id: string;
  question: string;
  expectedChunkId: string | null;   // null = not answerable from the corpus
  mustRefuse?: boolean;
};

const results = [];

for (const c of (cases as Case[])) {
  const out = await answer(c.question);

  // 1. Retrieval — exact, cheap, and the first thing to look at when a score drops.
  const retrieved = c.expectedChunkId === null
    ? true
    : out.chunkIds.includes(c.expectedChunkId);

  // 2. Refusal — does it decline when there is genuinely nothing to say?
  const refusedCorrectly = c.mustRefuse
    ? out.text.includes('I do not have that information')
    : true;

  // 3. Grounding — the only part that needs a model, and only if the rest passed.
  const grounded = retrieved && !c.mustRefuse
    ? await judgeGrounded(out.text, out.context)
    : true;

  results.push({ id: c.id, retrieved, refusedCorrectly, grounded });
}

const rate = (k: keyof (typeof results)[0]) =>
  (results.filter((r) => r[k]).length / results.length * 100).toFixed(0) + '%';

console.log(`retrieval  ${rate('retrieved')}`);
console.log(`refusal    ${rate('refusedCorrectly')}`);
console.log(`grounding  ${rate('grounded')}`);

// Fail the build on a regression. Thresholds are a ratchet: raise them as the
// system improves, never lower them to make a red build go green.
const failed = results.filter((r) => !r.retrieved || !r.grounded || !r.refusedCorrectly);
if (failed.length > 3) {
  console.error(`${failed.length} failures:`, failed.map((f) => f.id).join(', '));
  process.exit(1);
}
i

Run it on every change to a prompt, a model id, or the retrieval pipeline. Those three files are every bit as dangerous as a database migration, and they get a fraction of the attention. Wiring the test set into CI is what turns “we really should test this” into something that actually happens.

!

Running these tests costs real money, because they make real API calls. Keep the CI set small and quick — thirty to fifty cases — and run the big set overnight. A test suite that is too expensive to run is a test suite nobody runs.

Your grounding score is 95% and users still complain the answers are wrong. What is the eval missing?Answer

Most likely the search step, measured on its own. Grounding only asks “is this answer supported by the text we fetched?” — and an answer can be perfectly supported by the wrong chunk, scoring 95% while being useless. A high grounding score together with unhappy users is the classic sign of a search problem hiding behind a writing score.

The second suspect is having no refusal cases. If your set only has questions that can be answered, you have never measured what happens when your documents contain nothing — and confidently inventing an answer in that situation is what destroys trust fastest.

▶
Practice

Take any AI feature you already have. Open the logs, pull out thirty real inputs, and write down for each one what a good answer would look like. That is one afternoon of work, and it is the whole job.

Now run your current system against all thirty and count the results. Whatever number comes out is your real starting point — almost certainly lower than you expected — and from now on you can improve it on purpose instead of guessing.

✓ Worth remembering
  • Without a test set, every prompt change is a gamble and everything you break goes live quietly.
  • Thirty real cases beat three hundred made-up ones. Include the unclear, the hostile and the unanswerable.
  • Turn every reported bug into a case. That one habit builds up into your most valuable asset.
  • Use the simplest marker that works. Reach for a model examiner last, and check it against human marks first.
  • For RAG, score the search and the writing separately — one number cannot tell you which half is broken.
  • For agents, score the whole path: steps taken, tools chosen, cost, gates hit — not only the final answer.
  • Wire it into CI. Prompts and model ids are as dangerous as database migrations and get a fraction of the review.
