Why you cannot ship without this

2 min read Some experience helps

Ordinary code is deterministic: the same input gives the same output, so a test that passed yesterday means something today. A model gives you a distribution of outputs, and the distribution shifts when you change the prompt, the model version, the retrieval, or nothing at all.

💡
In plain English

Testing normal code is checking a calculator: 2 + 2 must be 4 every time. Testing a model is closer to marking exam papers — you cannot check for one exact string, you have to decide whether an answer is good, and you need enough papers that one lucky guess does not fool you.

An eval is that marking scheme, automated: a set of real inputs, a definition of a good outcome, and a score you can watch over time.

!

Without evals you are not engineering, you are gambling. Every prompt change becomes a vibe check on three examples somebody remembers. The regression you introduce on the fourth case ships, and you find out from a customer six weeks later — if at all.

What evals actually catch

ChangeWhat goes wrong without an eval set
You improve the prompt.It gets better on the case you were looking at and worse on two you were not. Nobody notices.
The model version updates.Behaviour your prompt quietly depended on changes. A newer model is better on average and not identical.
You switch to a cheaper model.You have no way to know whether the saving cost you anything, so you either never try it or try it blind.
You change chunking or retrieval.Answers get subtly less grounded. Nothing errors. Quality drifts down for a month.
Someone edits a tool description.The agent starts choosing the wrong tool in a class of cases nobody tests by hand.
