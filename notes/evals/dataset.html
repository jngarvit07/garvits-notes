Building the set — the part that matters

2 min read Some experience helps
💡
In plain English
An eval set is a collection of real cases with an agreed answer for each. This is the part people skip because it is unglamorous, and it is the part that determines whether any of it works. Twenty cases taken from things users actually asked are worth more than five hundred you invented, because invented cases are drawn from what you already thought of.

Almost all the value is here, and almost all the effort goes to the wrong place: people build elaborate scoring machinery on top of twelve examples they invented at their desk.

i

Your eval set is a real asset. Prompts get rewritten, models get replaced, frameworks come and go. The set of real cases with agreed-correct outcomes is the thing that stays valuable and gets more valuable every month. Keep it in the repository, next to the code it tests.

Where should the cases in an eval set come from?Answer

Real usage — logs, support tickets, the complaints. Especially the failures, because a set made only of cases you handle well cannot tell you when you have got worse.

Deliberately include the awkward ones: ambiguous questions, questions with no good answer, and questions the system should decline. A set of easy cases scores high and measures nothing.
