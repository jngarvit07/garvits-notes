PostgreSQL & Prisma

Where the data actually lives: tables, relations, SQL, indexes, transactions and migrations — and the layer this product uses to talk to them.

No experience needed 40 min read 11 sections

What a relational database is

Everything else in this stack forgets. Restart the server and its memory is empty; close the browser tab and the screen is gone. The database is the part that remembers, and it is the only part where a mistake cannot be fixed by deploying again.

💡
In plain English
A spreadsheet with rules that are actually enforced. Each sheet is a table with named columns; each row is one thing. The difference from a real spreadsheet is that the database refuses to accept a row that breaks its rules — you cannot type “maybe” into a date column, and you cannot delete a customer who still has orders.

Relational means rows point at other rows instead of repeating them. A project stores the id of its owner, not a copy of the owner’s name and email — so changing an email changes it everywhere at once, because there was only ever one copy.

jsTwo tables, one link
users
  id      email             name
  u_1     ada@example.com   Ada
  u_2     lin@example.com   Lin

projects
  id      name          user_id     <- points at users.id
  p_1     Portfolio     u_1
  p_2     Cafe menu     u_1
  p_3     Wedding       u_2

PostgreSQL is one particular relational database: free, extremely reliable, and unusually rich — JSON, full-text search, geographic data and vector search all live inside it, which means a lot of separate services never need to be added.

Tables, keys and constraints

A table is defined by its columns, each with a type that decides what may be stored and what may be done with it. Types are not paperwork: a date stored as text cannot be compared or sorted correctly, and finding that out later means rewriting every row.

TypeForNote
textAny stringIn Postgres there is no speed penalty over varchar(n). Use text.
integerWhole numbersCounts, ages.
numericMoney, exact decimalsNever use a float for money — 0.1 + 0.2 is famously not 0.3.
booleanTrue or falseAnd null, unless you forbid it.
timestamptzA moment in timeAlways the "tz" version. A timestamp without a zone is a number nobody can interpret.
uuidIdentifiersUnguessable, and generatable without asking the database.
jsonbStructured data with no fixed shapeIndexable and queryable, unlike plain json.
enumA fixed set of valuesThis product’s Role is one: USER or ADMIN, and nothing else is representable.

Constraints are the rules. They are the reason a database is trustworthy, and every one of them is a bug class that becomes impossible:

sqlA table with its rules
CREATE TABLE projects (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name        text NOT NULL,
  slug        text NOT NULL,
  is_public   boolean NOT NULL DEFAULT false,
  created_at  timestamptz NOT NULL DEFAULT now(),

  UNIQUE (user_id, slug),                    -- unique per owner, not globally
  CHECK (char_length(name) BETWEEN 1 AND 120)
);
ConstraintPrevents
PRIMARY KEYTwo rows you cannot tell apart. Every table needs one.
NOT NULLA missing value where the code will assume one exists.
UNIQUETwo accounts with the same email — the classic duplicate-signup bug.
REFERENCESA project owned by a user id that does not exist. This is the "foreign key".
CHECKValues that are the right type and still nonsense — a negative price, an empty name.
DEFAULTEvery insert having to remember to set the same thing.
!
Enforce it in the database, not only in the application. Application checks are skipped by an admin script, a data import, a second service, or a bug in one branch of an if-statement. The database check is skipped by nothing. Validate in both places — but if you only get one, this is the one.

ON DELETE CASCADE above answers a question every schema must answer: what happens to the children when the parent goes? Cascade deletes them. RESTRICT refuses to delete the parent. SET NULL orphans them deliberately. Choosing nothing means choosing whatever the default was, and finding out during a deletion.

The SQL you will actually write

Four statements cover almost everything. SQL reads like a sentence, which is the whole idea behind it.

sqlReading
SELECT id, email, created_at        -- name the columns; SELECT * in application code
FROM users                          -- breaks the day somebody adds one
WHERE is_active = true
  AND created_at > now() - interval '30 days'
ORDER BY created_at DESC
LIMIT 20;

-- Counting and grouping: "how many projects does each user have?"
SELECT user_id, count(*) AS project_count
FROM projects
GROUP BY user_id
HAVING count(*) > 5                 -- HAVING filters groups; WHERE filters rows
ORDER BY project_count DESC;
sqlWriting
INSERT INTO projects (user_id, name, slug)
VALUES ('u_1', 'Portfolio', 'portfolio')
RETURNING id, created_at;           -- Postgres hands back the row it just made

UPDATE projects
SET name = 'New name', updated_at = now()
WHERE id = 'p_1';                   -- forget the WHERE and you rename every project

DELETE FROM projects
WHERE id = 'p_1';
!
Run the WHERE as a SELECT first. An UPDATE or DELETE with a mistaken condition is instant and total. Select with the same condition, look at the count, then change the verb. In production, do it inside a transaction so a wrong number can be rolled back.

Two more worth knowing early. ON CONFLICT is the atomic insert-or-update — the correct way to do “create if missing” without a race between checking and inserting:

sqlUpsert
INSERT INTO settings (key, value)
VALUES ('theme', 'dark')
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;

Relations and joins

Three shapes cover essentially every relationship, and picking the wrong one is a schema problem you feel for years.

ShapeExample hereHow it is stored
One to manyA user has many projectsThe child holds the parent id: projects.user_id.
One to oneA user has at most one siteSame, plus a UNIQUE on the foreign key.
Many to manyComponents belong to many templatesA third table holding the two ids.

A join reads across a relationship — one query, one round trip, instead of a query per row.

sqlJoins
-- Every project, with its owner's email.
SELECT p.name, u.email
FROM projects p
JOIN users u ON u.id = p.user_id;        -- INNER: only rows with a match

-- Every user, and their projects if they have any.
SELECT u.email, p.name
FROM users u
LEFT JOIN projects p ON p.user_id = u.id;  -- keeps users with none; p.name is NULL

-- Users who have never made a project.
SELECT u.email
FROM users u
LEFT JOIN projects p ON p.user_id = u.id
WHERE p.id IS NULL;

The performance trap here has a name — the N+1 query — and it is the single most common cause of a page that is fine in development and unusable with real data.

Not this · 1 + 100 queries
const projects = await db.project.findMany();

for (const project of projects) {
  // One database round trip per project.
  project.owner = await db.user.findUnique({
    where: { id: project.userId },
  });
}
Do this · 1 query
const projects = await db.project.findMany({
  include: { user: true },
});

// Prisma fetches the related rows together
// instead of once per project.
i
It hides well: with ten test rows the loop version is imperceptibly slower. With ten thousand rows it is thousands of round trips, and the fix is one word. Any loop containing an await on the database deserves a second look.

Indexes: why queries are fast or slow

Without an index, answering “which user has this email” means reading every row. An index is a sorted structure the database maintains so it can jump straight there.

💡
In plain English
The index at the back of a book. Finding every mention of a word without one means reading the book. The index makes the lookup instant, costs some pages, and has to be reprinted whenever the book changes — which is exactly the trade-off, including the cost.
sqlAdding one, and proving it helps
CREATE INDEX idx_projects_user_id ON projects (user_id);

-- Ask Postgres what it will actually do:
EXPLAIN ANALYZE SELECT * FROM projects WHERE user_id = 'u_1';

-- "Seq Scan on projects"     -> reading every row. No usable index.
-- "Index Scan using idx_..." -> the index is being used.
  • Index what you filter, join and sort on. Foreign keys almost always deserve one; Postgres does not create them automatically.
  • Do not index everything. Every index must be updated on every write, so a table with twelve indexes is slow to insert into and expensive to keep.
  • Order matters in a composite index. An index on (user_id, created_at) helps a query filtering by user and sorting by date; it does not help one that only sorts by date.
  • UNIQUE creates an index for free. It has to, to check uniqueness.
A query filters on user_id and sorts by created_at. You add an index on (created_at, user_id). Why does it barely help?Answer

Composite indexes are ordered, like a phone book sorted by surname then first name. Sorted by created_at first, the rows for one user are scattered throughout, so the database still has to scan. (user_id, created_at) puts each user’s rows together and already in date order — the filter and the sort are both satisfied by one walk of the index.

Real worldWhat a missing index looks like from the outside

The admin Users screen loads in 80ms with fifty accounts and takes nine seconds with fifty thousand. Nothing in the code changed. The query filters on a column with no index, so the work grew with the table while the test data did not.

This is why EXPLAIN ANALYZE is worth learning before you need it: it is the difference between guessing and reading what the database says it did.

Transactions: all of it, or none of it

A transaction groups several statements so they either all happen or none do. It is the answer to “what if the server dies halfway through”.

jsThe canonical example
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'a';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'b';
COMMIT;      -- both, or ROLLBACK: neither. Money is never in flight.

The guarantees have a well-known acronym, and each letter is a real promise:

Means
AtomicAll of the statements, or none. There is no halfway.
ConsistentConstraints hold at the end. A transaction cannot leave broken rules behind.
IsolatedConcurrent transactions do not see each other’s half-finished work.
DurableOnce it commits, it survives the power going out.
Lock

A claim on a row while you change it. Other transactions touching the same row wait — which is correct, and why long transactions hurt.

Deadlock

Two transactions each holding what the other needs. Postgres kills one; the fix is to touch rows in a consistent order.

Race condition

Check-then-act with a gap. Two requests both see "no row yet" and both insert. Use a UNIQUE constraint or ON CONFLICT rather than checking first.

Isolation level

How much concurrent transactions can see of each other. The default is sensible; raise it only with a reason.

prismaIn Prisma
await prisma.$transaction(async (tx) => {
  const project = await tx.project.create({ data: { name, userId } });
  await tx.auditLog.create({
    data: { action: 'project.create', targetId: project.id, userId },
  });
  // Throw anywhere in here and both are undone.
});
!
Keep transactions short, and never await a network call inside one. An open transaction holds locks; other requests touching the same rows queue behind it. Calling an email provider inside a transaction means a slow provider becomes a database-wide stall. Do the database work, commit, then send the email.

What Postgres gives you beyond plain SQL

FeatureWhat it is for
jsonbStore a whole structure in one column — page content, settings — and still query inside it. This product keeps page structures this way, because their shape is defined by the editor, not by the schema.
arraysA list in a column: tags, allowed origins. Simpler than a side table when the list is short and never joined against.
enum typesA column that can only ever hold one of a fixed set. Illegal states become unrepresentable rather than merely discouraged.
full-text searchReal search — stemming, ranking, phrases — without adding a separate search service.
generated columnsA column computed from others and kept correct automatically.
pgvectorAn extension for storing embeddings and finding nearest neighbours. The foundation of retrieval for AI features — see the AI note.
LISTEN / NOTIFYLightweight pub-sub inside the database, for waking a worker when a row changes.
sqlQuerying inside JSON
-- Rows whose settings say the theme is dark
SELECT id FROM projects WHERE settings ->> 'theme' = 'dark';

-- Indexed, so it stays fast
CREATE INDEX idx_projects_settings ON projects USING gin (settings);
i
JSONB is a tool, not a shortcut. Anything you filter on, join on, or must guarantee the shape of belongs in a column with a type and a constraint. Put a user’s role in JSON and you have a permission system with no rules — the database cannot check what it does not model.

Changing the schema safely

The schema changes as the product does, and the change has to reach every environment in the same order. A migration is a recorded, versioned step: a file of SQL that has been applied, or has not.

sqlThe cycle with Prisma
# 1. Edit prisma/schema.prisma — add a field.
# 2. Generate a migration and apply it to the development database:
npx prisma migrate dev --name add_project_slug

# 3. It writes prisma/migrations/<timestamp>_add_project_slug/migration.sql
#    Read that file. It is what will run against real data.

# 4. In production, apply the recorded migrations — never 'migrate dev':
npx prisma migrate deploy
!
Never edit a migration that has already been applied. Databases record which ones they have run by name; changing an old file means the change never runs anywhere it has already been. Write a new migration instead — always forward, never sideways.

Some changes are safe on a live table and some hold a lock while every row is rewritten. The pattern for the dangerous ones is the same everywhere: expand, migrate, contract.

  1. Add the new column as nullable. Deploy. Nothing breaks — nothing uses it yet.
  2. Backfill it in batches, and write to both old and new from the application.
  3. Once every row has a value, add the NOT NULL.
  4. Only when nothing reads the old column any more, drop it.
i
In this product, production migrations are run by hand. Nothing in the deployment pipeline runs migrate deploy — it is npm run db:prod:status to see what is pending and npm run db:prod:migrate to apply it, both from backend/. Shipping code that expects a column before running the migration is therefore an outage you can cause yourself, and the order — migrate first, then deploy — matters.

Prisma: the layer this product actually types

Prisma is an ORM: you describe your tables once in a schema file, and it generates a typed client. Your editor then knows every model and field, and a typo is a build error instead of a runtime one.

prismaprisma/schema.prisma
model User {
  id        String    @id @default(cuid())
  email     String    @unique
  role      Role      @default(USER)
  isActive  Boolean   @default(true)
  createdAt DateTime  @default(now())

  projects  Project[]           // the other side of the relation

  @@index([email])
}

model Project {
  id       String @id @default(cuid())
  name     String
  userId   String
  user     User   @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}

enum Role {
  USER
  ADMIN
}
prismaQuerying
// One row
const user = await prisma.user.findUnique({ where: { email } });

// A page of rows, with a related record, choosing the fields
const projects = await prisma.project.findMany({
  where: { userId, name: { contains: search, mode: 'insensitive' } },
  select: { id: true, name: true, user: { select: { email: true } } },
  orderBy: { createdAt: 'desc' },
  skip: (page - 1) * 20,
  take: 20,
});

// Create, update, upsert
await prisma.project.create({ data: { name, userId } });
await prisma.project.update({ where: { id }, data: { name } });
await prisma.project.upsert({
  where: { id },
  create: { id, name, userId },
  update: { name },
});

// Counting and aggregating
const total = await prisma.project.count({ where: { userId } });

findManySELECT ... FROM ... WHERE ...
includeA join, or a second query — Prisma decides. Fetches the whole related row.
selectSELECT with named columns. Prefer it: fetching what you need is faster and leaks less.
skip / takeOFFSET and LIMIT.
$transactionBEGIN ... COMMIT.

!
Raw SQL must still be parameterised. Prisma’s $queryRaw tagged-template form is safe because the values travel separately from the query text. Building a query by concatenating strings — in any language, with any library — is how SQL injection happens, and it is the one mistake in this note that can hand over the entire database.
Not this · string concatenation
// email = "x'; DROP TABLE users; --"
const rows = await prisma.$queryRawUnsafe(
  "SELECT * FROM users WHERE email = '" + email + "'"
);
Do this · parameterised
const rows = await prisma.$queryRaw`
  SELECT * FROM users WHERE email = ${email}
`;
// The value is sent as a parameter, never as query text.

Backups, connections and safety

Real worldThe bug that only appears with real data

An admin screen lists every user with their project count. In development, with fifty accounts, it answers instantly. In production it times out — because the code fetched all users, then ran one count query per user. Fifty round trips is nothing; fifty thousand is a page nobody can open.

The fix is not a faster server. It is one grouped query, or a single Prisma call with the count included. Test on data the shape of production, or discover this on the day you cannot afford to.

  • A backup you have not restored is not a backup. The failure mode is always the same: backups ran for a year and nobody checked that the file could be read.
  • Connections are a limited resource. Postgres allows a fixed number; each serverless function that opens its own can exhaust them. A pooler sits in front and hands out a shared set — which is why this product’s schema declares both a pooled url and a directUrl, since migrations cannot run through a pooler.
  • Least privilege. The application user does not need to drop tables. A read-only account for analytics costs nothing and removes a whole category of accident.
  • Know which database your shell is pointed at. The most expensive database mistakes are not clever attacks; they are a correct command run against production because the terminal looked the same.
!
This repository has a scar to prove that last point. The Prisma schema names a shadowDatabaseUrl explicitly because leaving it unset means passing a URL on the command line every time — and prisma migrate diff wipes whatever it is handed. Passing the real development database there destroyed it once, in August 2026. The comment in prisma/schema.prisma says so, at length, on purpose.

The database in this product

  • backend/prisma/schema.prisma — every model, heavily commented. Start at User and follow the relations out.
  • backend/prisma/migrations/ — the history of every schema change, in order.
  • npm run db:studio — a browser view of the development data. The fastest way to understand a schema is to look at real rows in it.
  • npm run db:prod:status — what is pending in production. Safe: it reads.
▶
Practice
  1. Open db:studio, find your own user row, and follow it to a project. That is a foreign key, in the flesh.
  2. In psql or a SQL console, write a query that returns each user’s email and their project count, highest first. You will need a LEFT JOIN, GROUP BY and ORDER BY.
  3. Run EXPLAIN ANALYZE on it. Find whether any step says Seq Scan, and on which table.
  4. Add a field to a model in the schema, run migrate dev, and read the generated SQL before it runs. Then revert both.
✓ Worth remembering
  • The database is the only layer where a mistake is permanent — put the rules in it.
  • Constraints prevent bad rows; application checks only discourage them.
  • Index what you filter, join and sort on; prove it with EXPLAIN ANALYZE.
  • A loop with an await on the database is an N+1 query waiting for real data.
  • Migrations only go forward, and in production here they are run by hand, first.
