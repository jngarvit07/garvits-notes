Node.js

JavaScript outside the browser, and the one idea — never wait, never block — that the whole thing is built on. Everything on this product's server runs inside it.

No experience needed 35 min read 11 sections

What Node.js is

JavaScript was invented to run inside a browser tab. Node.js is that same language taken out of the tab and given a computer instead: it can read files, open network connections, talk to a database and listen for requests. Nothing about the language changes; what changes is what it is allowed to touch.

💡
In plain English
A browser is a locked room with a window. JavaScript in there can rearrange the furniture and shout through the glass, and that is all. Node.js is the same person, outside, with keys to the building.
In a browserIn Node.js
window, document, the DOMprocess, fs, http, the filesystem and network
Cannot read your filesCan read and write any file the process has rights to
Sandboxed away from secretsHolds the secrets — database URLs, API keys, signing keys
One copy per tab, per visitorOne process, serving everybody at once

That last row is the one with consequences. A browser tab holds one person’s data; a Node process holds a variable that every request can see. Storing “the current user” in a module-level variable works flawlessly while you are the only person testing, and hands one customer another customer’s data the moment two requests overlap.

The event loop: one worker who never waits

Node runs your JavaScript on one thread. One. Ten thousand people can be connected and there is still a single line of execution — which sounds like a crippling limitation and is the reason Node is good at what it does.

💡
In plain English
A good waiter with twenty tables does not stand beside table four while the kitchen cooks. They take the order, hand it to the kitchen, and go to table five. When the food is ready the kitchen calls them back. One waiter, twenty tables, because the waiting is done by somebody else. Node’s kitchen is the operating system: disks, networks, databases.

So the rule that governs everything: never make the waiter stand still. Anything slow must be handed off, not waited on. Handing off is what await does — it says “come back to this line when the answer arrives” and lets the thread go do other work in the meantime.

jsWhat the single thread means, concretely
// SLOW, but fine. The thread is free the whole time it waits.
const user = await db.user.findUnique({ where: { id } });   // 40ms, handed off

// FAST to write, catastrophic to run. This is arithmetic, not waiting:
// nothing can hand it off, so every other request in the process is frozen
// until it finishes.
let total = 0;
for (let i = 0; i < 5_000_000_000; i++) total += i;          // ~10s of frozen server
!
Blocking the loop stops the entire server, not one request. Health checks fail, every connected user hangs, and the process looks alive to your monitoring the whole time. The usual culprits are real work rather than silly loops: parsing a 200 MB JSON file, resizing an image, hashing a password with too high a cost factor, or a regular expression that backtracks. Anything CPU-heavy belongs in a worker thread or a separate service.

The same rule explains the fs.readFileSync family. Every synchronous API in Node stops the world while it runs. They are there for start-up — reading a config file once before the server listens — and are a bug anywhere inside a request.

Not this · blocking inside a request
app.get('/report', (req, res) => {
  // Every other user waits for this disk read.
  const data = fs.readFileSync('./big.csv', 'utf8');
  res.send(summarise(data));
});
Do this · handed off
app.get('/report', async (req, res) => {
  // The thread serves other people while the disk works.
  const data = await fs.promises.readFile('./big.csv', 'utf8');
  res.send(summarise(data));
});

Promises and async/await

A promise is a receipt for a value that does not exist yet. It is in one of three states — pending, fulfilled with a value, or rejected with an error — and it never goes back.

async and await are the readable way to use them. await pauses this function until the promise settles, without pausing the thread; async marks a function as one that can do that, and makes it return a promise.

jsThe same operation, three generations of syntax
// 1. Callbacks — how Node started. Nesting grows sideways forever.
fs.readFile('a.txt', 'utf8', (err, data) => {
  if (err) return done(err);
  db.save(data, (err2, row) => {
    if (err2) return done(err2);
    done(null, row);
  });
});

// 2. Promises — flat, but the flow is still written backwards.
fs.promises.readFile('a.txt', 'utf8')
  .then((data) => db.save(data))
  .then((row) => done(null, row))
  .catch(done);

// 3. async/await — reads top to bottom, errors use try/catch.
try {
  const data = await fs.promises.readFile('a.txt', 'utf8');
  const row = await db.save(data);
} catch (error) {
  // every failure above lands here
}

Sequential awaits are the most common accidental slowdown in a codebase. Three independent queries awaited on three lines take the sum of their times; run together they take the longest of them.

Not this · 300ms — one after another
const user = await getUser(id);        // 100ms
const sites = await getSites(id);      // 100ms
const usage = await getUsage(id);      // 100ms
// None of them needed the others' results.
Do this · 100ms — all at once
const [user, sites, usage] = await Promise.all([
  getUser(id),
  getSites(id),
  getUsage(id),
]);
A request handler calls await save(draft) but the response says success while nothing was written. What is the likeliest cause?Answer

An await missing somewhere further in: a promise was created, never waited on, and the function returned before the write finished. Nothing throws, nothing logs, and it usually only shows up under load or on a slow database — which is why the habit of awaiting or explicitly writing void promise.catch(log) matters more than it looks.

CombinatorSettles whenUse for
Promise.allAll succeed, or the first one failsWork you need every result of
Promise.allSettledAll finish, however they finishBest-effort fan-out where one failure must not sink the rest
Promise.raceThe first one settlesTimeouts: race the real work against a timer
Promise.anyThe first one succeedsSeveral sources, any answer will do
!
A promise nobody awaits is a bug with no error message. Forget the await on a save and the function returns before the write happens: the response says success, the data is not there, and if it later rejects you get an unhandled rejection that can take the process down. If you deliberately do not want to wait, say so — void doThing().catch(log) — so the next reader knows it was a decision.

Modules, npm and package.json

A file is a module. It shares things by exporting them and uses other files by importing them. There are two systems, and mixing them up produces the single most confusing class of Node error.

CommonJS (older)ES Modules (current)
Importconst x = require('./x')import x from './x.js'
Exportmodule.exports = xexport default x
Turned on byThe default"type": "module" in package.json
File extension in importsOptionalRequired — and it is the compiled .js, even from TypeScript
i
This product’s backend is ES Modules, which is why its imports read import app from './app.js' even though the file on disk is app.ts. The extension names the file that will exist after the build, not the one you are editing. Dropping it is an error that only appears when you run the built output — a genuinely annoying half hour if nobody warned you.

npm is the package manager: npm install express downloads a library into node_modules/ and records it in package.json.

tsWhat the fields mean
{
  "type": "module",              // ES Modules, as above
  "scripts": {
    "dev": "tsx watch src/index.ts",   // npm run dev
    "build": "tsc",
    "start": "node dist/index.js"
  },
  "dependencies": {              // needed to RUN in production
    "express": "^4.18.2"
  },
  "devDependencies": {           // needed only to BUILD or test
    "typescript": "^5.0.0"
  }
}

The ^ is a version range: ^4.18.2 accepts any 4.x from 4.18.2 up, on the promise that those releases do not break anything. package-lock.json records the exact versions that were actually installed, which is why it is committed and why npm ci — install exactly the lock file — is what runs in a deployment.

!
A dependency in the wrong section fails at the worst time: put a build-only tool in dependencies and the production image is fat but works; put a runtime library in devDependencies and everything passes locally, then crashes on the deployed server with “cannot find module”.

Never use Math.random() for anything security-related. It is fast and predictable — fine for shuffling, useless for a password-reset token, an invitation code or a session id. crypto.randomBytes and crypto.randomUUID exist for exactly this.

Streams and buffers

A buffer is a chunk of raw bytes — an image, a PDF, anything that is not text. A stream is data that arrives or leaves a piece at a time instead of all at once.

💡
In plain English
Reading a file normally is filling a bucket at the tap and then carrying it. Streaming is connecting a hose. For a glass of water it makes no difference; for a swimming pool, the bucket approach means finding a bucket the size of a swimming pool — which, on a server, is your memory.
Not this · a 2 GB file in memory
// Loads the entire file before sending a single byte.
// Two people doing this at once can exhaust the server.
const file = await fs.readFile('./huge.zip');
res.send(file);
Do this · streamed through
// Constant memory, whatever the size, and the download
// starts immediately.
createReadStream('./huge.zip').pipe(res);

Streams are why an upload limit exists in the first place. This product sets express.json({ limit: '10mb' }): without a limit, one request with a large body is a way to exhaust the server’s memory on purpose.

Configuration and the process lifecycle

Configuration comes from the environment, not from the code, so the same build can run against a development database on your machine and a real one in production without being edited. process.env is how you read it.

jsValidate configuration at boot, not at 3am
const required = ['DATABASE_URL', 'JWT_SECRET'];
const missing = required.filter((name) => !process.env[name]);

if (missing.length > 0) {
  // Refuse to start. A server that boots without a signing secret
  // is a server that fails on its first login instead of its first second.
  console.error('Missing environment variables: ' + missing.join(', '));
  process.exit(1);
}

const port = Number(process.env.PORT ?? 5000);

A server is a long-running process, and it needs to end properly. When a platform deploys a new version it sends SIGTERM and waits: a well-behaved process stops accepting new connections, lets the in-flight ones finish, closes the database pool and exits.

prismaGraceful shutdown
const server = app.listen(port);

process.on('SIGTERM', async () => {
  server.close(async () => {        // stop taking new requests, drain the current ones
    await prisma.$disconnect();
    process.exit(0);
  });
});
i
Without this, a deployment cuts off whatever was mid-flight. Usually that is a page load somebody retries. Occasionally it is a payment or a publish, and “occasionally” is doing a lot of work in that sentence.

The errors that actually kill servers

There are three, and they are all quiet until they are not.

  1. An unhandled promise rejection. A promise fails and nothing catches it. On modern Node this terminates the process by default.
  2. An error thrown inside an async handler. The framework never sees it, so the request hangs until it times out — no response, no log, nothing in the error tracker.
  3. An error thrown in a callback or a timer. There is no try block up the stack to catch it, because the stack it was created on is long gone.
jsThe safety net at the top of the process
process.on('unhandledRejection', (reason) => {
  logger.error({ reason }, 'unhandled rejection');
  process.exit(1);   // deliberate: an unknown state is worse than a restart
});

process.on('uncaughtException', (error) => {
  logger.error({ error }, 'uncaught exception');
  process.exit(1);
});
!
These handlers are for logging then exiting, not for carrying on. After an uncaught exception the process is in a state nobody reasoned about: half-written files, open transactions, listeners that will never fire. Log it, exit, let the platform start a clean one. A process that swallows these and continues is how a service ends up serving wrong answers for hours.

Logging is part of error handling, not separate from it. console.log is fine while you are developing and poor in production: no levels, no timestamps, no structure to search on. A structured logger prints JSON that a log tool can filter — and it lets you attach a request id so one user’s journey can be pulled out of a million lines.

!
Never log secrets. Logging a whole request body captures passwords and tokens, logs are kept for months, and they are readable by more people than the database is. Log the fields you need by name rather than the object.

Performance and scaling

One Node process uses one CPU core. A machine with four cores running one process is leaving three quarters of the machine idle.

ToolWhat it doesWhen
clusterForks one process per core, sharing the same portThe default way to use the whole machine
worker_threadsA real thread for CPU workImage processing, big parses — anything that would block the loop
A queueMoves slow jobs out of the request entirelySending email, publishing a site, generating a report
A cacheStops recomputing what has not changedAnything expensive and repeatedly asked for
Concurrency

Many things in progress at once, one at a time. What the event loop gives you for free.

Parallelism

Many things actually running at once. Needs cluster or worker threads.

Blocking

Work that will not yield. The only thing that can genuinely break the model.

Backpressure

Slowing intake when you cannot keep up — the reason streams exist rather than buffers.

Real worldWhy publishing a site is a job here, not a request

Publishing builds files and pushes them to a hosting provider. Done inside the request, the browser waits half a minute on a connection that may time out, a retry starts the whole thing twice, and the user learns nothing about progress.

So this product records a PublishJob, answers immediately with its id, and works through it separately — writing PublishJobEvent rows the screen can poll. The rule generalises: if it can take longer than a few seconds, it is a job, not a request.

Security basics

  • Secrets live in the environment, never in the repository. A key committed once is in the history forever; the fix is rotation, not deletion.
  • Never build a shell command from user input. exec('convert ' + filename) with a filename somebody chose is a way to run their commands on your server. Use the argument-array form, which never goes through a shell.
  • Treat every input as hostile — body, query, headers, cookies, uploads. Validate shape and size before use.
  • Keep dependencies current. npm audit lists known holes in what you installed. Most real Node compromises come through a package, not through your code.
  • Run as an unprivileged user. Root in a container is still root when something escapes the process.

Practice
  1. Write a file that reads its own source with fs/promises and prints the line count. Run it with node. That is the whole loop: no framework, no build.
  2. Add a 5-billion-iteration for loop before the read, and notice that nothing else in the process happens until it ends. That is the event loop, blocked.
  3. Fetch three URLs sequentially with await, time it, then switch to Promise.all and time it again.
✓ Worth remembering
  • Node is JavaScript with access to the machine — including every secret you hold.
  • One thread serves everybody, so slow work must be awaited and CPU work moved out.
  • Independent awaits belong in Promise.all; a forgotten await is a silent bug.
  • Validate configuration at boot and shut down gracefully on SIGTERM.
  • Log, then exit, on an uncaught error. Do not carry on in an unknown state.
