What to log on every call

2 min read Some experience helps
💡
In plain English
This is the highest-value habit in the note, because it is the one thing you cannot add retrospectively. Every question you will later want to answer — why was this answer wrong, what does this feature cost, when did quality drop — is only answerable if the data was written down at the time.

This is the highest-value thing in the note. Everything downstream — debugging, cost analysis, evaluation, incident response — is possible only if the data was captured at the time. You cannot go back and add it.

tsOne structured line per model call
log.info('llm.call', {
  // Who and what — so you can group by anything later.
  trace_id:   'req_8f3a...',    // ties every step of ONE request together
  user_id:    hash(userId),     // hashed: enough to group, not to identify
  feature:    'support_reply',  // WHICH feature — the field people forget
  env:        'production',

  // The exact configuration. Without these, a regression is unattributable.
  model:      'claude-sonnet-5',
  prompt_ver: 'support_reply@v7',
  temperature: 0.2,

  // The numbers.
  tokens_in:  1840,
  tokens_out: 260,
  latency_ms: 2310,
  cached:     false,

  // The outcome.
  status:     'ok',             // ok | invalid_shape | refused | error | timeout
  finish:     'stop',           // stop | length | tool_use

  // For RAG: which passages were used. This is what separates a
  // retrieval failure from a generation failure, and it is the single
  // most useful field in the whole line.
  chunk_ids:  ['doc_41#p3', 'doc_88#p1'],

  // Tool calls, if any.
  tools:      [{ name: 'lookup_order', ms: 120, ok: true }],
});
i
prompt_ver and feature are the two fields teams add late and wish they had added first. Without feature, your token spend is one undifferentiated number. Without prompt_ver, you cannot say “quality dropped when we shipped v7” — you can only say it dropped.

What about the prompt and the answer themselves?

They are enormously useful for debugging and are also the most sensitive thing you handle. Decide deliberately rather than by default:

ApproachWhen it fits
Log both in fullInternal tools, no personal data, short retention. Easiest to debug.
Log a hash and the lengthYou can tell whether two calls were identical and spot truncation, without storing content.
Log a redacted versionRun PII detection first, replace what it finds. Costs latency; catches most but not all.
Sample — store 1% in fullThe pragmatic answer for most production systems: enough examples to debug, a fraction of the exposure.
!
Whatever you choose, write it in the privacy policy and set a retention period that something actually enforces. “We log prompts for debugging” with no expiry means you have an indefinite archive of whatever your users typed, which is a liability that grows on its own. See the Governance note.
