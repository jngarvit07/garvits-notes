Prompts are code, so version them like code

2 min read Some experience helps
💡
In plain English
A prompt decides what your system does, which makes editing one a behaviour change. It therefore needs what any behaviour change needs: a diff someone reviewed, a version number, a test that ran, and a way back. A prompt living as a string in the middle of a function has none of those.

A prompt determines what your system does. Changing one is a behaviour change. It therefore needs everything a behaviour change needs: a diff, a review, a version, a test, and a way back.

Not this · a string in the middle of a function
const res = await llm({
  system: `You are a helpful support agent.
    Be concise. Never promise a refund.`,
  ...
});

// Which version is in production?
// Who changed it and why?
// What did it say last Tuesday?
// How do you put the old one back?
Do this · a versioned, testable object
// prompts/support_reply.v7.ts
export default {
  id: 'support_reply',
  version: 7,
  model: 'claude-sonnet-5',
  temperature: 0.2,
  system: readFile('./support_reply.v7.md'),
  // The eval set that must pass before
  // this version may ship.
  evals: './support_reply.cases.jsonl',
};

The rules that make this work

In the repository, not a database

A prompt in a database can be changed without review, without a diff, and without a deploy — which sounds like agility and is actually an unreviewable production change. Keep them in git. If non-engineers must edit them, give them a pull request, not a text box wired to production.

The version is logged on every call

This is what makes a regression attributable. “Quality dropped on the 14th” plus “v7 shipped on the 14th” is an answer. Without the version it is a mystery.

The model id is pinned

Never point at a moving alias in production. Pin the specific dated version, upgrade deliberately, and run your evals against the new one before you switch. A model that changes under you is a change you did not make and cannot roll back.

Evals gate the merge

A prompt change with no eval run is a guess deployed to users. This is the AI equivalent of merging without running tests, and it should feel equally uncomfortable.

!
Watch for silent model changes. If you call gpt-4o or any other unpinned alias, the model behind that name changes over time. Your prompt was tuned against one set of behaviours and is now running against another. Pin the dated identifier, and treat upgrading it as a change that goes through the same gates as a prompt edit.
Why pin an exact dated model version rather than a friendly alias like the latest one?Answer

Because an alias moves. The model behind it is updated, your prompt was tuned against the old behaviour, and your system changes without anyone deploying anything — so there is no diff to look at and nothing to roll back to.

Pin the dated version and treat upgrading it as a change that goes through the same review and the same eval run as a prompt edit. It converts a silent change into a deliberate one.
