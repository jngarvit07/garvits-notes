What happens when you press send

2 min read Read the AI note first
💡
In plain English
Generating a response is two phases with very different characters. First the model reads your entire prompt — all at once, in parallel, fast. Then it writes the answer one token at a time, each one requiring a full pass through the network. That is why the first word takes a moment and the rest stream out smoothly, and it is why output tokens cost several times what input tokens cost.

Three consequences worth designing around

Output costs more than input

Prefill is parallel; decode is one expensive pass per token. That is the cost difference, and it means “be concise” in a prompt is a genuine budget lever, not just a style preference.

Long chats get slower every turn

Each turn re-reads the entire conversation. Turn twenty pays for turns one to nineteen again. Summarising old turns is not tidiness — it is the fix for a cost curve that only goes up.

Prompt caching is caching the KV cache

Providers can keep the computed state for an unchanged prefix. Put your long, stable system prompt and your fixed examples first and the variable part last, and you stop paying to re-read them.

Streaming changes the felt experience, not the total

The same tokens take the same time. Showing them as they arrive turns eight seconds of nothing into eight seconds of visible progress, which users rate very differently.

i
A concrete prompt-caching layout. Order your messages as: system prompt, then long fixed instructions, then few-shot examples, then retrieved passages, then the user's question. Everything before the first thing that changes can be cached. Reversing that order — question first — makes the cache useless, and it is a one-line difference.
