The rest of the risk surface

3 min read Some experience helps
💡
In plain English
Injection gets all the attention, but it is not the whole picture. Data leaking out through a model's answers, someone running up your bill by making it do expensive work, libraries nobody checked, and information sitting in logs where nobody ever set a deletion date. Less dramatic, and every one of them has actually happened to somebody.

Injection takes over the conversation, but these are the ones that show up in real incident reports right beside it.

RiskWhat it looks likeWhat to do
Sensitive data disclosureSecrets, other users' records, or internal documents turning up in an answer — usually because they were in the searchable pile of documents in the first place.Filter when you index, not when you answer. Apply the user's permissions to the search itself, so they can only match documents they are allowed to read.
Excessive agencyAn agent with wide access doing something drastic while correctly following a bad instruction.Narrow tools, limited credentials, confirmation gates, and hard limits on the number of steps.
Insecure output handlingModel output shown as HTML, run as code, or glued into a query.Escape it when you display it. Use query parameters. Never eval it. Treat it exactly like input from a form.
Supply chainAn MCP server, prompt template or model from a source you do not trust. Tool descriptions that the model follows can change in an auto-update.Pin versions, review what a connector can reach, prefer first-party sources.
Unbounded consumptionExpensive requests running in a loop — either an attack or a bug. The bill is how you find out.Rate limit per user, cap tokens per request, cap steps per run, and raise an alert on spending.
Training on your dataInputs retained and used to improve a model.Read the terms. Business API terms are usually different from consumer app terms — check which one you are actually on.
OverreliancePeople acting on confident output that nobody checked. The most common real-world harm, and the least talked about.Show the sources. Show what was fetched. Make it easy to check, and make "I don't know" an acceptable answer.
Your coding agent reads GitHub issues and can open pull requests. Which of the three ingredients are present, and what is the cheapest fix?Answer

All three. Issues are untrusted content that anybody can write. The agent has access to the repository — the source code, and quite possibly the CI secrets too. A pull request is a way out, and so is any network call the code it writes can make.

The cheapest fix that works is the third ingredient: a pull request is already a human-reviewed gate, so make sure it really is one — no auto-merge, no CI that runs untrusted code with real secrets, and no secrets available to workflows started from a fork. Restricting what the agent's environment can reach on the network is the next cheapest.

What does not work is a system prompt telling it to be careful about the text in issues.
