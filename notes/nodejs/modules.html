Modules, npm and package.json

2 min read No experience needed
💡
In plain English
A module is one file that decides what it lets other files see. package.json is the list of every outside package your project depends on, and the lock file beside it records the exact versions that were actually installed — which is what makes the same code behave the same on your laptop and on a server.

A file is a module. It shares things by exporting them and uses other files by importing them. There are two systems, and mixing them up produces the single most confusing class of Node error.

This product’s backend is ES Modules, which is why its imports read import app from './app.js' even though the file on disk is app.ts. The extension names the file that will exist after the build, not the one you are editing. Dropping it is an error that only appears when you run the built output — a genuinely annoying half hour if nobody warned you.

npm is the package manager: npm install express downloads a library into node_modules/ and records it in package.json.

tsWhat the fields mean
{
  "type": "module",              // ES Modules, as above
  "scripts": {
    "dev": "tsx watch src/index.ts",   // npm run dev
    "build": "tsc",
    "start": "node dist/index.js"
  },
  "dependencies": {              // needed to RUN in production
    "express": "^4.18.2"
  },
  "devDependencies": {           // needed only to BUILD or test
    "typescript": "^5.0.0"
  }
}

The ^ is a version range: ^4.18.2 accepts any 4.x from 4.18.2 up, on the promise that those releases do not break anything. package-lock.json records the exact versions that were actually installed, which is why it is committed and why npm ci — install exactly the lock file — is what runs in a deployment.

!
A dependency in the wrong section fails at the worst time: put a build-only tool in dependencies and the production image is fat but works; put a runtime library in devDependencies and everything passes locally, then crashes on the deployed server with “cannot find module”.
Why commit the lock file when package.json already lists the dependencies?Answer

Because package.json usually names a range — “version 4 point anything” — so two installs a month apart can produce different code. The lock file pins the exact version of every package, including the packages your packages depend on.

Without it, “works on my machine” becomes a real and very hard-to-diagnose category of bug, because the difference is not in anything you wrote.
