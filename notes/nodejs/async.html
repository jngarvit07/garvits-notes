Promises and async/await

2 min read No experience needed
💡
In plain English
A promise is a receipt. You order a coffee, you get a ticket, and you carry on with your morning instead of standing at the counter. Later the ticket is exchanged for the coffee — or for an apology that the machine is broken. await is standing still until your ticket is called; the point of a promise is that you did not have to.

A promise is a receipt for a value that does not exist yet. It is in one of three states — pending, fulfilled with a value, or rejected with an error — and it never goes back.

async and await are the readable way to use them. await pauses this function until the promise settles, without pausing the thread; async marks a function as one that can do that, and makes it return a promise.

jsThe same operation, three generations of syntax
// 1. Callbacks — how Node started. Nesting grows sideways forever.
fs.readFile('a.txt', 'utf8', (err, data) => {
  if (err) return done(err);
  db.save(data, (err2, row) => {
    if (err2) return done(err2);
    done(null, row);
  });
});

// 2. Promises — flat, but the flow is still written backwards.
fs.promises.readFile('a.txt', 'utf8')
  .then((data) => db.save(data))
  .then((row) => done(null, row))
  .catch(done);

// 3. async/await — reads top to bottom, errors use try/catch.
try {
  const data = await fs.promises.readFile('a.txt', 'utf8');
  const row = await db.save(data);
} catch (error) {
  // every failure above lands here
}

Sequential awaits are the most common accidental slowdown in a codebase. Three independent queries awaited on three lines take the sum of their times; run together they take the longest of them.

Not this · 300ms — one after another
const user = await getUser(id);        // 100ms
const sites = await getSites(id);      // 100ms
const usage = await getUsage(id);      // 100ms
// None of them needed the others' results.
Do this · 100ms — all at once
const [user, sites, usage] = await Promise.all([
  getUser(id),
  getSites(id),
  getUsage(id),
]);
A request handler calls await save(draft) but the response says success while nothing was written. What is the likeliest cause?Answer

An await missing somewhere further in: a promise was created, never waited on, and the function returned before the write finished. Nothing throws, nothing logs, and it usually only shows up under load or on a slow database — which is why the habit of awaiting or explicitly writing void promise.catch(log) matters more than it looks.

CombinatorSettles whenUse for
Promise.allAll succeed, or the first one failsWork you need every result of
Promise.allSettledAll finish, however they finishBest-effort fan-out where one failure must not sink the rest
Promise.raceThe first one settlesTimeouts: race the real work against a timer
Promise.anyThe first one succeedsSeveral sources, any answer will do
!
A promise nobody awaits is a bug with no error message. Forget the await on a save and the function returns before the write happens: the response says success, the data is not there, and if it later rejects you get an unhandled rejection that can take the process down. If you deliberately do not want to wait, say so — void doThing().catch(log) — so the next reader knows it was a decision.
