Configuration and the process lifecycle

2 min read No experience needed
💡
In plain English
Configuration is what differs between your laptop and the live server. Keeping it outside the code means one codebase runs everywhere. The lifecycle half of this is what happens when the server is asked to stop: a well-behaved process finishes the requests it is already handling before it exits, rather than dropping them.

Configuration comes from the environment, not from the code, so the same build can run against a development database on your machine and a real one in production without being edited. process.env is how you read it.

jsValidate configuration at boot, not at 3am
const required = ['DATABASE_URL', 'JWT_SECRET'];
const missing = required.filter((name) => !process.env[name]);

if (missing.length > 0) {
  // Refuse to start. A server that boots without a signing secret
  // is a server that fails on its first login instead of its first second.
  console.error('Missing environment variables: ' + missing.join(', '));
  process.exit(1);
}

const port = Number(process.env.PORT ?? 5000);

A server is a long-running process, and it needs to end properly. When a platform deploys a new version it sends SIGTERM and waits: a well-behaved process stops accepting new connections, lets the in-flight ones finish, closes the database pool and exits.

prismaGraceful shutdown
const server = app.listen(port);

process.on('SIGTERM', async () => {
  server.close(async () => {        // stop taking new requests, drain the current ones
    await prisma.$disconnect();
    process.exit(0);
  });
});
i
Without this, a deployment cuts off whatever was mid-flight. Usually that is a page load somebody retries. Occasionally it is a payment or a publish, and “occasionally” is doing a lot of work in that sentence.
Why should a server read and validate all its configuration at startup rather than when each value is first needed?Answer

So that a missing or malformed value stops the process immediately, loudly, before any traffic reaches it. The alternative is a server that starts fine and then fails hours later on the first request that happens to need the value nobody set — at which point the failure is a user-facing 500 rather than a failed deploy.

The general principle: fail at the earliest moment you can detect the problem, because that is when it is cheapest and clearest.
