The errors that actually kill servers

2 min read No experience needed
💡
In plain English
In Node, an error in the wrong place does not produce a broken page — it can take the whole server down, disconnecting every user, not just the one whose request failed. That is the price of one process serving everybody. This topic is the short list of the mistakes that actually cause it.

There are three, and they are all quiet until they are not.

  1. An unhandled promise rejection. A promise fails and nothing catches it. On modern Node this terminates the process by default.
  2. An error thrown inside an async handler. The framework never sees it, so the request hangs until it times out — no response, no log, nothing in the error tracker.
  3. An error thrown in a callback or a timer. There is no try block up the stack to catch it, because the stack it was created on is long gone.
jsThe safety net at the top of the process
process.on('unhandledRejection', (reason) => {
  logger.error({ reason }, 'unhandled rejection');
  process.exit(1);   // deliberate: an unknown state is worse than a restart
});

process.on('uncaughtException', (error) => {
  logger.error({ error }, 'uncaught exception');
  process.exit(1);
});
!
These handlers are for logging then exiting, not for carrying on. After an uncaught exception the process is in a state nobody reasoned about: half-written files, open transactions, listeners that will never fire. Log it, exit, let the platform start a clean one. A process that swallows these and continues is how a service ends up serving wrong answers for hours.

Logging is part of error handling, not separate from it. console.log is fine while you are developing and poor in production: no levels, no timestamps, no structure to search on. A structured logger prints JSON that a log tool can filter — and it lets you attach a request id so one user’s journey can be pulled out of a million lines.

!
Never log secrets. Logging a whole request body captures passwords and tokens, logs are kept for months, and they are readable by more people than the database is. Log the fields you need by name rather than the object.
Why is a rejected promise with no catch more dangerous in Node than a thrown error in a browser?Answer

In a browser the damage is contained to one person’s tab. In Node, one process is serving every user at once, so an unhandled rejection that terminates the process disconnects all of them. A bug on one rare code path becomes a full outage.

That is why every async path needs an error handler, and why a top-level handler that logs and exits deliberately — rather than crashing at random — is worth having.
