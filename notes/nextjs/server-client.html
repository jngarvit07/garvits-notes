Server Components vs Client Components

3 min read Some experience helps
💡
In plain English
Two places code can run, and the difference decides most of what you can do. On the server, the code runs once on a machine you control before the page is sent — so it can read the database and hold secrets, but it cannot react to a click, because by the time the user clicks, that code has finished and gone. In the browser, the code is shipped to the visitor and runs while they use the page — so it can respond to clicks, and everything it knows is public.

This is the idea that makes the App Router different from everything before it, and the one worth reading twice. By default, your components run on the server only. They execute during the request, produce HTML, and their code is never sent to the browser.

Adding 'use client' at the top of a file opts that file — and everything it imports — into also running in the browser. That is what buys you state, effects and event handlers, and it is what costs you the download.

Server Component

The default. Runs during the request, can await a database, ships no JavaScript.

Client Component

Marked 'use client'. Gets state and events, and is downloaded by every visitor.

The boundary

A prop crossing into a client component crosses into the browser. That is the security line.

Hydration

The browser attaching behaviour to HTML the server already rendered.

!
Everything in a Client Component is public. Its source, and any value you pass into it as a prop, is in the browser and readable by anyone. An API key read in a Server Component and then handed to a client child is a leaked API key — the boundary is the prop, not the file.

The practical rule: keep pages as Server Components, and push 'use client' down to the smallest piece that actually needs to be interactive. A page marked client-side drags every component it renders into the browser bundle with it.

Not this · whole page goes client-side
'use client';         // at the top of the page

export default function Page() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <HugeStaticArticle />   {/* shipped too */}
      <button onClick={() => setOpen(!open)}>Menu</button>
    </>
  );
}
Do this · only the button is interactive
// page.tsx — a Server Component, ships no JS
export default function Page() {
  return (
    <>
      <HugeStaticArticle />
      <MenuButton />
    </>
  );
}

// MenuButton.tsx
'use client';
export function MenuButton() {
  const [open, setOpen] = useState(false);
  ...
}
i
A Client Component can still render server-rendered content: pass it as children from a Server Component parent. The child was already rendered on the server, so wrapping it in something interactive does not drag it into the bundle.

Every page in this admin area is a Client Component, and deliberately so: they are behind a login, they are dense with interaction, and they read the session from React context. The pages that a stranger sees first — the public site, published pages — are the ones where the server/client line is worth being strict about.

Why can a Server Component not use useState?Answer

Because state is a value that changes over time in response to a user, and a Server Component has no “over time”. It runs once, produces HTML, and is finished before the page arrives. There is nothing left to hold a value or re-run when it changes.

That is also the rule for hearing about it: the moment a component needs useState, an event handler, or a browser API, it needs 'use client'. Put that boundary as low in the tree as you can, so the interactive leaf ships to the browser and its parents stay on the server.
