Fetching and caching

2 min read Some experience helps
💡
In plain English
A cache is a note saying “I already looked this up, here is the answer”. It makes things fast and it makes them wrong, and the whole craft is deciding how long each answer stays trustworthy. A product price might be fine for an hour; an account balance is not fine for a second. Next.js caches aggressively by default, so most caching bugs here are stale data rather than slow pages.

In a Server Component you fetch data by awaiting it. There is no useEffect, no loading state, no waterfall of requests from the browser — the component is already running on a server that can talk to the database.

jsServer Component fetching
// No 'use client'. This runs on the server only.
export default async function ProjectsPage() {
  const projects = await db.project.findMany();   // safe here — never shipped
  return <ProjectList projects={projects} />;
}

In a Client Component you fetch the way the React note describes: an effect, a loading flag, an error state — which is what every screen in this admin area does, because it talks to a separate API with the signed-in user’s token.

Caching is where Next surprises people. On Next 14, fetch inside the App Router caches by default, so a request that looks live may be served from a store made minutes ago. Three controls decide it:

jsThe three cache instructions
// Cached forever until the build changes it:
await fetch(url);

// Re-fetched at most once a minute:
await fetch(url, { next: { revalidate: 60 } });

// Never cached — always fresh:
await fetch(url, { cache: 'no-store' });
!
A page showing stale data on a deployment while being perfectly fresh on your machine is almost always this. It is also the default that Next 15 reversed — there, fetches are uncached unless you ask. Being explicit costs one line and survives the upgrade either way.
